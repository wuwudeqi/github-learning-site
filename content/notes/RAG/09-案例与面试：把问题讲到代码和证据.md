# 案例与面试：把问题讲到代码和证据

这个项目的价值，在于你能解释一条回答是怎样得到的，哪一步会丢信息，以及修改后用什么证据判断是否更好。

面试官问“你做过什么”，你需要给出实施范围；问“为什么这样做”，需要解释机制和取舍；问“效果如何”，需要把实验条件与结果一起拿出来。下面按这三层准备。

## 1. 先把项目讲清楚

完成复现和理解后，可以这样介绍：

> 我做了一个面向内部代码托管与 CI/CD 平台的知识问答原型。资料包含使用说明、权限申请、故障记录和版本变化，输入是 Wiki 网页快照与文本 PDF。
>
> 我把 RAG 拆成文档解析、章节切分、向量与关键词检索、重排、上下文选择、证据判断和回答几个步骤。Python 实现关键逻辑，LangGraph 管理追问、一次补检索和终止分支。向量检索使用 BGE 和 Qdrant local，关键词检索使用 BM25，通过 RRF 融合。
>
> 我重点验证了三件事：正文与引用能否追溯；当前版本与历史版本是否会混用；跨章节问题是否找齐依据。实验使用自建模拟 Wiki 和带证据标注的题库，记录逐题结果与配置。真实生成模型的效果还需要接入后单独评测。

这段介绍刻意保留了“原型”“模拟语料”“生成效果待验证”。它们是实施范围，不能在简历里省略成“企业知识库生产落地”。你之后若用脱敏真实资料完成了测试，就补上自己确实完成的部分。

> [!TIP] 用一次失败替换一个形容词
> 与其说“显著提升稳定性”，不如说明：我把候选字段设计为每轮覆盖，并用机制检查验证第二轮检索不会混入旧候选。对方能继续追问，你也有代码可展开。

## 2. 五类业务问题，分别考察什么

以下平台与规则来自本项目的模拟语料。案例用于说明系统怎样处理问题，不代表你经历过这些线上事故。

### 案例一：我能拉代码，为什么还不能发布生产

**问题形态。** 用户把“仓库访问”和“环境发布”理解成同一种权限。检索如果只命中仓库成员说明，回答可能给出错误的申请路径。

**需要的依据。** `KH-002:s01` 说明仓库角色不自动授予生产发布权限；`KH-015:s01` 和 `s02` 说明生产授权期限与审批步骤。当前模拟规则中，生产发布最长 30 天，由项目负责人和生产环境负责人依次审批。仓库普通访问最长 180 天，不能套用到生产环境。

**定位方法。** 检查 query 是否保留“生产”；查看候选是否只有仓库文档；再核对最终上下文是否包含生产申请条件。若用户只是问“权限怎么申请”，仓库访问还是环境发布尚不明确，应先追问对象。

**可实施的优化。** 给证据保留 `system` 与章节标题，让重排区分访问目标；回答前逐项检查申请对象、期限和审批人是否都有依据。系统元数据可辅助检索，但跨系统问题不能简单只留下 CodeHub 或 FlowCI 的一侧。

**怎样检验。** 一组问题同时覆盖仓库、测试环境、生产环境和对象不明的提问。通过正确的仓库题，不能替代生产申请题和追问题的验证。

这里回答的是“如何申请”。用户是否已经拥有权限，需要实时身份与授权状态；当前知识问答代码没有查询这类状态。

### 案例二：本机 SSH 成功，流水线检出失败

**问题形态。** Q-009 的用户用个人电脑克隆成功，推断 FlowCI 应该也能成功。实际上，自动化流程通常使用配置的连接身份，不能直接套用个人电脑的凭据状态。

**需要的依据。** `KH-004:s03` 与 `KH-016:s01` 分别涉及本机密钥和自动化连接身份。回答应引导核对流水线使用哪个机器人或连接、该身份是否能访问目标仓库，并保留实际报错所限定的范围。

**本次观察。** 第一轮开发集里，Dense、BM25 与 RRF 的 Top-5 都只覆盖了一半标注章节。这是实际检索记录中的遗漏，不是模型生成错误。

**下一步怎样改。** 先检查缺失章节是否在 Top-20。如果不在，可比较“本机 SSH 身份”和“流水线检出连接身份”两个子查询；如果已经在，优先比较排序和上下文选择。子查询检索尚未加入当前实现。

**追问到源码。** 查询整理在 `prepare_question`；召回在 `HybridRetriever.search`；章节计分在 `retrieval_metrics`。能把同一道题沿这三个位置走通，比直接说“加 Agentic RAG”更具体。

### 案例三：合并到 main，流水线没有运行

**问题形态。** 用户提供了合并动作和现象，没有提供事件投递、接收与规则匹配记录。知识库中虽然有相似历史事故，也不能立刻断定本次根因相同。

**需要的依据。** `KH-017:s01` 记录过一个只配置 `merge_request`、没有配置 main 分支 push 触发的案例。`s02` 给出事件排查线索；`KH-010:s01` 区分 push 的推送分支与合并请求的目标分支。

**回答组织。** 先让用户沿 commit SHA、事件 ID、投递与接收记录检查，再核对触发规则和过滤原因。`EVENT_RULE_MISMATCH` 是本套模拟资料中的线索。相似事故可以作为一个待核对方向，不能写成“你的 main 规则一定没配”。

**RAG 中容易错的地方。** 故障记录语言通常更接近用户提问，可能排在规则说明前面。如果上下文只保留事故结论，生成模型就容易把过去的原因当成当前诊断。

**可检验的改善。** 保留 `authority=case_record`，在上下文中标明历史案例性质；让回答同时引用规则文档。当前代码保存了来源性质，模型提示也要求区分历史案例与本次根因，但这一生成效果还没有实测。

### 案例四：更新日期更晚，内容却是旧流程

**问题形态。** `KH-021` 是 1.0 的旧生产申请指引，虽然归档说明在 2026-09-02 更新，适用规则仍属于旧版本。它不能凭 `updated_at` 更晚就覆盖 2.0 的申请流程。

**方案。** 把文档修改时间、业务适用版本和有效状态分别存储。默认当前问题筛 active；明确问 1.0 时保留相应旧资料；明确比较新旧流程时需要两边的证据，不能默认只留一边。

**已修正的代码问题。** 多轮历史问过 1.0，当前用户转问“现在怎么申请”时，不能继续继承旧版本条件。`resolve_filters` 把本轮明确意图放在历史条件前面，机制检查覆盖了这个变化。

**局限。** 当前实现是可见的规则基线。诸如“迁移窗口内仍运行旧 Runner 的项目该怎么办”需要更细的业务条件，不能靠一个 `version` 字段自动理解。

### 案例五：两种 permission denied，处理却不同

**问题形态。** 平台在任务开始前返回 `ENV_ACCESS_DENIED`，与容器内脚本执行时返回 `permission denied`，虽然都带“权限”字样，失败层次并不相同。

**需要的依据。** `KH-019:s01–s03` 区分平台环境授权和任务内文件执行权限。回答要先识别失败发生在平台校验阶段还是脚本阶段，然后给出对应的检查方向。

**检索策略。** 错误码、文件路径和执行阶段是高价值信息，问题整理时要保留。BM25 有利于精确错误码，语义检索补充口语描述；是否更有效仍以逐题比较为准。

**验收重点。** 不能把两类问题都回答成“申请生产发布权限”。资料不足以确定失败阶段时应追问关键日志。本题属于保留测试集，不能拿它反复调到通过，再把结果当成未见问题上的效果。

## 3. 三个已经落到代码的工程问题

这些问题是在资料和代码核对过程中发现并修正的，可以作为实现记录。你亲自复现后，能够讲出触发条件和修复方式。

| 问题 | 为什么影响 RAG | 当前处理与证据 |
| --- | --- | --- |
| HTML 只提取链接文字，丢失 href | 命中“前往申请”，答案却没有可追溯入口 | 解析保留正文链接目标；机制检查核对输出 |
| tokenizer decode 重建切片 | 原始 URL、大小写或中文间距可能被改写 | FastTokenizer offsets 回切原文；真实 tokenizer 检查长文本与错误码 |
| 引用数组合法，正文却用了另一个 ID | 返回结构通过校验，展示引用仍然失真 | 同时核对正文标记、citations 数组和本轮上下文 |

这三项检查也有边界。保留 href 不能证明链接仍然可访问；保留原文不能证明 chunk 语义完整；ID 一致不能证明被引用的片段支持该句话。面试时把这一步的能力说准，后续讨论才有基础。

## 4. 面试追问怎样展开

### 为什么用了 LangGraph，还自己写检索函数

LangGraph 负责节点、状态更新和条件边，检索器负责候选与分数。把两者分开，可以在不改控制流的情况下比较 Dense、BM25 与 RRF，也能用固定检索结果检查重试分支。

对于固定的一次检索加一次生成，普通函数足够。本项目有“需要追问”“再检索一次”“资料不足终止”的不同路径，所以图结构有解释价值。框架本身不会让证据变得更正确。

### 为什么没有一开始就上多 Agent

本任务中的主要不确定性来自问题条件和证据完整性。先把检索与判断做好，能够直接解决这类损失。多个 Agent 各自总结一遍，并不会自动补回缺失章节，还会增加上下文传递与评测复杂度。

如果以后确实需要不同系统的独立工具和权限边界，可以再评估拆分。那是新增需求，不是当前原型必须拥有的部件。

### 向量查询和 SQL 查数据库的区别是什么

SQL 更适合按已知字段约束查结构化事实，例如当前审批单状态。向量检索根据语义表示找相近文档片段，适合员工用不同说法询问已有知识。两者能组合，但不能让向量近邻代替业务精确条件。

本项目里版本与状态属于 metadata 条件，片段相关程度交给检索。对于“我现在有没有发布权限”，最终需要权威业务接口；相似文档只能解释规则。

### 为什么用了向量，还保留 BM25

“任务一直等不到执行器”和 Runner 调度说明可以通过语义对应。`RUNNER_NO_MATCH`、`build/test` 与 `build-tests` 则包含需要精确保留的标识符。两种表示各有优势，候选能互补。

但混合检索不保证每题更好。当前开发集显示章节 Recall 略有改善，全覆盖却没有超过 BM25；本批保留题中 BM25 的表现更好。这就需要继续分析遗漏题和数据分布，不能只凭组件变多判断方案更好。

### 为什么不直接把相似度分数相加

向量相似度和 BM25 分数不在相同尺度。某一条路的数值范围较大时，直接相加可能让它主导结果。RRF 只用排名，减少对分值校准的依赖，代价是丢掉原始分数差距。

也可以做经验证的归一化或学习融合权重，但需要数据和校准。当前样本规模较小，RRF 是容易复查的起点，公式与手算例子见第 04 篇。

### Chunk 为何不是越小越精准

“有效期 30 天”单独成块，无法知道它限制的是生产发布还是仓库访问；一整篇都入上下文又可能塞入无关规则。切分需要同时保留条件和结论，再受模型长度约束。

本代码先按 h2 章节，再按 token 窗口切长片段。它没有完整实现列表、表格和跨页段落的语义切分。当前短语料也不足以比较 overlap 的最优值，所以长文实验应单独准备。

### Embedding 换模型后，为什么要重建索引

维度不一样肯定不能直接比较；维度一样也不代表坐标空间一致。文档向量和查询向量必须来自匹配的编码方案，前缀、归一化和版本也要保持一致。

切片正文改变同样需要更新对应向量。生产增量方案还要删除旧 chunk、防止新旧版本混存，并记录索引构建批次；当前实现每次重建本地索引，没有完成生产增量服务。

### 重排为什么更准，却不能把所有文档都交给它

双塔检索可以预先计算文档向量，查询时快速比较。CrossEncoder 把问题和每个候选一起输入模型，能看细致交互，但每对文本都需要计算。

因此先召回有限候选再重排。池子太小会丢证据，太大会增加计算成本。输入长度是问题与候选的联合长度；当前代码超过模型预算会报错，避免默默截断后还以为文档完整参与评分。

### 什么情况下应追问，什么情况下应补检索

“怎么申请权限”缺少申请对象，用户补一句可能就确定流程，适合追问。“生产权限由谁审批”对象已经明确，但当前候选没有审批说明，应尝试补检索；仍无依据则说明缺失。

让用户补充知识库本该拥有的答案，或不断改写一个本身含糊的问题，都不能解决信息来源不对的问题。当前真实模型判断效果尚未验证，规则替身只帮助检查这几个出口。

### 如何避免重试两轮以后状态越来越乱

只让轨迹字段追加。候选、上下文和引用属于当前轮结果，按轮覆盖；另存上轮候选 ID 用来判断补检索是否带来新证据。重试次数设置上限，并明确失败出口。

历史问题用于理解指代，本轮版本意图优先。LangGraph 的 reducer 如果误把候选定义成列表累加器，就会把过期证据带入下一轮。这是状态建模问题，不能靠更长提示词修复。

### 有引用就能认为没有幻觉吗

不能。引用 ID 可以合法，片段却不支持那句话；引用也可能支持旧版本规定，却不适用于当前问题。代码先验证引用范围和结构一致性，再由事实评审检查支持关系与适用条件。

“有引用”“引用支持说法”“回答解决了用户问题”是三个需要分别判断的层次。

### 如何说明没有答案时的效果

准备真实无答案问题和条件缺失问题，分别标 expected_action。检查系统是否给出错误确定结论，是否追问到了决定流程的条件，还要防止所有问题都拒答造成表面安全。

本次已有这类题，但没运行真实生成与判断模型，所以不能报告拒答准确率。把已有数据、接入点和后续评审方法说明白即可。

### Java 后端经验在哪里有帮助

数据契约、条件过滤、版本替换、幂等、超时、状态机与观测方法都能迁移。你熟悉的排查思路仍然有效：先确认输入、记录中间状态、定位异常边界、再用可重复样例验证。

需要额外补足的是检索评测、模型输入预算、概率输出的判断方式，以及 Python 依赖与类型使用。不能因为熟悉后端接口，就把相似度分数当成确定的业务结果。

JDK 8 → 21 和 Oracle → PostgreSQL 的经历可以放在独立 Java 专题里，围绕你实际做过的兼容评估、数据校验与回滚设计展开，不必强行塞进这个 RAG 原型。

> 研发平台知识问答原型（Python、LangGraph）：围绕代码托管与 CI/CD Wiki，实现正文解析、章节切分、BGE 向量检索、BM25/RRF 融合及带来源的上下文组织；构建 24 篇模拟文档和 72 道带证据标注的问题，分开验证召回、控制流与引用一致性，分析跨章节遗漏和版本继承问题。

如果要加指标，连同“模拟数据”“开发集/保留集”“指标单位”一起写。不要写“准确率达到 95%”，因为本次测的是章节检索，不是最终回答。

## 6. 按你的时间安排练习

你每天可投入 4 小时，同时还有预算 Agent 和其他面试准备。RAG 这一块先安排约 10～14 个学习日，实际进度以能否独立完成练习为准，避免把全部两个月耗在部署外壳上。

| 学习日 | 重点 | 结束时应能交付的东西 |
| --- | --- | --- |
| 1～2 | 阅读 01～03，补 Python 数据对象、列表与字典处理 | 手工追踪一篇 HTML 到 chunk，解释来源与版本字段 |
| 3～4 | 跑 BGE、Qdrant、BM25、RRF | 给一道题列出三路候选和分数含义 |
| 5～6 | 重排与上下文预算 | 解释一个排序失误及重排能否解决 |
| 7～8 | LangGraph、引用、真实模型接入 | 画出三种出口，用日志说明重试何时停止 |
| 9～10 | 评测与错误归因 | 复现开发集，完成一项受控对照实验 |
| 11～14 | 补薄弱环节、生成评审与面试演练 | 一份失败记录、一个可复现改动、一段能被追问的项目介绍 |

每天可把 1 小时用于阅读和画流程，2 小时用于运行与改代码，1 小时用于记录失败和口述讲解。真实模型接入需要你自己的服务配置；未接入时先完成检索与状态练习，别把替身输出误记为模型表现。

最后做一次不看笔记的演练：从用户提问开始，解释资料怎样进入索引、为什么命中这几条、缺少证据怎么办、引用如何产生，以及你怎样知道修改有效。卡在哪一层，就回到对应的文件和案例补齐。
