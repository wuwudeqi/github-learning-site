# 实验与评测：用受控时序验证机制

只读源码容易产生“看起来应该这样”的理解。实验要把边界变成可观察的状态：第二次模型请求到底何时发出？B 先完成时历史是什么？取消到达后是否覆盖最终结果？

本章提供两份可运行代码：新的机制实验 [runtime_lab.py](code/runtime_lab.py)，以及外部操作与裁剪实验 [harness_lab.py](code/harness_lab.py)。两者只用 Python 标准库，不联网、不调用真实模型、不修改实际业务数据。

```bash
python3 'content/notes/Codex Harness/code/runtime_lab.py'
python3 'content/notes/Codex Harness/code/harness_lab.py'
```

实际记录：[机制实验：13 项检查](code/runtime-verification.txt) · [基础实验：8 项检查](code/verification.txt)。它们验证教学实现，不等于运行 Codex Rust 测试，也不等于证明真实模型质量。

## 1. 为什么使用事件屏障，而不是 sleep

如果让 A sleep 0.2 秒、B sleep 0.1 秒，通常 B 先结束，但这把预期建立在调度与机器负载上。更好的方式是让 A 明确等待 `release_a`，B 设置 `done_b`。控制器确认 B 已结束后，再释放 A。

这样“B 先完成”是实验前提，不是一次偶然观察。脚本的十秒 timeout 仅用于发现死锁，不参与性能测量。

## 2. 实验 A：执行顺序与结果记录顺序

脚本模型不是调用真实 API，而是按计划发出 A、B 两个 call。运行时先记录 call，再 `create_task` 启动工具；模型响应结束后，按插入顺序等待这些 task，并把结果写进历史。

关键代码请对照文件阅读：

```python
in_flight.append(asyncio.create_task(tool(item['name'])))
# 两个 task 已经可以运行；下面的 await 不会把启动方式变成串行
for pending in in_flight:
    output = await pending
    history.append(output)
```

如果把 `create_task` 改成“存两个尚未调度的协程，再逐个 await”，可能就真的成为串行。理解 future、task 和调度时机，比看到 `async` 就说“并行”更重要。

实际轨迹的关键部分：

```text
record_call_A → handler_start_A
record_call_B → handler_start_B → handler_done_B
response_completed_1
handler_done_A → record_output_A → record_output_B
model_request_2 → turn_finished
```

这条轨迹同时证明教学实现里三件事：B 在 A 未结束时完成；response 完成后仍需等待 A；第二次模型请求看到 A、B 两份输出。它没有测量吞吐量，也没有复现 Codex 的全部事件协议。

**反事实练习：** 把第二次模型请求挪到 drain 之前，预测它的输入缺少什么；把有序收集改成按完成收集，预测历史顺序怎么变化。先写下预测，再修改副本验证。

## 3. 实验 B：公布能力与执行能力保持同一视图

脚本捕获一个只读 Step 视图，工具版本为 v1。A 还没完成时，全局注册表切换到 v2；A、B 返回的版本仍是捕获的 v1。

实验验证的是“执行使用被捕获的值”，不是冻结外部世界，也不是证明真实 MCP 连接不会失效。若把工具改成执行时读取全局注册表，则 A 可能读取新值，这正是第二章讨论的版本跨越问题。

Python 的字典拷贝加 MappingProxyType 只是这个语义的教学表达，不能用它的内存行为推断 Rust Arc 的性能。

## 4. 实验 C：取消在终态之后到达

handler 先设置 terminal，表示完成结果已经形成，然后暂停生命周期收尾。控制器此时发送取消。运行时如果看到 terminal，等待正常结果，而不是覆盖成 aborted；控制器最后释放收尾屏障。

这里刻意把“形成结果”和“全部收尾完毕”拆开，使竞态窗口可重复出现。测试检查取消分支已经选中保留结果、runner 尚未完成，最终返回 completed。

若取消在 terminal 之前到达，应走另一类路径；本脚本的 race 场景只执行晚取消分支，不据此宣称所有取消路径都已覆盖。更不能把本地 task 取消等同于远程业务撤销。

## 5. 实验 D：请求视图修复与稳定身份

`prompt_view` 拷贝普通调用历史，对缺失输出补 aborted，并由源 item ID 稳定派生合成 ID。连续执行两次，检查结果相同且原始历史未改变。再保持 call ID 不变、修改源 item ID，检查合成身份变化。

这解释为什么“配对 ID”和“条目身份”需要区分。脚本使用自己的 UUID 命名空间，不生成 Codex 同款 ID；也没有覆盖工具搜索、具名外部输出、多模态规范化。

**反事实练习：** 把派生 ID 改成随机 UUID，比较序列化后的两份输入。可以证明字节不稳定，但不能直接得出实际服务端缓存下降了多少；后者必须真实测量。

## 6. 实验 E：压缩后的旧基线为什么危险

教学状态包含 cwd 和禁止写入设置。压缩摘要不含这两个字段，如果基线仍声称它们已经发送，则差量为空。清空基线后，全量字段重新出现在下一次输入。

测试验证旧基线方案确实丢掉了模型可见设置，而重建方案补齐。这只演示基线一致性，不执行真实摘要模型；它无法检验摘要是否曲解用户意图。

同一组还检查外层决策：有待处理输入应继续；需要继续且超窗口应压缩；无后续工作但达到阈值，只进入候选终止分支，不为不存在的下一次采样强行压缩。真实停止钩子不在该教学函数内。

## 7. 外部副作用实验：提交后响应丢失

`harness_lab.py` 在同一个 SQLite 事务中写产物记录与操作记录，提交后主动抛出超时，再重新连接数据库，用相同 operation ID 重试。检查结果复用、产物未重复；同 ID 不同参数被拒绝；明确的新 ID 可以创建第二次操作。

边界很明确：产物是数据库记录，不是对象存储里的真实文件。这个实验没有证明跨系统原子性，也没有实现租约与 fencing。若面试官继续问多 Worker 接管，应回到第五章的故障窗口分析。

## 8. 从机制验证走向真实模型评测

下一阶段才能回答“这些优化让 Agent 更好吗”。固定模型、仓库版本、工具、权限、任务集和预算；一次只改变一个变量，例如输出裁剪策略或压缩时机。

| 问题 | 机制实验可以证明 | 真实模型实验还要测什么 |
| --- | --- | --- |
| 关键证据被保留了吗？ | 输入确实包含特定行 | 模型是否据此正确修复 |
| 请求身份稳定了吗？ | 重复构造结果一致 | 实际缓存用量、延迟与费用 |
| 工具并行了吗？ | 执行区间存在重叠 | 限流、冲突与端到端耗时 |
| 压缩后字段仍可见吗？ | 重建输入包含约束 | 长任务是否继续遵守约束 |
| 重试是否重复副作用？ | 教学数据库没有重复行 | 真实服务超时、接管和外部状态 |

评测任务要包含正常完成、需要澄清、应拒绝、工具故障和不可完成场景。预先定义各自成功标准；不要把正确拒绝视为失败，也不要删除基础设施失败样本。

## 9. 指标口径和归因

记录全部任务的成功数与分母、总费用、成功运行与全部运行的延迟分布、超时、人工干预和失败类别。费用/成功任务使用全部运行费用除以成功数，成功数为零时不定义这个比率。

另外记录关键路径事件：模型请求开始、完整工具 item 到达、准入、handler 完成、结果记录、下一次请求。这样能判断改善来自输入减少、排队减少还是失败减少。

不要同时修改模型、提示词、工具并发和压缩，再把最终变化命名为“Harness 优化收益”。当前专题没有完成真实模型对照评测，不提供性能提升百分比。
