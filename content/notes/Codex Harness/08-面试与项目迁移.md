# 面试与项目迁移

## 三分钟讲述：按实际完成程度使用

下面是学习分享的表达模板。实际读通源码、运行实验后再使用相应句子；不要把本专题的作者工作自动当成自己的经历。

**前 30 秒：问题与范围。** “我研究 Codex Harness，是想理解模型之外如何支撑持续执行。我关注执行循环、上下文和工具边界，固定了源码版本，没有把开源客户端实现等同于整个云服务。”

**接着 60 秒：一个具体机制。** “以工具输出进入历史为例，长结果需要限制体积，历史又必须保持调用和输出配对。裁剪与规范化解决不同问题，前者影响证据可见性，后者保证结构。结构修复也不能把缺失结果伪装成成功。”

**再 60 秒：验证与局限。** “我用教学日志验证了前缀裁剪会遗漏中间证据，并用数据库实验模拟提交后响应丢失。实验验证了局部不变量，还没有证明真实模型完成率提升，也不覆盖对象存储的跨系统一致性。”

**最后 30 秒：迁移。** “在预算分析 Agent 中，我会把业务权限留在服务端，工具结果绑定数据版本，导出使用业务操作 ID，并评测澄清、拒绝和故障场景。优先把单 Agent 执行做可靠，再判断是否需要多 Agent。”

## 连续追问与回答要点

### 1. Harness 与 Agent loop 有什么区别？

Loop 是决定继续推理、调用工具或结束的反馈结构。Harness 还要提供上下文、执行环境、权限、状态和观测。具体项目术语可能不同，应先明确自己讨论的边界。

追问“最小实现是什么”：一个模型适配器、有限工具集、历史、停止预算与执行边界能构成教学闭环。生产场景还要处理持久化、取消、权限和故障；不能把短循环演示当成完整系统。

### 2. 模型够强，还需要这些工程吗？

需要。工作目录、实际权限、进程生命周期和数据库事务是运行条件。模型可以提出正确动作，但执行环境仍可能失败。

追问“怎么定位”：按输入证据、模型选择、参数、权限、执行结果、状态记录逐层检查，避免把工具故障归因于推理。

### 3. 上下文越大越好吗？

更大的容量能容纳更多资料，但仍要考虑相关性、费用与干扰。关键是保留当前任务需要的证据与约束。

追问“怎样证明压缩有效”：固定任务和模型，对比约束遗漏、最终完成率、输入体积与压缩耗时。只证明摘要更短不够。

### 4. 共享历史快照有什么收益？

减少只读消费者的深复制。该版本用共享所有权与写时复制表达这种意图。

追问“是否降低 token”：不会自动降低，它作用于宿主内存。追问“有没有代价”：共享快照存活期间写入可能复制，旧版本也占内存，需要按读写比例测量。

### 5. 为什么不能把工具全部并行？

因为有输入依赖、副作用冲突和资源限制。资格声明与具体调用依赖是两个层面。

追问“读操作一定安全吗”：读操作也可能依赖前一步生成的文件，或耗尽连接池。还要考虑一致性快照与限流。

### 6. 会话恢复能保证只执行一次吗？

不能。历史恢复与外部副作用是不同的状态边界。超时之后可能已经提交，应先核对操作结果。

追问“如何做”：应用层操作 ID、参数指纹、唯一约束和结果查询；跨系统时进一步讨论外部幂等、发布流程与对账。明确同库事务能保证什么，无法覆盖什么。

### 7. 审批与沙箱能互相替代吗？

不能。审批对应授权决策，沙箱对应资源限制。业务操作还需要领域权限判断。

追问“缓存审批的风险”：键和作用域过宽造成错误复用，过窄导致反复询问。要检查动作变化与权限失效场景，不能只优化审批次数。

### 8. 工具调用成功，Agent 就成功了吗？

不是。命令可能测试错目录，查询可能使用错误口径。协议完成、工具成功与业务验收要分别记录。

追问“谁验收”：确定性条件交给程序检查；语义条件使用明确评测标准，必要时人工复核。不能只依赖同一个模型自称完成。

### 9. 你做了什么，哪些来自开源？

明确区分官方机制、自己的阅读归纳、教学实验和实际应用改造。用提交、日志或实验记录证明自己的贡献，不把阅读大型仓库表述为自研该系统。

追问“优化了多少”：没有真实测量就说尚未测量，给出评测方案。拿出一个清晰的失败样例和恢复验证，通常比虚构提升比例更扎实。

## 迁移到 Java 预算分析 Agent

| Harness 思路 | 业务迁移方案 | 验收证据 |
| --- | --- | --- |
| 工具契约 | 结构化指标查询，服务端校验部门与口径 | 越权被拒绝、单位与期间正确 |
| 有限上下文 | 摘要保存目标、版本和结果引用 | 压缩后仍使用正确数据快照 |
| 事件分层 | task、step、tool operation 分层记录 | 能关联查询、导出与终态 |
| 故障恢复 | 操作 ID、参数指纹、结果核对 | 响应丢失后无重复产物 |
| 评测 | 正常、澄清、拒绝、故障任务集 | 各类结果与费用口径明确 |

这些是拟实现方案，不是原公司已上线功能。更完整的业务讨论见[技术实现与工程边界](../agent项目/03-技术实现与工程边界.md)。

## 进阶：什么时候再引入多 Agent

当子任务可以独立验证、输入输出边界清楚且并行收益可覆盖协调成本时，再考虑拆分。读多个独立模块可能适合；多人同时修改同一份核心文件容易产生冲突。

代价包括重复上下文、结果合并、共享资源冲突、取消传播和总预算管理。可以用同一任务集比较单 Agent 与多 Agent 的完成率、总费用、耗时和人工修复次数。仅凭子任务“看起来同时运行”不能证明整体更优。

> **Tip｜高质量回答的顺序**
> 先描述具体故障，再解释机制，接着说明取舍，最后给证据与边界。技术名词只在帮助解释时使用。
