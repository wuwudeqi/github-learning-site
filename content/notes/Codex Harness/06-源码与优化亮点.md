# 源码与优化亮点：从控制条件推导收益

本章把前面分散的机制组合成一张可验证的源码地图。版本固定为 `d6489472f3c15e87d2d7763a5fde033545c530f8`。本次进行了关键路径静态阅读与教学实验，未运行 Codex 完整 Rust 测试。

## 1. 一条应当亲自走完的调用链

```text
session/turn.rs::run_turn
  ├─ 捕获 StepContext
  ├─ clone_history → for_prompt
  └─ run_sampling_request
      ├─ build_prompt
      └─ try_run_sampling_request
          ├─ 消费 ResponseEvent
          ├─ OutputItemDone → stream_events_utils::handle_output_item_done
          │   ├─ ToolRouter::build_tool_call
          │   ├─ 记录完整调用
          │   └─ ToolCallRuntime::handle_tool_call
          │       ├─ 保留同一个 StepContext
          │       ├─ readiness → 读锁 / 写锁准入
          │       └─ router.dispatch... → 对应 handler / runtime
          └─ drain_in_flight → 记录工具结果
  └─ 检查继续、输入队列、窗口边界、停止钩子
```

这张图覆盖本专题追踪的主要路径，不表示每个工具都进入 ToolOrchestrator，也不展开 Code Mode 的所有实现。读代码时先用一个普通工具建立路径，再扩展其他工具类别。

主要入口：[turn.rs](https://github.com/openai/codex/blob/d6489472f3c15e87d2d7763a5fde033545c530f8/codex-rs/core/src/session/turn.rs) · [stream_events_utils.rs](https://github.com/openai/codex/blob/d6489472f3c15e87d2d7763a5fde033545c530f8/codex-rs/core/src/stream_events_utils.rs) · [parallel.rs](https://github.com/openai/codex/blob/d6489472f3c15e87d2d7763a5fde033545c530f8/codex-rs/core/src/tools/parallel.rs)

## 2. 六个优化要分别记账

| 机制 | 直接作用 | 需要付出的代价 | 应观测什么 |
| --- | --- | --- | --- |
| 完整工具 item 到达即启动 | 重叠模型流与工具执行 | 收尾与失败路径更复杂 | 流结束前的工具执行区间 |
| 共享历史快照 | 减少只读消费者深复制 | 写时复制和快照滞留 | 分配量、快照寿命、规范化耗时 |
| 稳定合成输出 ID | 消除请求内无意义变化 | 依赖稳定派生规则 | 同历史重复生成的请求差异 |
| 有条件的工具并行 | 重叠独立操作 | 队列、资源竞争与粗粒度独占 | 准入等待与 handler 时间 |
| 增量上下文与基线 | 减少重复上下文表达 | 压缩 / 恢复必须维护基线 | 全量注入频率与请求大小 |
| 轮次内复用模型客户端 | 复用连接和路由状态 | 必须清理响应级身份 | 建连、请求重试与关联准确性 |

“源码使用了某机制”是观察；“因此这里可能减少开销”是机制推论；“在任务集上快了多少”必须有实验。三种说法不要混写。

## 3. 用关键路径算一次潜在收益

假设第一个工具在模型流结束前 0.8 秒启动，执行耗时 2 秒。若等模型流结束再启动，流结束后还需 2 秒；提前启动时，理想情况下只剩 1.2 秒。潜在节省是重叠的 0.8 秒，而不是整个 2 秒。

如果两工具 A=2 秒、B=0.4 秒都在流结束前启动，最终还需等待较慢的依赖路径。把并行工具耗时相加会高估端到端耗时；只看 B 的完成时间又会低估真正完成时间。

这些是假设值，用于解释测量口径。真正测量应记录 response 开始、每个 item 完整到达、准入、handler 完成、结果记录和下一次采样开始的时间。

## 4. 为什么优化不能只改一行并发参数

提高并发上限可能减少等待，但同时增加文件系统竞争、API 限流与上下文结果量。结果过多又可能触发压缩，压缩再增加模型请求。局部工具更快，最终任务未必更快。

正确实验应固定任务集、模型与工具集合，先画出关键路径，再挑一个瓶颈。例如瓶颈在串行准入，就检查哪些工具能安全声明并行；瓶颈在大输出，则先优化结果结构；瓶颈在重试，则优先定位错误类型。不要同时改提示词、工具和模型后再猜原因。

## 5. 两处不能被“亮点介绍”掩盖的限制

第一，`for_prompt` 会规范化共享快照，因此“Arc 让每个 Prompt 零复制”的说法不成立。必须沿消费者看到 `Arc::make_mut`，才能理解复制何时发生。[历史请求视图](https://github.com/openai/codex/blob/d6489472f3c15e87d2d7763a5fde033545c530f8/codex-rs/core/src/context_manager/history.rs#L389)

第二，`run_turn` 中存在预估新输入占用的 TODO：当前此处采样前压缩发生在部分新输入记录之前。这是一个待完善方向，不能描述成已经完全实现的提前预算保护，也不能据此推导其他边界保护不存在。[TODO 位置](https://github.com/openai/codex/blob/d6489472f3c15e87d2d7763a5fde033545c530f8/codex-rs/core/src/session/turn.rs#L180)

真正有深度的分析应同时看到收益和尚未覆盖的条件，而不是为开源项目整理一张优点清单。

## 6. 一个可执行的源码阅读方法

以“取消会不会覆盖已完成工具”为问题：先到 parallel.rs 找取消分支；记录它读取哪些终态标志；找到标志由谁设置；再看针对 race 的测试如何控制时序。最后明确 Rust task 终态与外部进程状态的边界。

推荐检索：

```bash
rg -n 'terminal_outcome_reached|dispatch_handle|cancelled' codex-rs/core/src/tools/parallel.rs
rg -n 'terminal_outcome_reached' codex-rs/core/src/tools
rg -n 'cancellation_after_handler_finishes' codex-rs/core/src/tools/parallel.rs
```

再以“请求缓存为何会被修复历史影响”为问题：追 `for_prompt` 到 normalize.rs，比较随机 item ID 和稳定派生 ID 生成的输入。不要只搜索包含 cache 的文件；缓存失效源可能出现在上游任何序列化内容里。

## 7. 每条源码结论都留一张记录卡

```text
问题：结果较快的 B 为什么没有先写进历史？
版本：固定提交
生产者：ToolCallRuntime 启动 dispatch task
集合：FuturesOrdered 按插入顺序交付
消费者：drain_in_flight 逐项记录
观察：并发完成顺序可与记录顺序不同
代价：慢的队头结果阻塞后续交付
验证：事件屏障确保 B 先完成，检查执行轨迹与历史顺序
限制：教学实验不是 Codex 全部工具路径的性能测量
```

> **Tip｜读懂的标准是能预测改动后果**
> 删除结果收尾会发生什么？把稳定 ID 换成随机值有什么变化？重试一直用旧输入会丢掉什么？能答这些问题，才说明已经超越“知道模块名字”。
