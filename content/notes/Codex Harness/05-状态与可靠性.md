# 状态与可靠性

## 会话恢复不等于业务恢复

官方提供 Thread 的恢复与读取接口，但不能由此推出外部命令、数据库操作都具备事务回滚或恰好一次语义。[App Server 会话接口](https://learn.chatgpt.com/docs/app-server)

以下以“生成预算导出文件”为教学场景，讨论可以迁移到业务 Agent 的工程设计。它不是对 Codex 外部副作用保障的承诺。

## 最容易出错的窗口：已经成功，响应却丢了

![故障窗口：外部操作提交与任务结果记录之间发生中断](images/recovery.svg)

时间线上，文件已经生成，但调用方在收到结果前超时。此时状态是“结果未知”，不能直接当成“没有执行”。如果重试总是生成新文件，就会产生重复操作。

| 中断位置 | 已知事实 | 合理恢复方式 |
| --- | --- | --- |
| 执行前 | 尚未发起副作用 | 根据当前授权重新调度 |
| 请求发出后、结果未知 | 可能已完成 | 先按操作标识查询结果 |
| 外部已提交、任务记录未更新 | 两边状态可能不一致 | 对账并补写记录，避免盲目重做 |
| 结果已记录、前端未收到 | 后端已有可信结果 | 重读状态或重新发送结果 |

## 调用 ID 与业务操作 ID

调用 ID 关联一次模型工具请求与返回。业务操作 ID 标识一次逻辑副作用。网络重试或模型再次提出同样请求时，调用 ID 可能变化，但同一逻辑导出应该复用业务操作 ID。

幂等键可绑定用户、规范化参数、数据版本和明确的操作意图。仅用自然语言文本容易误判；仅用参数哈希也可能把用户明确要求的第二次导出合并掉。应由应用层确定“这次究竟是不是重试”。

> **Tip｜幂等需要冲突检查**
> 同一个操作 ID 携带不同参数时应拒绝或显式处理，不能返回旧结果假装成功。先持久化“处理中”也不够，还需要识别失效 Worker 并处理恢复。

## 对后端工程师最有价值的迁移点

如果副作用与任务状态位于同一数据库，可以用事务与唯一约束保证特定边界内的原子性。如果跨文件系统、对象存储或第三方服务，就要依靠外部幂等支持、暂存后发布、操作查询与对账等办法。

“先写 checkpoint，再调用外部接口”仍有故障窗口；“先调用接口，再写 checkpoint”也有。难点在于两种系统没有共享事务。面试时要明确保证覆盖哪个边界，以及剩余风险如何发现和修复。

## 取消是一段协议

收到取消信号后，调度器停止产生新工作；执行器尝试取消当前工作；系统确认终态并记录已发生的副作用。如果进程忽略信号、子进程继续运行或远端请求已提交，就不能只更新前端按钮。

教学状态可采用 `RUNNING → CANCELLING → CANCELLED`，同时允许记录“远端结果待核对”。状态名不重要，关键是不能用本地取消成功推导远端没有执行。

## 可观测性要支持定位因果

一次运行至少记录任务、轮次、工具调用和业务操作的关联标识，以及模型耗时、工具耗时、审批等待、错误类型和最终验收结果。记录信息应足够重建执行过程，并对敏感内容做适当处理。

不能从单条“工具成功”日志推出任务成功；也不能从所有工具耗时之和推出端到端时间，因为工具可能并行。性能分析应沿关键路径区分推理、执行、等待和重试。

练习：用户取消导出后，文件仍然生成。如何回答？先说明取消到达哪个阶段、远端是否支持取消、文件是否已发布；再按产品语义决定保留、清理或提示。不要宣称撤销了无法回滚的操作。
