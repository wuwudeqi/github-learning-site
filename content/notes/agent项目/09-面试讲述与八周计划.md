# 面试讲述与八周实施计划

本篇用于安排讲述顺序和实施进度。逐题技术回答请读[面试追问与回答示范](10-面试追问与回答示范.md)。实现细节见 Agent 流程、分摊语义和对应专题，按照“架构 → Agent 机制 → 技术实现 → 难点 → 证据”准备。

## 1. 三分钟介绍结构

先背景约 30 秒，再架构约 45 秒，Agent 流程约 45 秒，核心难点约 45 秒，实际完成情况约 15 秒。时间仅作练习参考，不必机械计时。

### 当前设计阶段的讲述示例

“我过去做的是企业内部预算与核算系统，集中项目支出、人力费用等多来源数据，支持员工做多项目汇报。同一个项目还可以从部门、重量级团队和投资等维度看分摊结果。数据集中以后，临时卡片和图表仍主要靠开发定制，员工要学习复杂页面和口径，系统更新又需要培训。

在这个业务背景上，我设计了独立的智能分析与汇报助手，使用合成数据。用户描述要汇报哪些项目、什么期间、从哪个维度看，Agent 补齐必要条件后调用已有业务能力，按需下钻，生成图表、Excel 和可核对的数据。

架构上，Spring Boot 负责用户身份、分摊规则、指标查询和导出，Python/LangGraph 负责多步分析、等待用户输入和恢复。Java 持久化提交关系，Python 受理任务后立即返回 ID，模型调用和业务查询在后台推进。Skill 管分析方法和使用说明，MCP 包装已有 Java 能力，模型的 Function Calling 请求由运行时实际执行。

我最关注的是分摊语义正确，而不是 SQL 能不能跑。例如 P01、P02 总预算 120 万、实际 126 万，按部门 D_A 的比例计算后是预算 52 万、实际 56 万。不能拿整个项目总额冒充分摊结果，也不能把部门和投资两个口径的结果相加。查询计划绑定数据、规则和指标版本，Java 确定性计算，再让各种产物复用同一个结果。

工程上围绕错误连接、版本漂移、导出响应丢失等问题准备复现实验。当前完成的是设计文档和文中列出的局部合成实验，完整模型调用、权限隔离和 LangGraph 恢复仍以实际集成进度为准。”

实现完成后按实际状态改成过去时，加入最扎实的一项实验结果。不要把独立项目说成公司生产上线，也不需要主动讲与项目无关的简历历史。

## 2. 深入展开顺序

先画架构和一次请求链路，再讲 Agent 状态、路由与工具契约。面试官追问时进入指标、版本或任务实现，最后用对应失败轨迹和验证结果支撑。避免一开始列框架名或连续讲四个事故。

### 20 分钟技术展开地图

| 时间参考 | 重点 | 应展示的具体对象 |
| --- | --- | --- |
| 0～3 分钟 | 背景、范围、架构和职责 | 架构图、受理与执行分离 |
| 3～7 分钟 | 哪一步需要模型决策 | 动作 JSON、两条不同下钻路径、停止条件 |
| 7～11 分钟 | 如何保证查得对 | 查询 DSL、指标目录、聚合 SQL、证据引用 |
| 11～15 分钟 | 失败后如何恢复 | T0～T8 时间线、操作 ID、任务唯一键 |
| 15～18 分钟 | 如何定位和验证 | 错误分类、基准结果、评测分母 |
| 18～20 分钟 | 代价与尚未覆盖内容 | 服务复杂度、快照成本、未完成集成测试 |

根据面试官兴趣调整，不要求一次讲完。七年经验的重点是能从一个问题继续下钻到实现和取舍。

## 3. 不同面试官面前如何展开

| 面试关注点 | 先讲的具体问题 | 接着拿出的证据 |
| --- | --- | --- |
| 业务理解/项目负责人 | 原系统已解决数据集中，Agent 补临时组合和使用引导；分摊是业务核心 | 旧流程与新流程、清晰的角色及完成标准 |
| Agent 开发 | 模型在哪里选择工具、何时补问、观察后为什么下钻、如何停止 | 一条只制图和一条继续下钻的动作轨迹 |
| Java 后端 | 分摊粒度、版本发布、请求幂等、事务和资源隔离 | 有效计划、SQL、任务唯一键、故障时间线 |
| 数据/安全 | 结果是否语义正确、跨轴权限是否扩张、原始金额是否可反推 | 反例数据、拒绝结果、核对包、授权测试范围 |

完整问题和连续追问统一放在[面试追问](10-面试追问与回答示范.md)，不在本篇再背一张框架名词表。每次回答按“结论 → 本项目例子 → 实现机制 → 取舍与证据”推进。

### 五分钟现场演示脚本

1. **普通汇报。** 请求 P01、P02 上半年按部门汇总；展示系统确认的口径，D_A 52/56 万、D_B 68/70 万，图表与查询表能核对。
2. **有价值的澄清。** 清空分摊上下文后说“按部门看”；若项目管理归属和部门分摊都适用，系统问一次；选定后不再反复问。
3. **口径变更。** 说“改按投资看”；展示新 plan_revision、新 result_id，旧部门结论不混进投资报告；旧报告仍能以原版本查看。
4. **权限和能力边界。** 使用仅有 D_A 分摊范围的测试用户请求其他部门或原始全额；拒绝/说明授权范围。请求没有联合规则的“部门×投资”，说明不支持并给出两个独立视图。
5. **失败恢复。** 展示已有局部实验的任务提交后响应丢失与稳定 task_id；完整 Agent 未实现恢复前，只展示实验记录，不让演示暗示全链路通过。

前四步是完整应用的待实现演示目标，最后一步已有部分局部实验。面试前把演示清单逐项改成实际状态；不要展示静态 JSON 却描述为模型实时执行。

## 4. 八周实施安排

| 周 | 项目产出 | 面试准备 |
| --- | --- | --- |
| 第 1 周 | 确认合成数据粒度、单轴分摊服务、指标定义与基准结果 | 整理真实 Java 经历与项目介绍，开始投递 |
| 第 2 周 | 一个模型接入、受控工具循环、一次查询和最小 Excel/查询数据闭环 | 能解释工具选择与确定性业务执行的区别 |
| 第 3 周 | 显式状态图、持久化受理、必要澄清、规则/数据版本绑定 | 练习架构和状态归属、跑通改维度案例 |
| 第 4 周 | 服务端数据范围校验、MCP 薄适配、两个版本化 Skill | 面试反馈驱动补强，补 Skill 更新与权限负例 |
| 第 5 周 | 统一 result、SVG/Excel 核对、导出幂等与故障注入 | 将最扎实的失败与修复变成讲述材料 |
| 第 6 周 | 固定案例评测、限定分摊数据集的 Text-to-SQL 探索通道 | 记录首轮/修复后结果、无谓追问和成本 |
| 第 7 周 | 集成回归、修复真实发现的问题，视时间覆盖多分摊轴 | 模拟追问、继续投递，不再新增平台功能 |
| 第 8 周 | 稳定可演示版本，归档证据与明确限制 | 集中推进面试和复盘 |

这是参考进度，不是假定每天全职学习。投递、Java 基础与项目实践并行，不能等第八周再开始求职。

### 时间不够时如何裁剪

**P0 必须讲透并跑通：** 一个分摊轴、有限指标、语义校验、身份与范围校验、查询结果核对、一次导出及故障实验。目标是完整垂直路径，前期甚至可以用确定性引导模板验证产品流程。

**P1 提升 Agent 区分度：** 根据观察选择下钻、改口径清理旧证据、持久化澄清恢复、MCP 适配、业务可维护 Skill。至少挑两个做出真实轨迹，不能只有表单转 JSON。

**P2 有时间再扩展：** 受限 Text-to-SQL、多轴场景、说明检索、更多图表。对外展示时关闭未通过评测的能力。多 Agent、通用低代码平台、多副本图执行、任意 SQL/任意图形不进入这次求职的必做范围。

LangGraph 学到状态、路由、工具循环、checkpoint、interrupt、重放与副作用即可；LangChain 学模型/消息/工具的基础组件，不必先通读整个框架。Java 继续重点准备事务隔离、SQL、线程与资源限制、接口幂等、权限和排查。框架选型的依据与边界见架构章，具体库版本以实践锁定版本为准。

## 5. 完成标准

- [ ] 新环境按照说明可以启动；模型、依赖和数据版本可追溯。
- [ ] 一次多项目分摊查询能完成必要确认、计算、引用和导出。
- [ ] 项目归属与分摊、单轴与联合轴、原金额与分摊金额有明确边界。
- [ ] 同一轴的逐事实守恒、分币、缺规则、不同规则比较政策已验证。
- [ ] 无权限、缺数据、零预算、错误参数有明确行为。
- [ ] 三个难点至少各有一个稳定复现与修复验证。
- [ ] 有固定测试集及没有用于调参的留出案例。
- [ ] 提交真实 trace、结果和限制，没有凭空填写提升比例。
- [ ] 能解释一次失败从模型到 SQL/任务层的定位路径。
- [ ] Skill 版本与工具依赖可追溯，业务编辑不会扩大运行权限。
- [ ] MCP 端点已认证，工具执行仍检查当前数据范围。
- [ ] 探索 SQL 无组织过滤、字段越权和连接复用负例已验证。
- [ ] SVG、Excel、原查询数据共享结果集，能逐项核对与说明完整性。

## 6. 简历描述模板

完成后按实际删改：

可以分成两段，避免把原系统与新实践混为一谈：

**原系统工作（仅按实际职责删改）：**“参与企业预算与核算系统开发，整合系统同步、人工导入及页面维护的数据，支持多项目、部门/团队/投资等维度的预算核算展示，开发指标卡片与报表，支撑业务汇报。”

**Agent 独立实践（对应能力完成后再使用）：**“基于 Spring Boot 与 LangGraph，构建多项目预算核算分析助手；通过结构化计划确定分摊口径，复用 Java 分摊与指标服务；以数据/规则版本绑定、受控工具调用和不可变结果，支持动态下钻及 SVG、Excel、核对数据交付；通过合成案例验证分摊守恒、语义查询和导出故障恢复。”

设计阶段只写“设计并验证局部关键机制”，不要使用“上线”“推广至全员”“效率提升 80%”等未经证明的描述。有模型和用户测试后，可填任务数、正确数、错误类型、测试环境与限制；百分比必须有分母。

如果只完成部分能力，删去未完成项。实验数据写清测试条件，不能把模拟数据量描述成公司真实业务规模。
