# 面试时怎么说，追问来了怎么接

下面按一次真实面试可能出现的顺序展开。引号内是口语参考，后面的解释帮助你接追问。表达应以自己实际完成的工作为准：当前有 Java 演示与验证记录，完整生产应用仍在设计中。

![从业务问题讲到代码和验证](images/interview-depth-ladder.svg)

## 01. 这个项目到底解决什么问题？

“员工要做预算汇报，数据虽然已经在系统里，仍要自己选口径、查几张表、整理图和 Excel。我把这个过程做成一个任务，缺关键信息时追问，确定后复用现有业务服务。”

继续问价值，就举 P01、P02 的例子。用户需要的不是一段介绍预算概念的文字，而是指定范围的 52 万预算、56 万实际，以及能够核对的差异和材料。尚未做用户效率实验，就不报提效百分比。

## 02. 为什么需要 Agent，普通接口不能做吗？

“固定查询继续走接口。需要 Agent 的地方，是用户说法不完整、要根据结果决定是否下钻，以及同一结果要怎样组织成汇报。”

例如“做张对比图”不一定需要明细，“解释超支”才可能需要下钻。计算和鉴权始终固定执行。若某个场景始终只有相同步骤，用普通流程就够了，复杂度应与任务匹配。

## 03. 为什么用 Java 和 LangGraph4j？

“现有核算能力在 Java 中，图节点能直接复用业务接口。LangGraph4j 提供状态、条件边和检查点，适合有追问、分支和恢复的长任务。”

技术选择要连到代价。团队需要理解 reducer、线程编号和恢复位置，也要验证持久层；框架没有自动提供财务正确性和分布式任务锁。当前示例固定在 1.8.27，不能混用其他版本文档里的 API。

## 04. LangGraph4j、LangChain4j 和 Spring AI 是什么关系？

“本方案里 LangGraph4j 管执行图。LangChain4j 或 Spring AI 可以作为模型接入与工具适配层，已有 Spring 服务继续处理业务。”

接入时只保留清楚的一处动作执行责任。模型适配器如果自动执行工具循环，就不能再让图把同一调用重复执行。当前源码通过 `NextStepPolicy` 隔离模型选择，测试用固定替身，真实模型适配仍待接入。

## 05. Spring Boot 请求怎么避免一直等模型？

“入口先在短事务里保存任务，返回 run_id。Java Worker 领取后运行图，前端查状态或订阅事件。”

事务不能包住模型等待和人工回复。生产环境还要决定任务领取、租约续期、并发额度与重启恢复。HTTP 返回受理成功，只表示任务已经收下，不表示报表已经生成。

## 06. State 里放什么？

“放继续执行必需的事实：任务、口径、计划版本、结果引用、待回答问题和操作编号。大结果和文件单独存。”

状态不是越全越好。整张结果表塞进每个检查点会增加写入成本和数据暴露。另一方面，只存聊天历史又很难判断当前计划到底是哪一版。字段需要能回答下一节点为什么可以继续。

## 07. 为什么不能给所有列表都用追加 reducer？

“历史证据可以按 ID 合并，当前计划的结果必须允许替换。否则用户改了预算口径，旧数据仍留在当前列表里。”

代码里档案按结果 ID 与哈希合并，同 ID 不同内容报错；`active_result_ids` 用覆盖策略。测试同时验证去重、冲突和清空。普通对象相等意义上的去重，不等于业务上的同一份证据。

## 08. 用户补一句话，怎么接回原任务？

“图缺口径时走等待分支，在 await_basis 前暂停。答复入口检查任务归属、等待节点和版本，更新状态后用原 threadId 恢复。”

实际调用是 `updateState` 配合 `GraphInput.resume()`。还要处理旧页面重复提交、两个答案并发到达和权限变化。演示验证了归属与等待版本；持久化命令去重、并发恢复锁和真实权限重新校验是应用层后续工作。

## 09. 有检查点就一定能安全重启吗？

“检查点保存了执行位置，但还要看保存器怎么写、谁能同时写，以及外部操作是否可重试。”

当前用 FileSystemSaver 验证三个独立 JVM 的干净重启，不声称文件写入中断电也安全。多实例需要原子持久化和并发控制；恢复后已提交的导出可能再次被调用，因此业务服务仍要去重。

## 10. 模型一直重复查同一份数据怎么办？

“运行层只接受允许的动作，还检查这一步是否已经做过。明细已查过却继续要求相同下钻，直接拒绝或进入受控结束。”

图的步骤上限只是最后一道限制。真正要排查的是状态有没有写回、工具结果是否配对、允许动作是否更新，以及模型是否缺少判断完成的信号。生产预算还要覆盖总时长和工具费用。

## 11. Skill 能不能代替业务代码？

“Skill 说明这类汇报应该确认什么、按什么顺序做。比例校验、权限、发布版本和去重仍由代码执行。”

业务人员可以维护术语、流程和样例，但发布要检查所引用的指标与工具合同。运行中任务固定兼容版本，严重口径错误或权限撤销另设暂停策略。不能让一段新文案直接改变已批准分摊政策。

## 12. MCP 是不是必须有？

“同一个 Java 应用里，我直接调用业务接口。需要连接外部工具，或让多个客户端复用服务能力时，再加 MCP 适配层。”

MCP 解决工具连接，不能自动给工具调用授权。服务地址与凭据来自受信配置，工具目录经过筛选。模型参数中的用户 ID、网页里的连接地址，都不能直接变成应用的身份或新工具来源。

## 13. 一次调用为什么有好几个 ID？

“tool_call_id 配对模型请求与返回，operation_id 表达持久业务意图，export_task_id 是数据库受理后的记录。”

网络重试可以产生新调用编号，但同一意图必须保留操作编号。新口径的重新导出才是新意图。同编号不同参数报冲突，避免把旧任务偷偷改成另一件事。

## 14. SQL 执行成功为什么还可能错？

“语法正确只说明数据库能理解。预算连上多条费用明细后会重复出现，70 万可以被加成 140 万，业务结论就反了。”

先把预算和实际聚合到同一粒度再连接，同时固定轴、币种、期间和发布版本。`SUM(DISTINCT 金额)` 会误删金额相同的合法记录。对应 H2 测试先复现错数，再断言正确金额。

## 15. Text-to-SQL 怎么评测？

“固定问题、有效计划、数据版本和人工结果，再分别检查计划、执行与结果。不能只比较 SQL 字符串。”

不同 SQL 可能得到同一正确结果，同一 SQL 也可能在新数据上暴露粒度错误。评测集要有零预算、未分摊、缺来源、越权、跨币种和重复记录等负例。当前未接真实模型，因此没有准确率提升可以报告。

## 16. 为什么必须固定数据发布版本？

“汇总查完后比例可能更新。如果明细和 Excel 又读最新版本，就会出现一段任务里两套数字。”

有效计划固定数据与规则清单，结果带版本和哈希。新规则发布为新 ID，不原地修改旧内容。用户主动换口径时创建新计划，旧结果保留追溯，但从当前集合移出。

## 17. 导出重试怎么保证不重复？

“先保存操作编号，再调用导出服务。数据库按主体和操作编号做唯一约束，相同参数返回原任务。”

实验在数据库提交后故意抛异常，图恢复重新提交，任务数仍为 1。不能每次重试生成新 UUID，也不能用进程内布尔值防重。这里保证一个逻辑任务，不宣称外部计算物理上只运行一次。

## 18. 旧 Worker 很晚才算完，会覆盖新结果吗？

“发布时同时比较运行状态和执行代次。租约转交后，旧 token 就失去发布资格。”

测试验证旧 token 更新零行。生产环境还要保证 token 的单调分配、领取和续期流程，文件写入用每次尝试独立的路径，最终只发布被采纳的指针。不能仅在代码注释里写‘只允许一个 Worker’。

## 19. 图表和 Excel 怎样用同一批数？

“查完先冻结结果，模型给展示要求，Java 从结果行生成数组和表格。换颜色不重新查数，换口径才生成新结果。”

交付清单记录结果 ID、单位、规则版本、文件哈希与核对结果。Top N 图要标清省略范围，Excel 明细与汇总需要对账。当前演示只创建导出任务，文件生成还属于设计范围。

## 20. 三个分摊维度怎么避免把费用算三次？

“部门、团队、投资是独立视角，每个视角都可能展示完整总额。一轮计算先选一个轴，不能跨轴加总。”

部门占 60%、投资方占 50%，并不能推出交叉部分是 30%。不同联合分布能满足同样边际比例，只有批准的联合规则才能给出交叉金额。权限允许查看两个轴，也不能补出不存在的业务事实。

## 21. 预算和实际比例不同，能比较吗？

“要看批准的比较政策。预算按 60%、实际按 50% 未必错误，但必须说明使用发生时规则，还是统一口径重述。”

计划分别引用预算与实际规则，不拿一套比例覆盖另一套。规则有生效期间和指标类别，旧费用冲销优先反向引用原分摊。BigDecimal 解决表示精度，尾差给谁仍需要稳定且经过确认的政策。

## 22. 只输出分摊金额，权限就安全了吗？

“还要看能否结合比例或其他查询推回全额。用户看到 46.2 万，再看到精确 60%，就能算出项目全额 77 万。”

所以要一起控制主体、项目、轴、目标、期间、字段和导出动作。缓存、下载、图表、明细接口都走同一范围。真实数据库隔离、连接池身份切换与推断攻击仍需单独测试，现有合成实验不能代替。

## 23. Skill 更新后，怎样既教对新功能又不破坏旧任务？

“发布兼容清单，固定运行中任务的版本，新任务读新版本。同时跑旧任务回归，不只检查新增功能。”

如果更新后还是教旧操作，先看任务版本和实际召回片段，再查缓存与发布指针。权限撤销不等同于普通文档更新，要重新校验并按政策中止。能追到具体版本，才能解释为什么某个任务仍在走旧流程。

## 24. 最值得讲的三个亮点是什么？

“我会讲三件事：金额怎么查对、长任务怎么恢复、导出重试怎么收敛。每件都拿一个具体反例和测试结果。”

金额用 70 万变 140 万，恢复用缺口径后的三个 JVM，导出去重用提交后响应丢失。当前有 32 项 Java 检查支持这些机制；真实模型、生产权限和完整文件交付留在后续计划里。回答有边界，追问时才能继续拿出证据。

## 25. 你的 Java 优势具体体现在哪里？

“我会结合自己做过的后端工作，讲并发与资源管理、事务边界、排障和迁移适配。最近也补了可复现的小实验，用代码验证以前容易凭经验判断的行为。”

选两项与你真实职责吻合的内容，说明当时的条件、你做的修改和验证结果。独立实验可以拿来支持机制，不能替代生产经历。[第 11 篇](11-Java%20面试专题：并发、排障与工程取舍.md)提供了七个已运行场景。

## 26. 线程池最大线程数很大，为什么仍然排队？

“先看核心线程数和队列。达到核心线程数后会优先入队；使用无界队列时，调大最大线程数可能没有效果。”

再拆开排队、执行和等待连接的时间。下游连接池已满时，增加工作线程只会多一批等待者。本地实验稳定复现核心为 1、最大为 3、两个任务排队却只有一个工作线程的情况。

## 27. CompletableFuture 设置超时以后，还会继续写数据吗？

“可能。调用方停止等待和后台停止执行是两件分别需要实现的事。我的实验里 Future 已异常完成，后台后来仍完成了一次动作。”

继续解释总截止时间、客户端取消、连接释放、业务操作编号和晚到结果的状态检查。实验的动作是内存计数，没有验证 JDBC 取消；真实驱动必须单独测试。

## 28. 既然用 JDK 21，为什么不把所有线程换成虚拟线程？

“先看负载。等待型任务可能受益，计算和数据库吞吐仍然有上限。我会保留下游准入限制，单独验证一个接口的效果。”

JDK 21 还要观察具体阻塞栈中的 pinning。已有实验只验证虚拟线程配合信号量限制下游并发，没有吞吐提升数字。

## 29. JDK 8 升级 21，方案最需要控制什么？

“我会盘点构建、依赖和运行环境，尽量分开验证变化，再检查业务行为与新旧实例共存。能启动之后，还要过业务样本、性能基线和回退演练。”

用真实参与内容展开；如果讨论补充方案，明确它是复盘后的设计。`add-opens` 的过渡条件、文件编码、旧制品与共享数据合同都可以接着追问，见 [第 12 篇](12-JDK8%20升级%20JDK21：兼容评估、灰度与回退方案.md)。

## 30. Oracle 迁 PG，怎样证明数据迁对了？

“在同一个快照或切换水位下，先查主键和行数，再按项目、期间、币种核对业务金额，最后定位明细差异。只看总额会漏掉相互抵消的错误。”

本地 PG 实验中，P01 少 100、P02 多 100，总额仍为 126 万，但两个项目都错了。真实迁移还要走 JDBC 和业务接口，验证类型映射、日期、权限与报表行为。

## 31. 为什么捕获重复键异常后，查询已有记录还报错？

“PG 的同一个显式事务发生错误后会进入失败状态。catch 只控制 Java 流程，没有把数据库事务恢复。”

本地验证得到 23505 后，下一条查询是 25P02。可以根据合同使用 ON CONFLICT、savepoint，或结束失败事务后重新查询；Spring 的实际事务边界仍需集成测试，不能照搬 H2 行为。

## 32. 数据库切过去之后，为什么不能随时切回来？

“PG 一旦接受了新写入，Oracle 就可能落后。直接切回会漏掉这段新增、修改和删除。回退前需要补齐差异，或者选择在目标库向前修复。”

旧备份不包含这些新写入，双写也需要处理部分失败和顺序。方案应在开放目标写入前确定路径，并演练停写、追赶和对账。完整设计与实验边界见 [第 13 篇](13-Oracle%20迁移%20PostgreSQL：语义核对、切换与回退方案.md)。
