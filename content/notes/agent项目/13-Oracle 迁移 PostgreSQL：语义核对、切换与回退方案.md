# Oracle 迁移 PostgreSQL：语义核对、切换与回退方案

数据库迁移值得讲的地方，是数据和业务行为能否被解释清楚。把表建出来、数据导进去之后，还要确认金额没有被重新舍入，时间没有错位，重复请求仍然按原政策处理，查询计划也能承受实际负载。

你已经有 Oracle 迁移 PostgreSQL 的经历。本篇将它整理成方案设计专题，但不预设你主导了全部迁移。源库与目标库版本、数据规模、停机窗口、使用工具和个人职责仍待你从实际项目补齐。

文中 Oracle 语义参考 19c 官方文档；本次教学 SQL 在独立临时 PostgreSQL 18.6 实例上验证。这个版本不是对你生产数据库的假定。没有连接 Oracle、运行 CDC 或迁移业务数据，七个实验只验证 PostgreSQL 行为与合成对账案例。

## 1. 先定迁移范围和切换约束

| 需要确认 | 会影响什么决策 |
| --- | --- |
| Oracle/PG 完整版本、字符集、时区、扩展与部署方式 | 类型兼容、驱动选择、SQL 与工具支持 |
| 表大小、增长量、变更速率、大事务和 LOB 占比 | 全量时间、日志保留、增量追赶速度 |
| 停写窗口、可接受的数据损失与恢复时长 | 停机迁移或全量加 CDC、回退策略 |
| 写入入口 | Web、定时任务、消息消费者、脚本、外部直连都要纳入停写 |
| 库内逻辑 | 视图、包、存储过程、触发器、函数、序列、调度任务 |
| 下游依赖 | 报表、ETL、数据订阅、审计、备份、权限和运维脚本 |
| 业务不变量 | 哪些金额、主键关系、状态约束必须成立 |

RPO 表达可接受的数据损失范围，RTO 表达恢复服务需要多长时间。它们必须由业务和运维共同确认，不能因为材料好看就写“零停机、零丢失”。

方案范围也要清楚：只迁移业务库，还是同时重写存储过程、替换 ORM、升级 JDK。能分开的变更尽量分开验证。本篇默认先保持业务规则稳定，处理数据库变化；不是一次顺便重构全部系统的计划。

## 2. 建一份字段映射表，保留每个决定的理由

映射表至少有源类型、目标类型、业务含义、历史值范围、空值规则、转换表达式、异常处理和验收样本。工具生成的 DDL 可以作为起点，不能直接替代这些判断。

| 字段问题 | 容易做错的映射 | 应怎样决定 |
| --- | --- | --- |
| NUMBER | 全部转为 double 或统一 numeric(18,2) | 按金额、比例、计数分类，检查范围和实际小数位 |
| Oracle DATE | 直接映射成 PG date | Oracle DATE 含时分秒，先确认是自然日还是本地时间 |
| 带时区的时间 | 只保留格式化字符串，或统一去掉时区 | 区分时间点、业务本地时间、原始时区标识 |
| VARCHAR2 | 忽略 BYTE/CHAR 与实际字符长度 | 检查中文、补充字符、历史超长值与接口限制 |
| 空字符串 | 默认与 NULL 在两边相同 | 确认输入标准化、查询条件和唯一约束含义 |
| 序列与 identity | 导入 ID 后认为下个 ID 自动正确 | 核对下一值、步长、缓存、分配规则和切换写入者 |
| BLOB/CLOB | 只核对行数 | 核对长度、完整内容、编码与客户端流式读取 |

Oracle DATE 保存到秒，PostgreSQL date 只表示日期；PostgreSQL 的 `timestamp without time zone` 与 `timestamptz` 又表达不同含义。timestamptz 保存时间点，显示受会话时区影响，不保留输入时原有的时区名称。需要原时区时应另存字段。[Oracle 19c 数据类型](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Data-Types.html)、[PostgreSQL 日期时间类型](https://www.postgresql.org/docs/18/datatype-datetime.html)

### 金额和比例要先查历史值

假设一列现在叫 `amount`，不能据此认定历史数据最多两位小数。它可能保存税额中间值、汇率换算结果或尚未完成分摊的金额。先统计小数位、最大绝对值、负数、极端值，再确认目标列的精度。

PostgreSQL 写入有固定 scale 的 numeric 时会按该 scale 舍入；舍入后超出 precision 允许范围会报错。教学实验中，`123.456::numeric(10,2)` 得到 `123.46`，`999.995::numeric(5,2)` 则因舍入后超出范围失败。[PostgreSQL 数值类型](https://www.postgresql.org/docs/18/datatype-numeric.html)

这个差异应在迁移前转成规则：哪些字段必须原值保存，哪些允许按已批准的政策舍入，无法转换的行进入怎样的异常清单。不能自动截断以后只对比两位小数，说两边一致。

Java 端还要检查 JDBC 取值和 JSON 序列化。数据库保留精度，但驱动取成 double 再转 BigDecimal，应用仍可能丢精度。验收应走一次真实 JDBC 与业务计算链路；本次 SQL 实验没有覆盖它。

### 空字符串与 NULL 会改变新数据的行为

Oracle 19c 将长度为零的字符值按 NULL 处理；PostgreSQL 区分空字符串与 NULL。[Oracle 空值说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html)

源库里已经变成 NULL 的历史值，不应凭空还原成空字符串。更容易漏掉的是切换后的新写入：同一个 Java 表单提交 `""`，目标库可能存下一个非空的空字符串，原先 `IS NULL` 的查询就漏了它。

如果业务决定“空文本就是未填写”，可以在入口或转换层明确标准化，例如 `NULLIF(value, '')`。不要擅自把所有空格 trim 掉；编码、备注或外部编号中的空格可能有含义。再验证筛选、统计、唯一约束和接口返回是否符合新合同。

## 3. SQL 改造要验结果，不能只改到可执行

| 范围 | 需要检查的具体问题 |
| --- | --- |
| NVL、日期函数、字符串拼接 | NULL 行为、类型转换、求值与时间含义是否相同 |
| ROWNUM、分页与排序 | 先排序还是先截取，有没有稳定的最终排序键 |
| 大小写与标识符 | Oracle 未引用标识符通常折叠为大写，PG 折叠为小写，ORM 映射是否匹配 |
| MERGE 与 upsert | 并发冲突、重复源行、唯一约束和更新条件 |
| PL/SQL、包与触发器 | 哪些逻辑移到应用，哪些重写，事务边界是否改变 |
| 临时表与会话状态 | 连接池复用时是否残留，提交后数据如何处理 |
| 查询计划 | 索引、统计信息、数据倾斜、排序、连接次序与内存 |

例如将 ROWNUM 改成 LIMIT 时，要先写出“到底取按什么顺序的哪几行”。如果只按非唯一时间排序，同一时刻多条记录的顺序可能变化。分页补上稳定键，并针对并发新增与翻页定义一致性要求。

数据迁完后应更新统计信息，使用有代表性的参数检查计划。迁移前记录的慢 SQL 排名可作为入口，但还要覆盖数据倾斜：小部门、最大部门、空范围、长时间范围与批处理。Oracle 上有效的索引组合，在 PG 上仍需要重新验证，不能只比索引名称或数量。

## 4. 唯一键冲突后，为什么 catch 了还查不了

一个常见去重流程是“插入任务，捕获重复键异常，再查询已有任务”。如果在 PostgreSQL 同一显式事务中直接这样做，第二条查询可能收到 `25P02`，因为前一条错误已经使当前事务进入失败状态。

本次实验先故意制造 `23505` 唯一键冲突，随后执行 SELECT，得到 `25P02`；ROLLBACK 后才能继续。这比 H2 测试通过更能说明目标数据库的真实行为。[PostgreSQL 事务教程](https://www.postgresql.org/docs/17/tutorial-transactions.html)

可以按业务选择以下方式，但要把 Spring 与驱动行为一起验证：

| 方案 | 合适的前提 | 需要注意 |
| --- | --- | --- |
| INSERT ... ON CONFLICT | 冲突是预期业务分支 | 参数不能被静默覆盖；随后要检查原记录 |
| 提前建立 savepoint，冲突后回滚到它 | 需要保留同事务前面的工作 | 驱动、事务框架是否支持这条路径 |
| 结束失败事务，再开启新事务查询 | 可以把冲突处理放在事务外层 | 方法内部 catch 并不等于已结束事务 |

任务受理可以采用下面的合同：操作主键是 `(actor_id, operation_id)`，同时保存规范化参数的哈希。重复键且哈希相同，返回原任务；哈希不同，明确报冲突。

```sql
INSERT INTO operation_task(actor_id, operation_id, parameter_hash, state)
VALUES (:actor_id, :operation_id, :parameter_hash, 'ACCEPTED')
ON CONFLICT (actor_id, operation_id) DO NOTHING
RETURNING task_id, parameter_hash;
```

这是一段设计 SQL，表结构需由实际项目定义。插入没有返回行时，再按主键读取已有任务并比较参数。这里以 READ COMMITTED、记录在重试保留期内不被删除为前提；其他隔离级别、并发删除与序列化失败应另设重试政策。

不要把 `ON CONFLICT DO UPDATE` 当作默认方案。如果重复请求携带了不同参数，覆盖旧记录会把一个原本清楚的业务冲突变成静默修改。[PostgreSQL INSERT 文档](https://www.postgresql.org/docs/17/sql-insert.html)说明了冲突处理语义；本次实验只测单会话行为，未验证并发 JDBC 受理。

## 5. 一张报表查多次，怎样保证看到同一批数

PostgreSQL READ COMMITTED 下，每条语句获得自己的快照；同一事务中的两次查询可以看到中间新提交的数据。仅仅加上事务注解，并不保证多次查询对着同一个历史状态。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)

短时间一致读取可以评估 REPEATABLE READ。长报表若一直占着事务，可能带来连接占用及旧版本清理压力；也可以固定数据发布版本或物化结果，后续图表、导出读取同一结果集。应由报表时长、更新频率和一致性要求决定。

两种数据库都有多版本并发相关机制，迁移时要核对实际使用的隔离级别、语句行为与应用假设。会改变哪些业务结果，才是需要准备的回答。[Oracle 数据并发与一致性说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/data-concurrency-and-consistency.html)

## 6. 选择停机全量，还是全量加增量

| 方案 | 适用条件 | 成本与验证重点 |
| --- | --- | --- |
| 停写后全量迁移 | 数据量、传输与校验可放进允许窗口 | 流程较简单，但必须通过演练测出总时长 |
| 一致性全量快照 + CDC | 允许长时间准备，仅能短暂停写 | 多了日志保留、位点衔接、顺序、重复与追赶验证 |

停机全量也包括停写、导出、转换、加载、索引与约束、统计信息、对账、冒烟和恢复流量。导入只花两小时，不代表停机两小时就能完成全部工作。

CDC 方案应由实际版本和对象类型决定工具。选择清单至少包括：源库版本与日志条件、权限、快照支持、LOB、DDL、长事务、删除、断点恢复、监控、团队运维能力和授权成本。比如 Debezium Oracle 连接器有具体的 Oracle 配置、快照和 SCN 跟踪要求；应核对选定版本，而不是笼统写“接 CDC 即可”。[Debezium Oracle 连接器文档](https://debezium.io/documentation/reference/stable/connectors/oracle.html)

PostgreSQL 自带逻辑复制面向其发布与订阅机制，不能直接承担 Oracle 源端捕获；pg_dump 用于 PostgreSQL 数据库备份。工具名应对应实际方向和能力。[逻辑复制文档](https://www.postgresql.org/docs/18/logical-replication.html)、[pg_dump 手册](https://www.postgresql.org/docs/18/app-pgdump.html)

### 全量与增量衔接，最怕中间少一段

选定工具必须能够定义一致性快照与增量起点之间的关系，包括快照期间仍在进行的事务。不能先随手查一个 SCN，再逐张普通 SELECT 导出，声称这些表来自同一个时点。

源日志保留时间要覆盖全量扫描、故障恢复和增量追赶。目标应用按事务和实体顺序处理变化，避免较旧事件覆盖较新值；如果消息系统重新分区，需确认同一主键的顺序没有被打乱。重放重复事件应可识别，delete 不能只在全量阶段体现。

增量链路需要记录来源位点、捕获位点、目标已应用位点和失败记录。队列为空只表示没有待处理消息，不能单独证明源库最后一笔提交已经进入目标库。源到捕获端是否落后，也要一起判断。

演练至少覆盖：全量中断续跑、增量中断重放、重复事件、删除、长事务、日志保留不足、DDL 变化和目标端暂时不可写。任何一项未经验证，都应标在方案里。

## 7. 对账按同一个位点，逐层定位差异

源端继续写、目标端还在追赶时，直接比较两个库的实时总数，会混入时间差。先约定同一快照或切换水位；无法读取同一逻辑时点时，比较结果必须说明延迟范围，不能把差异都归为迁移错误或都归为延迟。

建议由便宜的检查逐步进入明细：

1. 对象与约束：该迁的表、列、索引、唯一约束、外键是否完整，状态是否有效。
2. 主键集合：总行数、主键缺失、多出、重复、孤儿记录。
3. 分组业务数：按项目、期间、币种、状态、规则版本核对金额和数量。
4. 字段与明细：在差异分组中比较每行，输出源值、目标值和转换规则。
5. 应用结果：通过实际接口比较分页、统计、权限和报表，而不只查数据库表。

### 总数与总金额完全相同，仍可能两笔都错

本次合成实验使用以下两组数据：

| 项目 | 源样本 | 目标样本 | 目标减源 |
| --- | ---: | ---: | ---: |
| P01 | 770000 | 769900 | -100 |
| P02 | 490000 | 490100 | +100 |
| 合计 | 1260000 | 1260000 | 0 |

行数都是 2，总金额都是 126 万，但两个项目都错了。SQL 实验用 FULL JOIN 和 `IS DISTINCT FROM` 找出了两条差异。这是为什么对账要检查业务分组和主键，不能只拿总金额相等作为迁移通过条件。

在实际预算系统中，还应验证同一分摊轴内的守恒、规则生效期间、调整前后预算、冲销和未分摊金额。各币种不能直接相加，多个独立分摊轴也不能跨轴加总。若接到现有项目，可以使用 [第 04 篇的核算规则](04-一笔费用怎样分摊，Java%20又该守住什么.md)作为对账条件。

### 哈希可以缩小范围，但先定义规范化

跨库逐行哈希前，明确字段顺序、类型、编码、NULL 标记、长度边界、小数表示和时间标准。同一个 numeric 值可能显示为 `1.0` 或 `1.00`；同一个时间点可以显示不同偏移。原始文本不同，不一定代表业务不同。

反过来，不能为省事把 NULL 和空字符串合并、把金额先转 double、把时间只保留日期。这样会让真实差异消失。较稳妥的方式是按字段合同规范化，再用带类型和长度边界的序列编码计算哈希。发生差异后，仍要能回到原始字段值解释原因。

金额这类确定性数据应按已批准的精度严格核对。只有业务本来就允许近似的字段，才设计容差及其理由。不要统一设一个金额误差阈值，掩盖分摊或舍入错误。

## 8. 切换步骤与放行条件

下面是一份方案模板。负责人、时间窗口、命令、位点和阈值要在演练后填入，不能直接当成生产操作单执行。

| 阶段 | 要完成的工作 | 放行证据 |
| --- | --- | --- |
| 准备 | 完成依赖适配、全量加载、增量追赶、备份恢复演练 | 版本清单、恢复记录、未关闭问题清单 |
| 停写 | 停止全部写入口，排空或处理在途事务与后台任务 | 写入入口清单逐项确认，活动事务与写入监控 |
| 确定水位 W | 标识最后一批应迁移的已提交事务 | 源端事务状态与工具可解释的位点记录 |
| 追赶到 W | 捕获与目标应用均覆盖 W，检查失败与遗漏 | 全事务应用完成，差异和错误队列已处理 |
| 核对与准备 | 同水位对账，检查序列、权限、统计信息与配置 | 必需业务不变量通过，阻断差异为零 |
| 切流量 | 更新连接配置，重建连接池，启用目标写入者 | 每个实例实际连接目标库，源端仍受写入限制 |
| 观察 | 核对新写入、任务、延迟、数据库负载与告警 | 代表性业务通过，能够识别并处理异常 |

停写不能只把页面按钮置灰。消息消费者、定时核算、重试任务、人工脚本、外部直连和旧实例都可能继续写。需要应用与数据库访问控制配合，并确认连接池里的旧连接不会绕过切换。切流量后，旧库也不能无人看管地恢复写入。

新库启用写入前要做业务冒烟。任何测试写入都应纳入记录，明确是否产生了需要回迁的数据或外部副作用；即使事务回滚，序列取值也不一定回退。不能以“只是测试请求”为由忽略它。

### 序列对齐不能只抄一个 MAX(id)

显式导入 identity 字段的值，不意味着对应序列自动移动。本次实验导入 ID=1，下一次默认插入仍尝试 ID=1 并冲突；在这个独立、非空、正向递增且没有其他写入者的样本中，对齐后下一值为 2。[PostgreSQL 序列函数](https://www.postgresql.org/docs/18/functions-sequence.html)

```sql
-- 教学条件：非空表、正向步长为 1、所有写入者已停止。
SELECT setval(
  pg_get_serial_sequence('sequence_sample', 'id'),
  (SELECT max(id) FROM sequence_sample),
  true
);
```

真实切换还要检查序列是否被多表共用、源端是否预留 ID 区间、外部是否已经拿到尚未落库的编号、目标端是否已分配过更高值，以及步长、起始值、上限和缓存策略。不能把序列回拨到更低位置。空表也要按配置的起始值与 `is_called` 处理，不能把 NULL 传给这段模板了事。

序列允许产生空洞，不应用它保证账务编号连续性。若业务要求连续单据号，那是另外一个业务分配与审计机制，需要单独迁移和验证。

## 9. 回退的分界点是目标库是否已接受新写入

### 目标库还没有新增业务写入

源库继续是完整事实来源。若目标校验失败，可以保持源库数据，撤销切换准备，恢复原入口和后台任务。但仍要核对在途请求、配置、连接池与任务领取状态，不能只把域名指回去。

### 目标库已经产生新增、修改或删除

此时源库可能落后。直接切回源库会丢掉目标端的新业务变化。之前保留了 Oracle 备份，也不能恢复迁移完成以后只写到 PG 的数据。

方案需要在开放目标写入前选定可行路径：

| 回退路径 | 适用前提 | 额外工作 |
| --- | --- | --- |
| 经过验证的反向同步 | PG 新数据可无损表达回 Oracle，顺序与冲突政策明确 | 反向链路、去重、防循环、追赶与对账 |
| 再次停写，提取差异后回迁 | 能接受再次停机，变化范围可完整识别 | INSERT/UPDATE/DELETE、事务关系、外部副作用核对 |
| 保持目标库，向前修复 | 回迁成本更高或目标写入已不兼容源端 | 限流、功能降级、修复、数据校正与恢复验证 |

无论选哪条，必须有变更记录与明确的事实来源。双写也不是自然成立的替代方案：一边成功、一边失败、两边顺序不同、网络分区之后，仍需要决定谁为准、如何重放和怎样处理冲突。没有演练过的反向同步，不应写成随时可用的回退保障。

面试可以直接解释：“我会把目标库开放写入作为回退方案的分界。之前主要是恢复旧入口；之后必须先补齐目标端产生的新数据，或选择向前修复。恢复旧备份无法覆盖这些新写入。”

## 10. 迁完之后，哪些问题还会逐渐出现

观察期应覆盖正常业务周期，包括定时报表、批量写入、月末计算和备份，不只看切换后最初几分钟。

| 观察对象 | 应关注的变化 |
| --- | --- |
| Java 连接池 | 借连接等待、未释放连接、旧库连接残留 |
| 数据库活动 | 长事务、idle in transaction、阻塞链、慢 SQL |
| 数据维护 | 统计信息、autovacuum、死元组、索引与磁盘增长 |
| 业务一致性 | 同期间对账、冲销、重复受理、漏处理任务 |
| 运维能力 | 备份可恢复、故障切换、告警可定位到业务接口 |

长事务可能让旧行版本无法及时清理，单次查询快并不能说明长期运行健康。大量更新的表要结合实际负载观察维护行为，不能原样照搬 Oracle 的维护脚本。[PostgreSQL 日常清理与维护](https://www.postgresql.org/docs/18/routine-vacuuming.html)

SQL 性能报告至少保存查询、参数分布、数据版本、结果核对、执行计划和资源使用。优化后若金额变了，先处理正确性；若延迟降低但数据库 CPU 明显升高，也应说明代价。

## 11. 本次实际验证了什么

文件位于 [SQL 场景](code/pg-migration-lab/checks.sql)、[运行脚本](code/pg-migration-lab/run-lab.py)、[运行说明](code/pg-migration-lab/README.txt)和[完整日志](code/pg-migration-lab/verification.txt)。在装有 PostgreSQL 服务端工具的机器上运行：

```sh
python3 run-lab.py
```

脚本新建临时集群，只监听独立 Unix socket。结束后停止并删除该临时集群，不连接已有业务库。所有样本均为合成数据。

2026-09-10 在 PostgreSQL 18.6 上通过以下七个场景：

| 场景 | 实际验证结果 |
| --- | --- |
| 空字符串与 NULL | 两者可区分，NULLIF 可以按指定规则归一化 |
| numeric 转换 | scale 舍入成功，舍入后溢出被识别 |
| 日期与时间点 | date 不保存时间，两个偏移表示可对应同一时间点 |
| identity 序列 | 显式导入后发生冲突，样本对齐后默认插入为 2 |
| 操作冲突 | DO NOTHING 保留旧参数，不会自动接受新参数 |
| 项目对账 | 相同行数、相同总额下，检出两个项目差异 |
| 失败事务 | 先得到 23505，再得到 25P02，回滚后可查询 |

最后一个场景会故意打印两条 ERROR，脚本随后断言 SQLSTATE 必须分别为 23505 和 25P02；若不符合，执行失败。这些错误是被验证的现象，不是被忽略的失败。

尚未验证的范围包括 Oracle 实际导出与类型映射、CDC 衔接、并发 upsert、JDBC/Spring 事务、目标生产版本、真实数据量、停机时长和回退演练。不能用这七个小实验推出“已完成数据库迁移”。

## 12. 怎样用这段经历回答面试

先确定自己实际承担的部分，再选一个方向展开。

| 真实职责 | 可以重点讲的内容 |
| --- | --- |
| 应用适配 | SQL 改造、驱动、类型、事务和接口回归 |
| 数据核对 | 主键与分组对账、差异定位、业务不变量 |
| 迁移实施 | 工具配置、快照位点、追赶、切换步骤 |
| 方案或上线支持 | 依赖盘点、放行条件、回退边界与排障 |

一段不夸大范围的开场可以是：“我参与过 Oracle 到 PostgreSQL 的迁移，我实际负责的是……。我会先讲这一部分，再说明整套方案里数据如何核对、切换时怎样停写，以及目标库开始写入后为什么不能直接回到旧库。”

接下来准备这些追问：

| 追问 | 需要讲清的内容 |
| --- | --- |
| 最难改的一条 SQL 是什么？ | 真实 SQL 的语义、输入与正确结果；未提供时不虚构 |
| 总金额一致，为什么还不放心？ | 分项目抵消、主键缺失、币种与期间，拿合成实验解释 |
| 重复键 catch 后为什么还失败？ | 失败事务状态、事务边界、ON CONFLICT 或 savepoint |
| CDC 追上了怎么判断？ | 一致性快照、捕获和应用位点、最后已提交事务 |
| 迁移后能一键回滚吗？ | 目标写入前后不同，新增数据回迁与外部副作用 |
| 迁移效果怎样证明？ | 真实对账记录、接口正确性、计划与同负载指标 |

建议先花 8～10 小时整理真实职责、运行这组实验、完成一份迁移方案和五分钟讲述。真正重建 Oracle、CDC 与切换环境需要单独估时。求职准备中先把已有迁移经历说明白，新增实验用于补足原来没有验证过的机制。
