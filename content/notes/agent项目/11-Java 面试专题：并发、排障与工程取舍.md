# Java 面试专题：并发、排障与工程取舍

这一篇单独准备 Java 面试。订单、报表、批处理、后台管理系统都能用到，不需要把每个知识点放进 Agent 项目。

你已经有 Java 后端工作经历。准备时应当把过去做过的事情讲深：请求慢在哪里，哪个资源先耗尽，为什么选这个事务边界，修改后怎样证明没有引入另一种错误。能画出故障发生的顺序，通常比背出更多类名更有说服力。

文中的业务故障是练习场景，不是你的生产事故。已实际运行的内容只有文末列出的七个 Java 21 语义实验；Spring、Redis、JDBC 排障与压测属于待你在对应环境验证的部分。

## 1. 先决定哪些内容值得花时间

| 准备优先级 | 应该掌握到什么程度 | 最后留下的材料 |
| --- | --- | --- |
| 先练：线程池、异步超时、事务 | 能复现异常，解释任务和事务实际在哪个线程执行 | 一份代码、失败日志、修复后的结果 |
| 先练：JVM 与慢 SQL 排查 | 能根据证据缩小范围，知道下一条命令要回答什么 | 一张排查记录和前后对照 |
| 重点展开：JDK 与数据库迁移 | 能说清兼容范围、切换条件及回退限制 | 专题 12、13 的方案与验证清单 |
| 按经历选择：缓存、后台任务 | 能解释并发时序、数据一致性和失败恢复 | 一个具体场景的时序与测试 |
| 随问题补：集合、锁、类加载原理 | 能把原理连回上述场景 | 面试追问笔记 |

先从自己实际负责过的系统中选两个问题。不必给自己增加一套与现有经历无关的“大促千万并发”故事。规模可以普通，判断过程必须经得起追问。

## 2. 线程池为什么没用满，接口却已经排队

假设一个报表接口把任务交给线程池，配置 `corePoolSize=8`、`maximumPoolSize=32`，队列是未指定容量的 `LinkedBlockingQueue`。监控里活跃线程长期为 8，队列持续增加，接口超时。这个时候把最大线程数改为 64，可能没有作用。

`ThreadPoolExecutor` 在达到核心线程数后先尝试入队，队列放不下才尝试扩容到最大线程数；再无法接纳时执行拒绝策略。无界队列通常让扩容分支失去机会。[JDK 21 ThreadPoolExecutor 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

### 先把“慢”拆开

一次请求至少记录提交、开始执行、拿到连接、SQL 完成、返回这几个时间点。线程池队列等了两秒、SQL 只用了五十毫秒，和 SQL 本身用了两秒，需要不同的修改。

| 观察结果 | 接着查什么 | 当前不宜直接做什么 |
| --- | --- | --- |
| 队列增长，工作线程都在等数据库连接 | 池中已借出连接、持有时长、长事务、连接泄漏 | 继续增加应用线程 |
| 队列增长，线程在跑计算，CPU 接近配额 | 热方法、分配速率、算法、批量大小 | 无上限增加计算并发 |
| 队列增长，线程在等外部 HTTP | 对端延迟、连接池、读超时、重试次数 | 让每层都独立重试 |
| 应用 CPU 不高，线程卡在 Future.get | 父任务是否等待同池子任务 | 仅凭 CPU 低判断容量充足 |

线程池容量应受下游约束。教学例子中，数据库池只有 20 个连接，报表最多借用其中 6 个，其他请求需要保留容量，那么报表的并发准入上限就应考虑这 6 个名额。多实例时还要算所有实例的总连接数，以及数据库能承受的活跃查询数。这些数字是演算条件，不是推荐配置。

稳态下，可以用平均在途量约等于到达率乘平均耗时做容量估算。但尾延迟、突发请求和多次数据库访问仍需压测。不要把公式算出的值直接写进配置。

### 队列满了以后，接口应该怎么表现

普通查询可以在准入失败时明确返回繁忙及可重试信息；已持久化的后台任务可以保留在任务表，等待调度。拒绝不能让业务记录显示“已受理”，实际却没有任何地方能找回任务。

`CallerRunsPolicy` 会把工作交给提交线程，在 HTTP 入口可能直接拖慢请求线程；静默丢弃策略可能让调用方一直等不到完成信号。选择拒绝策略时，先画出提交线程是谁、调用者如何得知失败，再决定是否合适。

本篇实验把第一个任务停在门闩上，稳定观察到“核心 1、最大 3、排队 2、实际工作线程 1”。有界队列版本则观察到“两个工作线程占满、一个任务排队、第四个任务被拒绝”。它验证的是接纳顺序，不是生产容量。

## 3. CompletableFuture 超时后，事情到底停没停

设想调用方等待一份报告，100 毫秒后超时返回。后台仍在查询，随后写入文件。用户重试又创建了一份任务，于是出现重复文件。日志里第一条请求标记失败，容易让人误以为它没有产生结果。

`orTimeout` 让 CompletableFuture 异常完成，并不自动停止底层工作；`CompletableFuture.cancel(true)` 也不以中断底层执行作为取消机制。它和某些 Executor 返回的 Future 对中断的处理不能混为一谈。[JDK 21 CompletableFuture 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html)

### 一次超时需要分别回答四个问题

1. 调用者是否停止等待？这是接口层的结果。
2. 后台计算有没有收到停止信号？业务代码是否检查它？
3. JDBC 或 HTTP 请求是否已取消，连接什么时候释放？需要具体驱动与客户端支持。
4. 结果已经提交时，重试怎样查到原结果？此时再发中断不能撤销已提交操作。

可以把总截止时间沿调用链传递，下游只使用剩余预算。重试也要消耗同一个总预算，不能每次从头获得完整超时时间。等待连接、执行查询和读取响应应分别有界；任务取消后还要记录仍在执行的工作，防止前台超时量下降而后台资源一直被占用。

对于有副作用的任务，需要稳定的业务操作编号，以及发布结果时的状态检查。HTTP 超时不必等于后台任务取消：若产品允许转为后台完成，就返回任务 ID，并清楚显示当前状态。若用户明确取消，则通过原子条件更新阻止晚到结果进入“成功”状态。文件已经写出时，可以保留未发布文件并做清理，不能仅修改 Future 的状态。

本篇实验先确认后台已经启动，再触发超时。调用方得到异常后，释放门闩，后台仍产生一次副作用。日志中的副作用是内存计数，没有连接真实数据库。

### 同一个池里的父子任务为何会饿死

一个只有一个线程的池正在执行父任务。父任务又往同一个池提交子任务，然后同步 `get()`。子任务在队列里，唯一工作线程被父任务占着。增加等待时间无法打破这种依赖。

改法取决于任务关系：使用完成阶段组合，避免占着工作线程等待；不需要并行的步骤直接顺序执行；必须隔离的资源使用不同执行器，并核对两者之间是否形成新的等待环。把线程数从 1 改成 10，只会把触发门槛变成 10 个同时等待的父任务。

实验故意让父任务在有界等待后返回，随后子任务才能执行。它复现的是线程池饥饿，并没有把测试进程永久锁死。

## 4. 从一次重复处理，追到原子性和可见性

“这个字段已经加了 volatile，为什么还是少计数？”可以把 `count++` 展开成读、加一、写回：两个线程都读到 0，各自写回 1。可见性无法把几个动作合成一个动作。

Java 内存模型用 happens-before 描述跨线程操作的可见性与顺序保证。比如对同一监视器解锁先行发生于后续加锁，volatile 写先行发生于后续对该变量的读。它不等于现实时间里哪个线程先启动。[Java 21 语言规范：内存模型](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html)

| 业务需要保护什么 | 可选手段 | 还需补上的判断 |
| --- | --- | --- |
| 单个计数的原子递增 | AtomicInteger / AtomicLong | 溢出、统计口径、是否需要持久化 |
| 多个字段一起变化 | 同一把锁、不可变对象整体替换、版本 CAS | 所有访问路径是否遵守同一协议 |
| 单 JVM 中按键创建对象 | ConcurrentHashMap 的原子方法 | 映射对象本身是否线程安全，构建能否阻塞 |
| 多实例只能受理一条业务操作 | 数据库唯一约束与事务 | 冲突参数怎样处理、提交后响应丢失怎样恢复 |

`ConcurrentHashMap` 可以保护映射结构，放进去的 `ArrayList` 并不会随之成为线程安全的列表。`containsKey` 后 `put` 也不是一个原子判断。适合的场景可以用 `computeIfAbsent`，但映射函数应短小，不把长时间网络调用藏进去。[JDK 21 ConcurrentHashMap 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)

面试继续追问 AQS 时，可以回到“线程没有拿到资源怎么办”：尝试获取失败后如何等待，谁负责唤醒，唤醒后为什么仍要重新竞争，超时和中断怎样退出。ReentrantLock、Semaphore 等同步器借助 AQS 实现，但不能把每一种锁都描述为同一套实现，更不能把 AQS 等同于 synchronized。[AQS 官方说明](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/AbstractQueuedSynchronizer.html)

## 5. ThreadLocal 为什么会串用户

线程池复用工作线程。任务 A 写入用户 A 的信息，退出时没清理；任务 B 没有覆盖该字段，就可能读到 A 的信息。这是身份污染，即使暂时没有内存溢出，也已经是错误。

清理必须在执行任务的线程中完成，并放在 `finally`。把 `remove()` 写在提交任务的 HTTP 线程上，无法清掉池中工作线程的值。嵌套作用域若本来有上下文，应在退出时恢复之前的值，避免内层直接清掉外层上下文。

异步执行要明确哪些上下文需要传递，比如 trace ID；业务授权最好通过显式参数和服务端重新校验。不要默认事务、登录主体、MDC 都会自动随任务跨线程。[ThreadLocal 文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ThreadLocal.html)解释了每个线程的独立副本语义。

七个实验中的一个使用单线程池，让第二个任务读到第一个任务留下的 `user-A`，再通过 `finally/remove` 验证第三次读取为空。它验证上下文残留，不声称做过堆内存泄漏分析。

## 6. JDK 21 虚拟线程，面试应该讲到哪里

先说适用负载：大量阻塞等待、单个任务计算不重时，虚拟线程可以降低每个并发任务占用平台线程的成本。CPU 密集计算仍受 CPU 核数限制，数据库吞吐也不会因为 Java 能创建更多线程而自动提高。

JDK 21 可以使用 `Executors.newVirtualThreadPerTaskExecutor()`，按任务创建虚拟线程。下游并发仍需要 Semaphore、连接池或其他准入控制。等待者也不能无限积累：入口要有请求数上限、截止时间或拒绝策略。[JDK 21 虚拟线程指南](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)

JDK 21 中，虚拟线程在 synchronized 区域内执行阻塞操作，可能固定住承载它的平台线程。先用 JFR 观察具体栈，再决定是否缩短锁范围或使用适合的锁；不要全项目机械替换 synchronized。JDK 24 对这类 monitor pinning 作了改进，面试时应明确自己讨论的是 21。[JDK 24 变更说明](https://docs.oracle.com/en/java/javase/24/migrate/significant-changes-jdk-24.html)

一个可用的试点是阻塞式外部查询接口：保留同样的连接上限和数据规模，比较完成率、P95/P99、CPU、内存、下游活跃请求、超时后的资源释放。先证明瓶颈在等待平台线程，再讨论收益。七个实验只验证“三个虚拟线程任务经过信号量后，下游同时最多进入两个”，没有测吞吐，也没有复现 pinning。

## 7. JVM 排障：证据应该怎样连起来

### 接口慢，CPU 很高

先记录故障时间窗、实例、接口、请求量、发布版本和容器 CPU 配额。单实例满负载和整个集群一起变慢，排查起点不同。容器被限流也可能让应用变慢，应一起看 CPU throttling。

在 Linux 平台线程场景中，可以用 `top -H -p <pid>` 找持续占用 CPU 的线程，再把线程 ID 转为十六进制，与线程转储中的 `nid` 对照。连续采样才能判断热点是否稳定；单次栈只是一瞬间。虚拟线程不能照搬一一对应平台线程 ID 的假设。

更完整的证据来自 JFR：查看热方法、分配热点、锁等待及相关事件，再与请求路径对应。某个序列化方法 CPU 高，接着要问它处理的是超大对象、重复工作，还是正常负载。修改前保留输入规模，修改后重放相同请求。

### CPU 不高，工作线程很多

线程停在 `Future.get`、连接池借连接、socket read 和 monitor 竞争处，代表不同等待。`WAITING`、`TIMED_WAITING`、`BLOCKED` 这些状态只能提供线索，不能直接等同于“数据库死锁”。数据库内部的锁等待还要从数据库活动会话和阻塞关系确认。

可以先收集下面的材料。命令中的 PID 与路径需要换成实际值；这些是操作示例，本篇没有在生产 JVM 上执行。

```sh
jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> Thread.print -l
jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/tmp/incident.jfr
# JDK 21 排查虚拟线程时另取线程转储
jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json
```

`jcmd` 的可用命令、权限和影响以目标 JVM 为准。记录 profile 会增加开销，应限定时间与输出大小；堆转储的影响通常更大，先确认磁盘与执行窗口。[JDK 21 jcmd 手册](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)

### 内存一直涨，是否就是泄漏

先区分堆、进程 RSS、直接内存、线程栈和元空间。`-Xmx` 限制堆，容器内存限制约束的是整个进程；堆没满不代表不会被容器终止。

观察相近负载下 GC 后存活对象是否持续增长，再找对象被谁持有。类直方图能告诉你什么对象多，支配树和到 GC Root 的引用路径才能帮助解释为什么没释放。常见练习路径是任务队列持有大参数、无上限缓存、线程上下文残留，或一次性加载整份报表。

修复也要对应证据：队列持有大量对象就限制排队与参数大小；缓存缺少边界就加容量和淘汰；报表一次读全量就分批处理。分批不意味着可以忽略一致性，应固定数据版本或读取快照。单纯增大堆可能只是延后再次失败。

### 每次排障保留一页记录

| 项目 | 应该写下的内容 |
| --- | --- |
| 现象 | 哪个接口、哪个时间窗、影响多少请求，是否持续 |
| 初步假设 | 例如等待连接，而非直接写“JVM 问题” |
| 支持证据 | 连接池等待数、持有时间、线程栈、对应 SQL |
| 排除证据 | CPU 无热点、GC 停顿不足以解释该时间窗 |
| 修改 | 缩短哪段事务，移走哪项外部调用 |
| 验证 | 相同样本下连接等待是否下降，数据是否一致 |
| 剩余限制 | 未覆盖峰值、未验证某类大报表等具体缺口 |

## 8. Spring 事务：先说清楚边界，再背传播属性

### 自调用导致注解没有按预期生效

默认代理模式下，同一对象内部 `this.save()` 不经过代理，内层方法上的事务注解不会因此开启一个新的事务。如果外层已经有事务，内部调用仍可能在外层事务里执行；不能简单说“自调用就完全没有事务”。[Spring 事务注解说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

修复可以拆分职责，让事务方法经由另一个 Bean 调用，或用 TransactionTemplate 明确包住需要原子提交的代码。选择依据是业务边界是否清楚，不是为了绕代理而把所有类都拆开。

验收需要通过 Spring 容器中的真实 Bean 调用，制造第二条写入失败，再查询第一条是否回滚。直接 `new` 对象的单元测试无法证明代理事务生效。还要核对异常是否被吞掉，以及当前项目的回滚规则；Spring 通常默认对 RuntimeException 和 Error 回滚，受检异常要看显式配置。[Spring 回滚规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)

### @Async 为什么不能顺手继承原来的事务

传统 JDBC 事务绑定当前线程。新线程不会因为调用来源在事务内，就自动加入那笔事务。异步方法可以开启自己的事务，但那是另一个提交边界。把支付状态更新和通知发送简单扔进两个线程，不能获得共同成功或共同失败。[Spring 声明式事务原理](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-decl-explained.html)

需要可靠异步时，可以在业务事务内同时写业务记录与待发送事件，再由后台投递。消费者按事件 ID 去重，投递失败继续重试。事务提交后的内存回调可以改善执行顺序，但进程在提交后退出时，回调本身不能提供持久投递保证。

### REQUIRES_NEW 为什么可能耗尽连接

外层事务持有连接，进入 REQUIRES_NEW 后另开物理事务，需要再拿连接。若所有请求都先占着外层连接等待内层连接，就可能耗尽连接池。外层事务的锁也可能让内层事务等待。[Spring 事务传播说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

不要只回答“把池扩大”。先判断内层独立提交是否必要，能否移到外层事务结束后，能否合并事务或改变数据依赖。若保留，应按最大同时嵌套数评估连接需求并压测，不把一个固定倍数当成所有系统的正确配置。

## 9. 慢 SQL：为什么有索引也可能慢

以下是 PostgreSQL 的方案示例，字段名代表教学订单表，并未对业务库执行。

```sql
SELECT id, created_at, amount
FROM orders
WHERE tenant_id = :tenant_id
  AND created_at >= :start_time
  AND created_at < :end_time
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

`(tenant_id, created_at DESC, id DESC)` 可以作为候选索引。是否采用，需要看租户分布、时间范围、返回列、写入量和实际计划。只看“出现 Index Scan”不够：大量回表、过滤掉多数行、估计行数偏差、连接节点反复执行，都可能让它慢。

对只读查询，可以在测试环境使用 `EXPLAIN (ANALYZE, BUFFERS)`。它会实际执行查询；分析修改语句时不能把它当作无副作用的预览。对比估计与实际行数、loops、排序是否落盘、读缓冲数量，再决定更新统计信息、改查询、改索引还是减小结果范围。[PostgreSQL EXPLAIN 指南](https://www.postgresql.org/docs/17/using-explain.html)

深分页可以考虑游标方式，沿上次最后一行继续：

```sql
AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

这里假定 `created_at`、`id` 非空，排序方向一致，筛选条件不变，游标绑定租户与查询条件。数据会被修改时，还要定义分页看到哪个版本；游标分页本身不提供完整快照。需要任意跳页的界面也未必适合直接替换。

SQL 优化的验证至少包含结果集一致性、典型参数和极端参数。小租户很快、大租户仍超时，说明测试样本没有覆盖数据倾斜。压测要同时报告成功率、尾延迟、数据库 CPU/IO 与应用连接等待；只报告平均耗时会漏掉用户最容易遇到的问题。

## 10. 缓存和后台任务，各选一个能讲透的问题

### 删除缓存后，旧值为什么还会回来

可以手动画出下面的顺序：读请求 A 没命中缓存，从数据库读到旧值；写请求 B 提交新值并删除缓存；A 最后把旧值写回。于是数据库是新的，缓存又变旧了。

先问业务允许多长时间不一致。普通展示数据可以使用失效事件、较短 TTL 与回源监控控制影响；金额校验、库存扣减等决策不应依靠可能过期的展示缓存。延时双删降低某些时序的出现概率，但无法排除所有长尾请求。

如果要用版本号阻止旧数据回填，版本比较和缓存写入必须原子执行，而且删除后仍要保留可比较的版本屏障。否则键删掉后，旧版本又能以“缓存为空”为由写入。这里增加了额外状态与维护成本，应根据业务一致性要求选择。

### 分布式锁超时了，旧任务为什么还在跑

持有者 A 长暂停，租约过期，B 获得锁并完成写入，A 恢复后继续写。锁已经转移，但 A 的代码并不会自动停止。解锁时校验持有者 token 只解决“误删别人的锁”，不能阻止 A 的迟到写入。

需要正确性保证的发布操作，应让存储端检查执行代次或业务版本。任务领取时产生新的代次，结果发布用状态和代次作原子条件，旧代次更新零行。外部服务如果不支持这种检查，就要考虑它提供的幂等键、补偿机制及能保证到哪一步。不能声称所有副作用都已变成恰好一次。

这些问题可以用普通报表任务、文件生成或消息消费解释。你若在真实项目里做过其中一项，就拿当时的业务条件展开；没有做过的部分标为方案或实验。

## 11. 七个可以现在运行的实验

源码：[Java21InterviewLab.java](code/java21-interview-lab/Java21InterviewLab.java)。运行方式见 [README](code/java21-interview-lab/README.txt)，完整结果见 [verification.txt](code/java21-interview-lab/verification.txt)。在该目录使用 JDK 21 执行：

```sh
java Java21InterviewLab.java
```

2026-09-10 在 Microsoft OpenJDK `21.0.9+10-LTS` 上通过七个场景。测试使用门闩或屏障安排执行顺序，避免靠随机循环碰运气；等待均有上限，失败会抛断言异常。它们是独立语义实验，不计入预算 Agent 原有的 32 项 JUnit 测试。

| 场景 | 实际观察 | 能支持的结论 |
| --- | --- | --- |
| 无界队列 | 一个工作线程，两个排队任务 | 最大线程数不会因排队自动生效 |
| 有界队列 | 两个线程、一个排队，第四项被拒 | 接纳与拒绝分支符合预期 |
| Future 超时 | 调用方失败后，底层继续完成一次动作 | 超时不等于工作停止 |
| 同池父子任务 | 父任务等待超时返回后，子任务才执行 | 同池同步等待可能造成饥饿 |
| ThreadLocal 复用 | 下一任务读到旧用户，清理后为空 | 清理位置与线程复用有关 |
| volatile 读改写 | 强制交错后为 1，原子递增为 2 | 可见性不保证复合操作原子性 |
| 虚拟线程准入 | 三项任务，下游峰值为 2 | 虚拟线程与下游限并发可以分开控制 |

这里没有性能百分比。下次补实验时，优先选一个与你实际工作有关的问题：通过真实 Spring Bean 验证事务回滚，或者在测试数据库制造长事务，记录连接等待和恢复过程。

## 12. 面试时怎样把深度说出来

可以按“触发条件 → 证据 → 判断 → 修改 → 验证”准备，每次只讲一个问题。下面是基于已运行实验的口语示例，不对应公司事故：

“我专门复现过线程池扩容不符合直觉的情况。最大线程数设为 3，但队列无界，第一个任务阻塞时，后续两个任务都排队，实际仍只有一个线程。换成容量为 1 的队列后，才进入扩容和拒绝分支。这个实验提醒我，处理接口积压时要先拆开排队时间和执行时间，再结合数据库连接上限决定并发，不能只调最大线程数。”

更深入的追问可以这样练：

| 问题 | 回答中至少要包含 |
| --- | --- |
| 为什么不把队列开得更大？ | 等待时长、内存、过期任务、调用方如何知道失败 |
| 为什么不用虚拟线程全部替换？ | 等待型负载、CPU 与下游容量、JDK 21 的实际约束 |
| 加了超时怎么还会重复？ | 等待超时、执行取消、提交结果、业务去重的区别 |
| @Transactional 没生效怎么证明？ | 调用是否经过代理、实际写入是否回滚、异常规则 |
| 你如何判断优化有效？ | 相同数据与负载、成功率与尾延迟、正确性、资源成本 |

建议先用约 18～24 小时完成这篇的复习、实验和一次模拟追问。这是两个月总计划中的时间分配建议，优先从已有 Java 知识恢复，不另外扩成一轮完整后端课程。最后留下两张排障记录，再进入迁移方案；时间不够就缩小案例数量，把选中的问题讲清楚。
