# 这套项目资料，先从这里读起

员工要汇报几个项目的预算和费用。系统里有数据，但他还得找到页面、选对口径、整理图表，最后导出 Excel 核对。这套项目想把这些步骤接起来：用户说明要汇报什么，Agent 补齐缺少的信息，调用业务服务，再给出有依据的结果。

全文采用 Java 21。Spring Boot 承接业务接口，LangGraph4j 保存执行状态、组织节点和恢复任务；查询、分摊、权限仍由 Java 业务代码执行。先理解一笔账和一次任务，再去记框架名。

## 全套资料只用这一组账

| 项目 | 调整后预算 | 已核算费用 | 部门 D_A 的分摊比例 |
| --- | ---: | ---: | ---: |
| P01 | 70 万元 | 77 万元 | 60% |
| P02 | 50 万元 | 49 万元 | 20% |

因此 D_A 的预算是 `70×60%＋50×20%=52 万元`，实际是 `77×60%＋49×20%=56 万元`，差额 4 万元，执行率约 107.69%。P01 贡献了 4.2 万元超支，P02 比预算少 0.2 万元。

部门、重量级团队、投资方是不同分摊轴。每个轴都可能展示完整的 126 万元实际费用，不能把三个轴相加。也不能拿部门比例乘投资比例，凭空推导联合分摊。第 04 篇会把这个问题算清楚。

## 现在能运行到哪一步

[下载 Java 示例](code/langgraph4j-demo.zip)，或直接看 [pom.xml](code/langgraph4j-demo/pom.xml)、[运行说明](code/langgraph4j-demo/README.txt)和[验证记录](code/verification.txt)。依赖固定为 LangGraph4j 1.8.27。

目前实际通过 32 项 JUnit 检查：12 项分摊计算、11 项业务一致性、9 项图执行与状态恢复。另用三个独立 JVM 完成“等待口径 → 提交导出后丢失响应 → 恢复”的实验，最终只有一个导出任务。

这份示例使用合成数据、固定决策替身、H2 文件库和 FileSystemSaver。它验证的是查数与导出任务受理，尚未接真实模型、Spring Boot HTTP 服务、生产权限系统，也没有真正生成图表或 Excel。正文中的完整应用架构是下一步设计；面试时要把这两个范围分开说。

新增的独立实验有两组：[Java 21 七个语义场景](code/java21-interview-lab/README.txt)和 [PostgreSQL 七个语义场景](code/pg-migration-lab/README.txt)。均已本地运行，记录分别见 [Java 日志](code/java21-interview-lab/verification.txt)、[PG 日志](code/pg-migration-lab/verification.txt)。它们不计入上面的 32 项 JUnit，也不代表预算 Agent 已接入 PostgreSQL 或完成了生产迁移。

## 读完怎样判断自己懂了

试着不看正文，画出一次请求从入库到完成的过程；再手算 D_A 的 52 万和 56 万；最后运行响应丢失实验，说明为什么恢复后没有多出第二个任务。能解释这三件事，比背下一串组件名称更有用。
