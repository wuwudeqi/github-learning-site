# 业务方法管理、系统导航与 MCP 能力接入

> 本文为目标设计，工具、表结构和版本号均是项目自定义示例，不是已上线能力，也不是框架内置字段。真实背景是原系统复杂、多个分摊查看维度、固定卡片图表依赖开发，员工使用和功能更新需要培训宣讲。

## 1. 从真实痛点划分三类知识

员工以前需要记住从哪里进入、选什么维度、采用什么口径，以及导出后如何做图。系统更新以后，旧操作路径和旧培训材料可能继续流转。Agent 要降低这部分成本，不能只加一份“你是预算专家”的 Prompt。

| 内容 | 权威存储与责任 | Agent 如何使用 |
| --- | --- | --- |
| 如何完成一次汇报：确认范围、选择视角、差异下钻、附核对数据 | 业务维护的 Skill 和模板，发布后生效 | 按需加载任务方法，组织分析与材料 |
| 指标含义、分摊比例、规则生效期、项目及维度适用性 | Java 业务服务及已审核规则目录 | 通过工具查询、校验和计算，不能从文本复制公式作为执行依据 |
| 页面说明、术语解释、功能更新、版本差异 | 有版本和适用范围的知识资料 | 检索并引用，解释功能或提供入口，不据此获得权限 |

例如，业务可以把“汇报需列出部门承担金额和人力费用构成”加入方法；不能通过改 Skill 把部门比例从 60% 改为 70%。已审核规则变化需要走原系统的规则管理流程，Skill 只引用规则含义与能力标识。

**实践假设**仍是部门、重量级团队、投资为独立分摊轴。业务写“同时看部门与投资”时，可以并列两张独立视图；如果要求联合交叉金额，必须有对应规则，不能用两个边际比例相乘。硬约束放在 Java 校验器，不能只靠 Skill 提醒。

## 2. Skill、RAG、Function Calling、MCP 分别负责什么

| 机制 | 本项目中的职责 | 不能替代 |
| --- | --- | --- |
| Skill | 可复用的业务任务方法及参考资源 | 正式分摊规则、数据库权限、确定性计算 |
| RAG/资料检索 | 找到与当前功能和规则版本匹配的解释、操作指引 | 权威规则查询；文档写了不代表能力已实现 |
| Function Calling | 模型提出工具名和结构化参数 | 应用执行、参数语义验证、业务授权 |
| MCP | 规范化工具发现与调用，接入已有 Java 能力 | 企业数据权限、业务事务、自动幂等 |
| LangGraph 运行层 | 路由、状态、追问、恢复、停止，执行模型提出的合法动作 | Java 领域规则及持久业务事实 |
| Java 预算应用 | 身份、有效计划、规则、查询、结果和产物 | 理解各种自然语言表达、自由组织汇报 |

Function Calling 中由应用执行工具并把结果交回模型；提供 JSON Schema 不会使模型自行拥有执行能力。[Spring AI 工具调用文档](https://docs.spring.io/spring-ai/reference/api/tools.html)

![Skills 与 MCP 协作关系](./images/capability-management.svg)

先用两个主 Skill，不按每个部门或项目复制一套：

| Skill | 适用场景 | 本次任务中的方法 |
| --- | --- | --- |
| budget-execution-analysis | 多项目预算核算查询、分摊视角分析 | 确认项目/期间/预算定义/分摊轴，查汇总，按可比较粒度下钻，引用证据 |
| budget-report-generation | 已有有效结果，生成临时汇报 | 校验证据和完整性，选择卡片图表，附查询数据、口径说明和待核查项 |

系统操作和更新说明先作为参考资料，不必再建一个自主 Agent。简单“页面入口在哪里”的请求可以直接查指引；复杂“帮我完成汇报”才进入完整分析流程。

## 3. 业务怎么维护 Skill

业务后台提供任务场景、必需条件、分析建议、输出要求、术语别名、参考资料和试运行入口，不要求业务人员学习 MCP 或写程序。底层可生成以下目录：

```text
budget-execution-analysis/
  SKILL.md
  references/
    allocation-view-guide.md
    variance-analysis-method.md
    release-notes.md
  assets/
    report-template.md
```

Skill 格式可以使用 SKILL.md、references 和 assets，并按元数据、正文、相关资源逐步加载；业务后台、审批记录和运行版本绑定是本项目另外实现的能力。[Agent Skills 规范](https://agentskills.io/specification)

示例节选：

```yaml
---
name: budget-execution-analysis
description: 根据多项目汇报目标，确认预算与实际口径及分摊视角，查询可核对的执行结果并定位差异。
metadata:
  version: "1.3.0"
---
```

正文方法可以是：

1. 判断用户是在询问操作方法，还是要求取得业务结果。
2. 查询指标与分摊视角定义；关键歧义由有效计划校验返回，必要时澄清。
3. 先查指定范围汇总，再根据差异与支持粒度选择项目、费用类型下钻。
4. 事实只引用当前有效结果。无法从数据证明的原因写为待核查项。
5. 汇报列出项目范围、期间、预算定义、分摊轴、数据截止时间及查询数据入口。

“必需显示分摊轴”不能仅存在自然语言正文中。项目另存受校验配置，例如 `required_sections=[scope,period,budget_basis,allocation_axis,data_release,evidence]`，由报告验证器检查；下钻顺序等灵活建议才交模型参考。该字段是项目配置，不是 Agent Skills 标准字段。

业务可维护报告关注阈值，但阈值必须带单位、适用范围、生效期与用途。它决定哪些差异值得展示，不改变实际发生额或已审核分摊比例。新增正式指标、联合分摊或权限变化，仍由原业务治理流程处理。

## 4. 方法更新如何减少重复培训

例：原来员工只用部门视图，后来增加重量级团队视图。传统方式需要重新讲页面入口、适用项目、操作方式；目标方案把更新拆为三项：

- 开发发布查询能力和合法轴目录，声明哪些项目、期间和指标支持重量级团队视图。
- 业务更新说明及分析方法，解释这个视角回答什么问题、何时使用，关联对应能力版本。
- Agent 依据用户任务按需展示说明，已有合法工具则直接完成查询；需要页面核对时提供版本匹配的入口。

这不能保证完全取消培训。指标定义或规则发生实质变化时，仍需要向使用者明确披露；Agent 只减少反复讲操作步骤和到处找资料的成本。评价可以比较固定任务的首次完成率、人工求助次数及完成耗时，不能未经测试就声称培训成本下降多少。

### 检索要带版本，不能只找最相似的段落

资料记录至少包括 doc_id、revision、适用功能、适用项目类型、规则版本范围、valid_from/valid_to、发布状态、访问范围和正文 hash。

先由有效计划或能力目录确定当前版本，再按访问权限、发布状态及适用版本过滤，最后做关键词/向量匹配。仅两个 Skill、几十条说明时，目录与关键词检索即可起步；资料规模和语义召回问题出现后再引入向量索引。

一次结果应包含引用 ID、资料版本、适用性和出处。检索不到匹配版本时说明“暂无对应说明”，仍可使用合法业务工具完成支持的查询；不能用旧资料代替现行计算规则。查询“过去的规则如何解释”可以检索历史版本，但不得混入当前执行上下文。

## 5. 发布、固定版本与回退

| 对象 | 关键内容 |
| --- | --- |
| skill_definition | 稳定身份、负责人、编辑与发布权限 |
| skill_revision | 不可变正文及资源清单、body_hash、创建人 |
| skill_dependency | 所需能力、合同版本范围、引用资料及模板版本 |
| skill_release | active_revision、适用范围、生效时间 |
| skill_eval_run | 固定案例集版本、逐例结果、失败归因 |
| guidance_revision / index_release | 文档内容版本、适用范围、已完成索引版本 |
| analysis_run | 实际使用的 Skill、资料、工具合同和模板版本 |

发布流程是：草稿 → 结构校验 → 工具/规则依赖检查 → 固定案例回归 → 更新发布指针。首版不允许业务上传任意可执行脚本，引用路径和资源大小也有边界。

回归要包括：部门汇报、投资切换、缺失规则、预算口径歧义、无联合分摊却要求交叉金额、用户无权范围，以及更新后无法找到对应说明。方法必须能在现有能力上执行，不能因为正文写了新工具就允许发布。

新 run 绑定当前发布版本；运行中固定旧 Skill 与引用资料，避免报告生成到一半突然改方法。回滚只切换新任务使用的活动指针，不覆盖旧版本。已生成的报告仍保留原方法与数据证据，不用回滚后的内容重写历史。

紧急安全禁用优先于版本固定：工具被禁用或权限撤销后，旧任务在下一执行边界也不能继续。规则变化则由有效计划的版本及当前可用性策略判断，不能假定固定版本意味着永远可执行。

资料索引构建完成后，再发布匹配的 index_release。首版可以采用“未就绪的新说明不进入发布”的简单流程，避免发布指针先变而检索仍读旧向量。无需为了两个 Skill 先建设复杂平台，但不可变版本、明确依赖、回归及回退应保留。

## 6. MCP 包装现有 Java 能力

Java 应用内增加薄适配模块，复用原有领域服务，不复制分摊计算：

```text
MCP 工具适配器
  → 验证服务身份与用户委托上下文
  → 参数、当前授权和合同校验
  → 原有指标 / 分摊 / 查询 / 结果 / 产物服务
  → 统一业务状态与错误
```

工具目录按能力划分，避免每张报表一个工具，也避免一个无约束 execute_sql：

| 工具名（项目示例） | 输入概要 | 返回概要 |
| --- | --- | --- |
| budget_resolve_context | 意图、项目/期间/分摊轴候选 | 指标、合法维度、可用规则和歧义 |
| budget_validate_plan | requested_plan、可选父计划 | 有效计划及版本、范围、允许下钻项 |
| budget_query | effective_plan_id | 标准指标 result_id、schema、有界摘要 |
| budget_validate_sql | effective_plan_id、候选 SQL | validated_query_id 或结构化拒绝原因 |
| budget_execute_query | validated_query_id | result_id、版本、完整性 |
| budget_get_result | result_id、分页游标、字段 | 有界数据及字段元信息 |
| budget_get_guidance | 问题、能力标识、相关版本 | 经权限及版本过滤的说明和引用 |
| budget_create_artifact | result_ids、格式、ChartSpec/模板 | artifact_job_id、状态 |

这些能力可先内部 HTTP 验证，再通过 MCP 适配暴露相同领域服务。MCP 定义工具发现和调用方式，项目仍需实现工具到业务服务的映射以及业务权限。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

Spring AI 提供 Spring Boot MCP Server 集成，可用于包装 Java 能力；这不表示 Java 端再启动第二套 Agent 编排循环。实现时锁定 Spring Boot、Spring AI/MCP SDK 和 Python 客户端版本，做合同与认证测试，不给出未验证的依赖组合。[Spring AI MCP Server 文档](https://docs.spring.io/spring-ai/reference/api/mcp/mcp-server-boot-starter-docs.html)

工具描述至少说明何时使用、前置有效计划、支持粒度和不可做的事。例如 budget_query 明确不能修改分摊比例、不能将部门结果自动转换为投资结果、不能把预览前十行当全量。

## 7. Function Calling 到 MCP 的真实运行路径

模型不直接执行 MCP。完整路径是：

```text
受信 MCP Server 的工具目录
  → Python 适配器筛选兼容且本任务需要的工具
  → 转成当前模型支持的工具 Schema
  → 模型返回 Function Calling 请求
  → 运行层检查当前节点、参数和计划归属
  → MCP Client 发起 tools/call
  → Java MCP Adapter 重新鉴权并调用业务服务
  → 工具结果标准化，按模型调用 ID 配对回传
  → 更新证据与状态，模型继续或结束
```

例如模型可提出如下逻辑内容，示例不是完整 MCP 协议报文：

```json
{
  "tool": "budget_create_artifact",
  "arguments": {
    "result_ids": ["res-dept-001"],
    "formats": ["xlsx", "svg"],
    "template_id": "budget-report-standard"
  }
}
```

actor、tenant、服务凭证、operation_id 从可信运行层注入，不能作为模型可随意更改的字段。拒绝未知身份字段，Java 也要验证委托主体与运行归属；不能相信一个普通请求头里随便写的 user_id。

运行层分别记录三个标识：模型 tool_call_id 用于配对工具消息，MCP 请求 ID 用于协议关联，operation_id 用于跨重试识别同一业务操作。重连或模型重试可能改变前两个 ID，但导出的业务操作 ID 保持稳定。

工具目录绑定 server endpoint、工具名和合同版本。跨 Server 同名工具采用受控命名空间，不按第一个裸工具名匹配。多个调用只能在没有依赖、无冲突副作用时并行，工具结果按 ID 而非完成顺序配对。

成功也有三层：传输成功、工具业务成功、用户任务完成。HTTP 成功或 MCP 返回正常并不代表 SQL 被批准；SQL 成功不代表所有格式导出都成功。状态机分别记录并决定澄清、重试、降级或终止。

## 8. 一次版本可追溯的执行

用户请求按部门汇总两个项目，生成图表与 Excel。运行层选择 budget-execution-analysis，固定 Skill v1.3、工具合同清单和解释资料版本。Java 将需求转为有效计划，绑定部门轴、指标、规则包与数据发布版本。

查询返回 D_A 预算 520,000 元、实际 560,000 元；模型决定按项目下钻，派生计划仍保持同一轴和版本。上述金额来自合成案例，不是运行记录。模型如果进一步要求“按投资方解释 D_A 的金额”，Java 发现没有联合规则，返回不支持；允许另开独立投资视图，不能直接交叉计算。

进入报告阶段时按固定版本加载 budget-report-generation。模板要求显示部门视角、期间、预算定义、来源结果及待核查项。运行层准备稳定操作 ID，MCP 调用产物服务；Java 再查当前权限，所有产物消费同一组有效 result_id。

若中途发布新 Skill，当前 run 继续使用已固定版本；若工具被紧急禁用，则终止相关执行。员工询问“为什么结果与旧页面不一样”，Agent 先检查项目范围、分摊轴、数据和规则版本，再引用对应更新说明，不能直接声称是数据错误。

## 9. 难点：症状、排查、解决和验证

以下是可实施的故障演练，不是虚构线上事故。

### 9.1 Skill 更新了，Agent 仍教员工旧操作

**症状：** 新请求仍引用旧入口，或解释旧分摊视图。先区分是新 run 还是固定旧版本的在途 run，后者未必有错误。

**排查顺序：** run 的 Skill revision → 实际加载的资源 hash → 当前说明发布指针 → 检索过滤条件 → index_release → 命中文档及版本 → 缓存 key → 模型最终引用。只看后台“发布成功”不足以证明运行中已加载。

**可能根因：** 更新正文但忘记 references；索引尚未完成；缓存只按问题文本命中；检索忽略适用版本；模型上下文还保留旧引用。修复分别是资源 manifest、索引就绪后切指针、版本/权限参与缓存、过滤后检索及失效证据清理，不能仅提示“请使用最新版”。

**验证：** 固定同一句问题分别运行旧、新版本；核对引用 ID、内容 hash、入口和适用范围。回退后新请求应选择回退版本，在途任务仍可追溯原版本。

### 9.2 Skill 说按投资拆，工具只支持部门

**症状：** 模型持续重试不存在的 allocation_axis 或调用未注册工具。

**排查：** Skill 依赖 → 当时工具 schema → Java 能力目录 → 项目/期间适用性 → 实际工具错误码。支持某个工具不等于每个项目都支持每个维度。

**解决：** 发布时验证能力合同，运行时取得具体项目的合法轴；UNSUPPORTED_AXIS 进入能力说明或澄清，不当成瞬时故障重试。新增轴由开发接入权威规则后才发布方法。

**验证：** 同一 Skill 面对支持与不支持投资轴的两组项目，分别应正常执行和明确报告限制，不能静默排除不支持的项目后标记全量。

### 9.3 文档说比例 60%，实际工具按 70% 计算

**排查：** 是否同一项目、费用范围、期间和分摊轴 → 预算规则还是实际规则 → 当前有效计划命中的规则绑定 → 文档适用版本。先排除不同对象和时期，再判断陈旧文档。

**解决：** 已审核规则服务是执行权威。不能让模型用文本重新算一遍“纠正”结果。暂停给出确定的原因解释，显示采用的规则版本，将冲突记录为资料修订项；若权威规则本身异常，由原业务流程核查，不由 Agent 修改。

**验证：** 构造旧资料和新规则冲突，确保金额始终来自工具，报告不把旧比例写为当前依据，引用冲突可定位。

### 9.4 MCP 超时后出现重复导出

**排查：** 模型调用 ID、MCP 请求 ID、稳定操作 ID是否混用 → Java 是否已受理 → 参数 hash 是否一致 → 任务及产物状态。

**解决：** 操作意图先持久化，重试沿用 operation_id，Java 唯一约束并比较规范化参数；重连不能生成新的业务身份。传输超时与业务拒绝分别处理。

**验证：** 在 Java 提交后主动丢弃响应，恢复仍返回同一 artifact_job_id；相同 ID 不同参数明确冲突。

## 10. 面试如何回答到工程层

**业务维护 Skill，是不是把 Prompt 开放给业务？** 开放的是任务方法、参考说明和模板。强制输出项结构化校验；指标、规则和权限由可信服务维护。还要有不可变版本、依赖、回归、发布和回退，不能在线覆盖一个大字符串。

**Skill 和 RAG 为什么都要？** Skill 组织“怎样完成任务”，检索提供“当前功能和口径怎样解释”。少量说明可直接按版本加载，不必先建向量库。它们都不能替代正式规则计算。

**MCP 能不能直接解决数据权限？** 不能。MCP 解决能力接入，Java 对每次调用验证当前用户、计划、结果及数据范围。高权限业务作者发布的 Skill 不把作者权限交给执行用户。

**为什么接入 MCP，还需要 Function Calling？** 模型用 Function Calling 表达工具请求，运行层把请求转换为 MCP 调用。模型不是 MCP Client，MCP Server 也不等于 Agent。内部最小验证可以先用 HTTP；需要标准化接入和合同管理时再包装相同服务。

**怎样说明它降低了培训成本？** 用固定任务比较新员工首次正确完成率、人工求助次数与耗时，并核对数据正确性。把“无需记住入口”和“无需理解业务口径”分开，后者仍需解释和必要澄清。没有真实测量，就只讲设计目标和验证方案。

**怎么证明更新能安全回退？** 展示旧、新 Skill 与索引版本及同一组回归输入，发布后新 run 切换、旧 run 固定，回退后再次验证新 run。还要覆盖缺工具、正文注入、越权试运行与资料版本冲突，不只测试一条正常路径。
