# 项目背景与整体架构

> 本文为独立实践项目设计，组件与场景不代表原公司系统已采用。

## 1. 项目定位

项目名称：预算分析与导出 Agent。

预算和项目数据分散于业务系统、导入文件与人工维护记录。已有报表解决固定维度的展示，但临时问题仍需要人员确定口径、切换筛选条件、查看明细并整理导出结果。

项目提供自然语言入口，将用户需求转换为受控查询计划，通过 Java 业务工具完成计算和导出，并保留数据出处及执行记录。

### 贯穿案例

用户：“分析研发部 2026 年上半年预算执行情况，列出主要超支费用项，并导出项目明细。”

模拟数据设定：研发部拥有项目 P01、P02；上半年年初预算为 100 万元，调整后预算为 120 万元，实际发生额为 126 万元，已付款额为 90 万元。金额均为合成数据。

当口径是“调整后预算、实际发生额”时：执行率为 105%，预算差异为实际减预算，即超支 6 万元。若错用“年初预算、已付款额”，会得到 90%，结论完全不同。

项目必须先解决“查得对”，再解决“解释好”。真实业务公式以业务定义为准，本文公式只用于模拟环境。

## 2. 输出与完成标准

一次成功任务应返回：采用的指标口径、组织范围与期间；预算/实际/差异；必要的明细或主要贡献项；查询证据标识和数据截止时间；用户要求导出时的任务状态或文件入口。

如果条件不足，应明确追问；如果数据缺失，应返回缺失状态。不得把缺失记录默认为零，也不应把差异贡献直接写成业务原因。

## 3. 整体架构

![预算分析 Agent 整体架构](./images/architecture.svg)

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 交互层 | 简单 Web 页面 | 问题输入、口径确认、进度、结果与导出下载 |
| 接入层 | Spring Boot API | 登录态、会话归属、请求校验、任务接口、事件转发 |
| 编排层 | Python 服务 + LangGraph | 状态图、模型调用、追问、工具路由、下钻与停止 |
| 业务工具层 | Spring Boot 服务 | 指标定义、权限检查、确定性查询计算、导出 |
| 数据层 | PostgreSQL | 模拟业务数据、报表版本、操作任务与检查点的独立 schema |
| 支撑层 | 文件存储、结构化日志 | 导出文件、证据引用、调用轨迹与评测记录 |

Java 接入与业务工具可以放在同一个 Spring Boot 应用中，不必拆微服务。Python 编排单独部署即可。首版用一个 PostgreSQL 实例隔离 schema，Redis 和消息队列不是必选项。

LangGraph 支持在同一图中混合确定性步骤和模型驱动步骤，可以独立于 LangChain 使用。本设计用 LangChain 的模型/工具组件简化接入，用 LangGraph 控制执行流。[官方概览](https://docs.langchain.com/oss/python/langgraph/overview)

## 4. 一次请求的完整链路

1. Java 验证用户身份，创建任务与会话关联，把可信身份上下文传给编排服务。
2. Agent 识别意图，读取相关指标定义，将自然语言整理成查询计划。
3. 条件含糊时暂停追问；明确后由 Java 校验组织范围和指标组合。
4. Java 选择已发布报表版本，生成绑定版本的有效计划标识。
5. Agent 调用查询工具。后端查询、计算、生成结果摘要和证据标识。
6. Agent 根据差异选择允许的下钻维度，最多执行配置的分析步数。
7. 生成带证据的分析；校验数值与来源，失败则使用确定性结果模板。
8. 用户已要求导出时创建异步任务，无需重复确认。用户改变条件或请求超出授权范围时重新处理。
9. 页面查看进度并下载文件；下载接口重新检查当前权限。

## 5. 关键技术取舍

### 为什么 Python + Java

Python 负责 Agent 编排实践，Java 复用后端工程能力。代价是双服务部署、接口版本、调用链排查和鉴权传递。这里选择 HTTP 工具接口，先不增加 MCP 层；当工具需要被多个客户端发现和复用时再评估 MCP。

纯 Java 方案也可行。选择混合方案的原因是求职目标同时覆盖 Agent 编排与企业后端，不是认为 Java 无法开发 Agent。首版不同时维护 Spring AI 和 LangGraph 两套运行时。

### 为什么单 Agent

任务围绕同一指标语义和权限范围。多个 Agent 会增加上下文同步、失败定位与成本问题，暂时没有独立角色或隔离执行的必要。并行查询可以由程序并发完成，不需要为每个查询创建一个 Agent。

### 为什么不直接开放数据库

受控工具可以统一口径、权限和查询资源。模型选择查询目的，后端决定可访问的数据与计算方式。固定工具先覆盖核心场景，受限 Text-to-SQL 留作独立对比实验。

## 6. 数据模型的最小集合

| 数据对象 | 关键内容 |
| --- | --- |
| project、organization | 项目、组织及层级映射 |
| source_batch | 来源、批次状态、业务截止时间、导入校验结果 |
| report_release | 报表发布版本及各来源批次组成 |
| budget_fact、actual_fact | 版本、项目、期间、费用项、币种、金额 |
| metric_definition | 指标 ID、定义版本、公式、可用维度与说明 |
| analysis_run | 会话归属、任务状态、有效计划、版本与关联 ID |
| export_task | 操作 ID、参数摘要、状态、租约和文件位置 |

报表发布版本与业务预算版本不同：前者固定一次分析读取的数据集合，后者表示年初/调整等预算口径。两者均需记录。组织映射和指标定义也必须绑定版本，避免事实数据固定而关联规则改变。
