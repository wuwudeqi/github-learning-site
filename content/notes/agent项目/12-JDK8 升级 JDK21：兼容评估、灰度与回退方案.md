# JDK 8 升级 JDK 21：兼容评估、灰度与回退方案

你已经经历过 JDK 8 到 JDK 21 的升级。这段经历可以展开为一次工程方案设计：团队怎样发现兼容问题，怎样缩小变更范围，凭什么决定放量，出现问题又怎样退回。

目前已知的是“参与过升级、当前使用 JDK 21”。原系统的 Spring Boot 版本、依赖清单、实例规模、具体职责与实际收益尚未提供。下面是一份可用于复盘和面试的方案，示例故障没有被写成你的亲历事件。本次没有执行真实业务系统的 JDK 迁移，也没有得到升级前后的性能数据。

## 1. 升级方案先写清什么

方案首页可以用下面这张表。准备面试时，把每一行补成你确实知道的事实；缺失的信息保留为待核对，不需要编一个数字填满。

| 信息 | 为什么要确认 | 可以从哪里找证据 |
| --- | --- | --- |
| 原 JDK 与目标 JDK 的发行版、完整补丁号 | 同为 8 或 21，补丁、证书与运行环境仍有差异 | 容器镜像、VM.version、发布记录 |
| 构建 JDK、运行 JDK、目标字节码 | 三者可以不同，编译成功不能证明运行成功 | CI 配置、Maven/Gradle 配置、制品 |
| 框架、ORM、驱动、字节码库、APM Agent | 应用启动之外还有代理生成与插桩路径 | 锁定依赖树、启动参数、镜像内容 |
| 操作系统、CPU 架构、容器资源配额 | 原生库兼容和性能比较都依赖环境 | 部署配置、镜像架构 |
| 升级动机 | 安全维护、依赖支持、新能力，各自对应不同验收 | 技术评审和业务约束 |
| 个人负责范围 | 区分方案负责人、模块适配、回归和上线支持 | 提交、测试报告、评审记录 |

成功条件至少包含：关键业务结果符合合同，依赖故障可定位，新旧实例可以按计划共存，性能满足原有服务目标，旧制品可以在规定条件下恢复。先写这些条件，再选具体升级路线。

## 2. 分阶段升级，控制每次改变的变量

先保留一份可以重建、可以部署的旧基线：源码提交、依赖版本、JDK 镜像、启动参数、配置和测试样本都能找到。只存一个旧 jar，不足以保证能回退。

| 阶段 | 改变什么 | 主要回答的问题 |
| --- | --- | --- |
| A：原版本基线 | 仍使用原 JDK 8 与原依赖 | 旧系统的正确结果与资源表现是什么 |
| B：准备依赖 | 在版本支持的前提下，先更新阻碍迁移的依赖 | 依赖更新自身是否改变行为 |
| C：目标运行时验证 | 对兼容的制品使用 JDK 21 运行 | 哪些问题来自运行时变化 |
| D：目标构建验证 | CI 与插件切换到明确的 JDK 21 构建方案 | 能否稳定构建、测试、打包和诊断 |
| E：后续能力试点 | 单独引入虚拟线程、新语法或框架大版本 | 新能力带来的收益与代价是什么 |

阶段 B 的前提不能省：如果新依赖最低要求已经超过 JDK 8，它就无法先在 8 上验证。此时需要调整阶段边界，单独记录这组必须一起变化的依赖与运行时，并增加对应回归，不能声称完全隔离了变量。

没有普遍要求必须把生产环境按 8 → 11 → 17 → 21 逐次上线。中间版本可以辅助定位问题，是否采用过渡部署取决于依赖支持、团队能力和回退成本。

`--release 8` 约束编译目标及可使用的对应平台 API，但不会把依赖库自动变成兼容 JDK 8 的版本。目标为 21 的新制品也不能交给旧 JVM 运行。回退应部署保存好的旧制品和旧运行时，而不是临时修改启动命令。[javac 的 --release 说明](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javac.html)

## 3. 依赖盘点要覆盖启动以外的路径

检查范围包括运行依赖和构建依赖。Lombok、注解处理器、测试插件、代码覆盖率工具、Byte Buddy/ASM、旧代理库、JDBC 驱动、日志组件与 APM 插桩都可能影响迁移。

对每项依赖，记录当前版本、目标版本、JDK 21 支持依据、引入位置、验证用例和负责模块。不要把 Maven 能解析依赖当作兼容证明。测试环境没加载 APM，而生产启动时会加载，也应列为环境差异。

下面的命令用于方案准备，没有对你的生产制品执行。`app.jar` 假定是普通应用 jar，依赖展开在 `lib/`；Spring Boot 可执行 jar 的嵌套依赖需要先按实际布局展开或逐项检查。

```sh
mvn dependency:tree
jdeps --multi-release 21 --jdk-internals --class-path 'lib/*' app.jar
jdeprscan --release 21 --class-path 'lib/*' app.jar
```

`jdeps` 能帮助发现字节码中的静态依赖，但无法穷举字符串反射、运行时生成类与动态插件路径；`jdeprscan` 检查废弃 API 使用，也不是“全量兼容扫描”。扫描报告没有问题后，仍要运行功能与集成测试。[jdeps 手册](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jdeps.html)、[jdeprscan 手册](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jdeprscan.html)

## 4. 兼容问题怎么分类处理

### 强封装：InaccessibleObjectException

一个典型练习是旧序列化库反射访问 `java.lang` 的私有成员，在新 JVM 上报错。先从栈中找到发起反射的依赖和版本，确认是否有使用受支持 API 的新版本，再决定升级、替换或临时放行。

JDK 17 起强封装收紧；在 21 上，旧的 `--illegal-access=permit` 不能恢复原来的访问行为。必要时可针对具体包使用 `--add-opens`，但应保存触发原因、依赖版本和移除条件。[JDK 21 迁移指南：强封装](https://docs.oracle.com/en/java/javase/21/migrate/migrating-jdk-8-later-jdk-releases.html)

```sh
# 仅当已确认问题涉及该包、且短期无法升级依赖时，作为过渡示例
java --add-opens java.base/java.lang=ALL-UNNAMED -jar app.jar
```

这个参数给所有未命名模块开放了对应包，范围不能忽略。修复验收包括：原失败路径成功，回归没有新错误，并在依赖替换后去掉参数再次测试。把网上一长串 opens 全贴进启动脚本，会失去对真实依赖问题的掌握。

### 移除的模块和运行参数

旧程序如果依赖 JDK 内置 JAXB/JAX-WS，需要显式提供合适的 API 与实现；Nashorn、CMS 等能力也不能按旧假设继续使用。这些变化发生在不同版本：相关 Java EE 模块在 11 移除，CMS 在 14 移除，Nashorn 在 15 移除。[JDK 21 迁移指南：移除的工具与组件](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)

对应验收要具体。XML 接口测实际报文读写；脚本功能测原来的业务表达式；GC 参数检查启动是否生效并保存实际 VM.flags。不能只删掉无法识别的参数，然后认为系统行为没有变化。

### 编码：中文文件不该依赖机器默认值

从 JDK 18 起，Java SE API 的默认字符集改为 UTF-8。原系统如果依赖操作系统默认编码读写文件，迁移后可能改变字节与文本之间的解释。控制台编码还需要单独确认。[JDK 18 官方发布说明](https://www.oracle.com/java/technologies/javase/18-relnote-issues.html)

假设上游历史 CSV 合同为 GBK，就按 GBK 解码；输出合同为 UTF-8，就明确用 UTF-8 编码。不要为了“统一编码”把已有 GBK 文件直接当 UTF-8 读。建议保留含中文、特殊符号、换行、空字段和 BOM 的脱敏样本，比较字段值，并验证下游软件能否正常打开。

同样要检查日期格式、Locale、时区、TLS 握手与证书链。每个问题对应一个接口合同或数据样本，不只确认接口返回 200。TLS 失败应核对证书和协议，不以全局关闭校验作为迁移修复。

### Spring Boot 3 与 Jakarta 是另一组变更

升级 JDK 21 不必然等于升级 Spring Boot 3。先查当前框架具体版本的 JDK 支持范围；如果确实要升 Boot 3，再按对应迁移指南处理依赖、配置与 Jakarta EE API。

`javax` 到 `jakarta` 的变化针对迁移的 EE API，不能全局替换所有 `javax.*`。例如 `javax.sql`、`javax.crypto` 不该被机械改名。还要检查 Servlet 容器、校验组件、持久化组件与第三方库是否使用同一代合同。[Spring Boot 3.0 官方迁移指南](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-3.0-Migration-Guide)

方案里可以把这组变更单列，明确是本次必需依赖还是后续升级。面试时能说清这些边界，比只说“把 javax 改成 jakarta”更有价值。

## 5. 业务回归怎样才算覆盖到位

先从最容易静默出错的路径选样本。编译失败容易发现，金额、时间或序列化结果改变却可能一路通过接口。

| 回归路径 | 样本 | 断言方式 |
| --- | --- | --- |
| 金额计算 | 正负数、零额、大数、小数尾差 | 按业务精度逐项相等，明确舍入政策 |
| 时间和期间 | 月末、闰日、时区边界、历史时间 | 查询归属期间和输出含义相同 |
| 序列化 | null、空数组、枚举、日期、旧消费者 | 字段合同一致，旧端能读取 |
| 文件交付 | 中文 CSV、Excel、旧模板、下载文件名 | 内容一致，目标客户端可使用 |
| 异步任务 | 超时、重试、重启、重复受理 | 没有额外副作用，状态可以解释 |
| 鉴权与事务 | 未登录、越权、写入中途失败 | 权限边界不变，回滚符合政策 |
| 外部系统 | 数据库、HTTPS、邮件、文件服务 | 使用与生产相符的协议及认证配置 |

基线若已有错误，不能把“保持旧错误”当作通过标准。应单独登记差异、确认正确答案，把修复和升级的影响区分清楚。测试输出也应去除无意义波动，比如随机请求 ID；但不能为了对齐而删除金额、时区或权限字段。

新旧版本共存时，还要验证共享消息、数据库字段、缓存值和会话格式。新实例写出的值，旧实例是否能读；新任务被旧 Worker 接到会怎样；新枚举值是否让旧消费者失败。这些问题决定了灰度与回退是否真的成立。

## 6. 性能基线：怎样才能把改善归因于升级

使用相同数据、请求分布、硬件或资源配额、连接池上限、缓存策略和观测方式。分别保存冷启动与预热后的结果，避免拿一个刚启动的实例和一个充分预热的实例比较。若 GC、框架或 SQL 同时改变，应记录为组合方案，不能把全部收益归给 JDK。

| 维度 | 应记录什么 | 可能掩盖的问题 |
| --- | --- | --- |
| 业务结果 | 成功率、金额或结果集一致性 | 快了，但部分请求失败 |
| 延迟 | P50、P95、P99、超时率 | 平均值正常，长尾变差 |
| 容量 | 到达率、完成率、队列长度 | 压测端因响应变慢而自动减少施压 |
| JVM | CPU、分配速率、GC 停顿、GC 后存活量 | 只看最大堆，漏掉分配与回收问题 |
| 进程与下游 | RSS、连接等待、DB/HTTP 活跃请求 | 应用把压力转给下游 |
| 运维 | 启动时间、诊断能力、日志量 | 功能通过，滚动发布变慢 |

压测系统要报告真实到达率和未完成请求。若只采用“上一请求结束再发下一请求”的负载模型，服务越慢，实际流量越小，可能把过载藏起来。不同运行至少覆盖常规负载、峰值、持续运行与依赖变慢后的恢复；具体持续多久，由业务峰谷和问题性质决定。

验收阈值应在测试前根据现有服务目标填写。比如“关键账务样本无未解释差异，P99 不超出现有目标，峰值持续运行队列不单向增长”。这里没有实际生产 SLO，不能替你写成“必然提升 30%”。

## 7. 灰度与回退设计

先用测试环境和独立验证实例跑完业务合同，再选择受控流量进入新实例。灰度维度可以是实例、租户或接口，但要能把指标关联到版本。分组只接收轻量请求时，结果不能代表全量重负载。

放量需要一张明确的判定表：负责人、观察窗口、阻断条件、回退指令和当前制品版本。金额错误或权限异常应直接停止扩量并处置；单次长尾抖动则结合样本量和持续时间判断，避免事后凭感觉解释结果。

回退前回答下面几个问题：

1. 旧镜像和旧依赖能否直接部署，配置是否仍可用？
2. 新实例写过的数据、消息、缓存值，旧代码能否读取？
3. 长任务如何停止领取、等待完成或转交，是否会重复执行？
4. 外部已经发生的副作用怎样核对，回退后如何查询原操作？

优先采用兼容式数据变更：先新增可选字段，新旧版本都能工作，确认旧版本不再使用后再删除旧字段。回退操作也要演练，包括新实例退出前排空请求、停止领取后台任务、转交流程和恢复后的对账。

JDK 升级如果同时改变数据库结构、消息协议和业务规则，回退条件会明显增多。方案应尽量把可独立发布的变更拆开，并说明哪些约束迫使部分变更一起进行。

## 8. 虚拟线程放在迁移后的单独试点

业务迁移稳定后，再选择一个等待型接口试用虚拟线程。维持原有下游并发上限，观察阻塞位置、连接等待、内存和截止时间处理。JDK 21 的 pinning 问题应按具体调用栈验证，不能套用 JDK 24 的行为。

本套资料已经提供 [Java 21 七个语义实验](11-Java%20面试专题：并发、排障与工程取舍.md)，其中一个验证虚拟线程配合信号量限制下游并发。它不能证明迁移收益，也不能替代真实框架与驱动测试。

## 9. 把你的经历整理成可讲的材料

先补一页真实经历表，不需要写成长篇项目故事。

| 项目 | 要补的事实 |
| --- | --- |
| 为什么升级 | 当时的维护问题、依赖要求或团队目标 |
| 我负责什么 | 具体模块、依赖适配、测试、方案或上线支持 |
| 遇到过什么 | 实际错误栈、行为差异、失败样本；没有就不编 |
| 怎样取舍 | 为什么选目标版本，哪些内容分阶段做 |
| 怎样验收 | 谁确认业务正确，实际运行哪些回归，是否做过灰度 |
| 最后结果 | 已知的上线情况、问题关闭情况和有依据的指标 |

口语可以从已知事实开始：

“我参与过 JDK 8 到 21 的升级，目前项目使用 21。复盘这次经历时，我会先说明自己实际负责的模块，再展开依赖兼容、业务回归和回退设计。升级能启动只是第一步，我更关注金额和时间这类行为是否变化，以及新旧实例共存时的数据合同。”

这段话之后必须接你的真实职责，不能用“参与”代替具体工作。如果原项目没有做完整灰度，可以说“当时采用的是某种发布方式；现在重新设计，我会补上这些验证”。改进方案本身可以展示判断力，无须改写历史。

| 常见追问 | 回答应落到哪里 |
| --- | --- |
| 为什么选 21？ | 当时依赖支持、维护目标、团队能力与验证成本 |
| 最大的兼容问题是什么？ | 真实问题；若讨论练习，明确它是练习 |
| 为什么不顺便全上虚拟线程？ | 升级与并发模型分别验证，负载和下游容量有约束 |
| add-opens 算修好吗？ | 是否只是过渡、开放范围、移除条件、替代依赖 |
| 如何证明变快？ | 同负载前后对照及正确性；没数据就不报比例 |
| 出问题能直接退回 8 吗？ | 旧制品、共享数据合同、后台任务与外部副作用 |

完成这篇的学习产物是一份 2～3 页方案、依赖与样本清单、一段五分钟讲述。已有经历的复盘建议先安排 6～8 小时；需要重建原环境的部分另行估时，不把重新学习所有 JDK 版本作为求职前置条件。
