# 多项目预算核算智能分析与汇报助手

这套资料服务于七年 Java 后端开发者的社招准备。主线是：在已有预算核算数据底座上，让员工用业务语言完成多项目、不同分摊维度的查询与汇报，减少复杂页面学习、临时卡片图表定制和 Excel 加工。

面试要能讲清“为什么值得做 → 模型负责什么 → Java 怎样保证可信 → 失败如何排查 → 用什么证据验证”。不追求把所有 Agent 框架塞进项目。

## 2. 已知事实、实践假设与实现状态

| 类型 | 本项目如何表述 |

真实公司经历和独立实践在简历中分开。讨论中没有确认的业务规则不靠技术设计反推为事实。所有金额、组织 ID、运行负载和故障均为模拟；代码和图示不能冒充公司内部实现。

### 统一贯穿案例

P01 预算/实际 70/77 万元，P02 为 50/49 万元；项目总额 120/126 万元。部门 D_A 比例分别为 60%/20%，分摊后预算/实际为 52/56 万元，差异 +4 万元；D_B 为 68/70 万元。部门、团队和投资各轴独立核对，不跨轴相加。完整规则、其他轴算例和联合分摊反例在第 04 篇。

这里的核心不是记住数字，而是能指出：预算与实际用了哪套规则、结果处于什么粒度、用户有权看到哪一部分，以及图表依据哪一个结果。

## 3. 三条面试主线

**业务理解与 Agent 决策。** 用户说“按部门看”，要区分管理归属与部门分摊；明确任务直接查，不明口径才补问。模型只在已支持的工具、指标和下钻维度内选择行动，查询服务核验有效计划。

**可信计算与核对交付。** 把轴、规则、数据、指标、维度和精度政策绑定成有效语义上下文。Java 确定性计算，模型不改比例、不拼财务数组、不用文字代替金额。一个 result 支撑图表、Excel 和授权查询表。

**可定位、可恢复的工程实现。** 从最终错误追到结果、有效计划、工具与 SQL；对版本漂移、连接倍增、导出响应丢失分别给出不同措施。检查点不等于外部事务幂等，生成成功不等于任务正确。

## 4. 关键对象速查

| 对象 | 含义与权威来源 |
| --- | --- |
| requested_plan | 模型提议的业务查询候选，可能缺字段或含歧义 |
| effective_plan | Java 校验后的可执行语义计划；不能由模型自封有效 |
| allocation_axis / target | 分摊观察维度 / 维度内目标，例如部门 / D_A |
| allocation_rule_bundle | 已批准的预算、实际规则映射及比较/舍入政策；不是模型公式 |
| data_release | 固定来源批次及适用数据集合，不等于所有来源实时同步 |
| result_id | Java 产生的不可变授权查询结果引用，各格式复用 |
| skill_revision | 业务分析方法/说明的版本，不能赋予权限 |
| tool_call_id | 模型协议的调用关联标识，用于匹配工具结果 |
| operation_id | 可信执行器持久化的一次副作用意图标识，重试保持稳定 |
| trace / evidence | 排查执行的日志链 / 支撑用户结论的结果引用，各自有权限和保留策略 |

各章代码是契约示意而非已实现 SDK。rule bundle 在部分 JSON 中名为 allocation_rule_version，导出 DTO 使用 camelCase；实际接入时应统一 Schema 并做显式适配，不能把不同拼写视为多个可任意变更的语义版本。

## 5. 学习和实践方式

第一次先读 01、02、04，把架构和一个分摊例子讲顺，再补 03、05～07 的能力与边界。然后运行第 08 篇的实验，最后用 09、10 练讲述和追问。只剩一天复习时，优先看统一案例、三条主线、三个故障证据和完成状态。

已有实验附件：

- [原工程不变量实验](./code/reproduce_invariants.py)与[运行记录](./code/verification.txt)：连接倍增、比例聚合、版本固定、幂等与 Worker 发布等局部验证。
- [分摊语义实验](./code/reproduce_allocation.py)与[运行记录](./code/allocation-verification.txt)：单轴守恒、多轴错误、规则校验、分币与语义身份等，具体已执行范围见记录及第 08 篇。

模型评测另建固定案例：正常查询、必要澄清、无需澄清、跨轴不支持、越权、规则缺失、改口径与工具故障。分别记录计划正确、数值正确、正确拒绝、无谓追问、耗时和成本，不能把数据库实验通过率当成模型准确率。

## 6. 这次准备不必做成通用平台

先完成单轴受控查询和核对闭环，再做动态下钻、暂停恢复、两个业务 Skill 与薄 MCP 适配，最后才扩展有限 SQL 和多轴。保持单 Agent；预算修改、付款、任意代码执行、自动领导决策、复杂工具市场不进入范围。

业务收益需要之后用真实或模拟用户任务比较：是否能独立完成汇报、是否减少开发介入、是否选对口径、生成结果是否可信。当前只有设计与局部实验，不填写未经测量的提升数字。
