# 这套项目资料，先从这里读起

先想一个你熟悉的场景：员工要汇报十几个项目的预算和费用。数据已经进了系统，但他还得知道看哪个页面、选哪个分摊维度、怎么调整图表。现有卡片不合适，就找开发改；来不及，就导出 Excel 自己做。

这个 Agent 要帮他完成的是：**说清楚要汇报什么，就能得到口径明确、数字可核对的材料。** 例如：“把 P01、P02 上半年按部门分摊的预算和费用整理一下，做张对比图，再给我 Excel。”

> [!TIP] 先把这句话讲顺
> 模型负责理解需求、选择下一步；Java 负责权限、分摊和查数；图表与 Excel 使用同一份查询结果。后面的技术都围绕这条线展开。

## 2. 全套材料用同一组数字，避免越读越乱

| 项目 | 预算 | 实际费用 | 分给部门 D_A 的比例 |
| --- | --- | --- | --- |
| P01 | 70 万元 | 77 万元 | 60% |
| P02 | 50 万元 | 49 万元 | 20% |

所以，D_A 的预算是 **70×60%＋50×20%=52 万元**，实际费用是 **77×60%＋49×20%=56 万元**，差异为 **+4 万元**。这是后面判断查询、图表和导出是否正确的共同答案。

> [!NOTE] “按部门看”为什么值得专门做一个项目？
> P01 全项目实际费用是 77 万元，D_A 分到的是 46.2 万元。两份数据都可能来自正确的 SQL，但回答的是不同问题。Agent 必须先听懂用户要哪一种，后端再按选定的规则计算。

同一项目还可以从重量级团队、投资等维度查看。当前实践把它们当作**各自独立的分摊方式**：部门视图和投资视图不能相加，两个比例也不能直接相乘得出联合分摊。详细算例在第 04 篇。

## 4. 先认识几个词，不用记整张架构表

**查询计划**就是“这次到底查什么”的清单：哪些项目、哪个期间、哪个分摊维度、用什么预算口径。

**有效计划 effective_plan**是 Java 检查过的那份清单。模型提出候选，后端发现缺规则、没权限或口径冲突，就不会批准执行。

**结果编号 result_id**指向已经查出来并保存的结果。后面做图或导出都拿它，不再各查一遍。

**版本固定**就是一次汇报始终用同一批数据和同一套规则。否则开头查到 D_A 56 万，做图时规则变了，又变成 48.3 万，两边就对不上。

## 5. 哪些是真实背景，哪些是这次设计？

**真实背景**来自你做过的系统：多来源数据集中、多项目汇报、项目支出与人力费用、部门/重量级团队/投资等分摊维度、定制卡片图表，以及培训和更新宣讲成本。

**Agent 部分是独立实践方案。** 其中的金额、规则、组织 ID 和故障都用合成数据。各轴是否独立、怎么分币等没有确认的业务细节，在文中按实践假设处理。

目前有两组已经运行的局部实验：

- [原工程实验](./code/reproduce_invariants.py)及[记录](./code/verification.txt)：11 项，涉及 SQL 连接、比率、数据版本和导出去重。
- [分摊实验](./code/reproduce_allocation.py)及[记录](./code/allocation-verification.txt)：12 项，涉及分摊金额、跨轴错误、规则变化、分币和冲销。

**23 项检查通过，说明这些小实验的结论有依据。** 完整 Java/Agent 集成、真实模型准确率、PostgreSQL 权限隔离和 LangGraph 崩溃恢复，仍要分别验证。面试时说清做到哪一步，反而更容易接住追问。

## 6. 每学完一块，用这三个动作检查自己

选一个请求，画出它经过哪些组件；选一个错误，解释先看哪条数据或日志；最后关掉笔记，用一分钟说清为什么这个设计有用。

如果时间紧，先做**一个分摊维度、一组指标、一条查询到导出的完整路径**。接着补必要澄清、动态下钻与恢复。MCP、Skill 和 Text-to-SQL 都放回这条路径里理解，别让学习变成收集框架名称。
