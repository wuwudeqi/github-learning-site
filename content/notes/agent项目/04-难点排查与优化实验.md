# 难点排查与优化实验

> 本章包含实验设计和已运行的最小工程实验。Python/SQLite 实验已验证部分数据与幂等不变量；Java/PostgreSQL 集成、真实模型调用、LangGraph 恢复及性能收益仍待验证。示例时间线不是生产日志。

## 实验公共准备

固定合成数据随机种子，保存 schema 与初始化脚本。记录应用 Git SHA、模型标识、提示版本、依赖锁文件、温度、硬件和数据量。即使温度较低，模型输出也不能假设完全确定。

模拟基础数据：年初预算 100 万元、调整后预算 120 万元、实际发生额 126 万元、付款 90 万元。P01 调整预算 70 万元/实际 77 万元，P02 调整预算 50 万元/实际 49 万元。总差异 6 万元，由 P01 的 7 万元超支和 P02 的 1 万元结余构成。

差异贡献以有符号金额展示。若计算贡献比例，需处理负项和总差异接近零的情况，不能误以为每项贡献率都在 0～100%。

## 难点一：语法正确、执行成功，业务口径却错了

### 场景与失败基线

基线 B0：将问题与较简单的工具说明交给模型，缺失口径时允许其选择默认值。问题“研发部上半年预算执行如何”可能得到 90%，而确认后的目标口径结果是 105%。

如果模型未自然产生该错误，记录这一事实。可以直接注入错误计划测试校验器，但必须把“模型自然误判测试”和“错误计划注入测试”分开报告。

### 排查路径

1. 固定 report_release，执行人工基准 SQL，确认实际数据不是同步遗漏。
2. 比较原始工具结果与最终答案：结果对但答案错，定位生成/格式化阶段。
3. 工具结果也错时比较有效计划：budget_basis、actual_basis、period、organization。
4. 计划错则检查模型上下文：指标定义是否缺失，组织别名是否冲突，是否强制静默默认。
5. 对同一问题多次运行，统计稳定错误与不稳定输出，不挑选一次成功截图作为证据。

证据格式示意：

```text
case_id=metric-007  run_id=demo-a  release_id=rel-demo-001
requested_basis=unspecified
plan.budget_basis=INITIAL  plan.actual_basis=PAID
tool.execution_rate=0.90
expected_action=CLARIFY
```

### 修复与取舍

增加指标目录、结构化计划、业务校验和关键口径追问。默认值只能来自显式业务规则，并在答案展示。公式由后端固定实现。

追问会增加交互轮次，因此不要对不影响结果的字段机械追问；对定义明确且用户已确认的同一任务可复用条件。

### 验证

构造 30 条案例：明确表达、同义词、缺失条件各 10 条。分别检查计划字段精确匹配、应追问是否追问、合法查询结果是否一致。歧义问题不存在唯一查询真值，预期动作应是追问。

留出未用于调整提示的测试表达。比较 B0、只加提示、完整方案三个版本，避免把所有提升归因于单个组件。

## 难点二：总额与明细属于不同数据时点

### 场景与复现

基线 B0 的工具每次查询最新数据。先查总额 126 万元，用同步屏障暂停第二次工具调用；把 P02 实际从 49 万元改为 52 万元，再查询明细，合计变成 129 万元。

使用可控屏障或测试钩子，不依赖随机 sleep 碰运气。保留旧、新记录和两次查询证据。

### 排查路径

1. 确认总额与明细的组织、期间、费用过滤一致。
2. 排除一对多连接重复、空值处理、单位和舍入差异。
3. 在同一个版本重跑两条 SQL；若能对齐，说明聚合逻辑不一定有错。
4. 对照 trace 中的 source_batch、release_id 与调用时间，确认两次查询读到了不同集合。

预期证据：summary 使用旧集合，detail 使用新集合；不是“模型算错 3 万元”。

### 修复与取舍

发布不可变报表版本，分析计划绑定版本，所有汇总、明细与导出复用它。定义和组织映射也进入发布清单。发布未完成的版本不对查询开放。

代价是存储和一定延迟；解决的是本次分析可重复，不承诺各来源同时实时。简单更新时间过滤无法恢复已覆盖的数据，长事务跨模型执行也会增加资源占用。

### 验证

在同一屏障位置发布 rel-demo-002：旧 run 仍返回 126 万元及匹配明细，新 run 返回 129 万元。再测源批次失败、发布中途终止、定义更新、旧版本到期和导出复用。预期旧版本不可用时明确失败，不自动降级到最新版本。

## 难点三：响应丢失造成重复导出

![工具响应丢失与幂等恢复](./images/retry.svg)

### 场景与复现

Java 已提交 export_task，测试钩子丢弃响应或让客户端超时。无幂等基线重试后出现两条任务。第二组实验在工具成功后、Agent 保存结果前终止编排进程。

### 排查路径

1. 用 run_id 和工具调用 ID 确认第一次请求确实到达服务。
2. 查询任务表和提交日志，判断任务是否已成功创建。
3. 检查重试参数和操作 ID，确认每次重试是否重新生成身份。
4. 区分任务创建重复和 Worker 执行重复：前者看唯一键，后者看认领、租约和产物发布。

### 修复与取舍

提交前在独立节点生成并持久化 operation_id 与冻结参数；提交节点重放时复用。Java 以用户范围内的 operation_id 唯一约束返回已有任务，相同 ID 不同参数返回冲突。

Worker 采用租约和 fencing token，旧执行者不能覆盖新执行者的发布结果。Agent 通过 task_id 查询状态。检查点与任务提交不是分布式原子事务，因此始终保留业务幂等。

### 验证矩阵

| 注入位置 | 必须成立 |
| --- | --- |
| 请求发送前终止 | 恢复后能够创建任务 |
| 数据库提交后响应丢失 | 重试返回同一任务 ID |
| 并发提交同一 operation_id | 只有一条逻辑任务记录 |
| 同 ID 改变查询条件 | 返回冲突，不复用错误文件 |
| Worker 租约失效后旧进程继续 | 旧 token 无法发布产物 |
| 用户重新要求相同条件导出 | 新操作 ID 可以创建新任务 |
| 下载前权限被撤销 | 拒绝下载 |

不能只加 Redis 锁就认为完成：锁过期、进程崩溃和数据库提交的间隙仍需处理。

## 优化四：查询与模型链路耗时过高

### 基线与定位

固定案例与数据量，分开记录冷启动、冷缓存和热缓存。拆分模型调用、工具 HTTP、数据库 SQL、序列化和导出时间。并行 span 总和不等于端到端时间，应查看关键路径。

SQL 慢时检查扫描行数、连接倍增、排序和索引；SQL 快而工具慢则查结果大小与序列化；工具都快则看模型轮数、输入 Token 和队列等待。

### 按瓶颈改进

- 预算与实际若能同一聚合查询完成，优先减少往返；独立且版本一致的查询才并行。
- 明细在数据库聚合，返回主要差异项与按需分页入口，避免把整张表塞进上下文。
- 只传当前指标定义和相关证据，不无限追加历史工具结果。
- 查询与导出资源隔离，限制并发；只在线程池数量上加大可能放大数据库压力。
- 缓存作为后续优化，键必须包含权限、数据和定义版本。

### 结果记录模板

| 版本 | 成功/总案例 | 数值错误数 | P50/P95 | 每任务 Token | 查询扫描量 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 基线 | 待测 | 待测 | 待测 | 待测 | 待测 | 固定环境 |
| 优化后 | 待测 | 待测 | 待测 | 待测 | 待测 | 相同测试集 |

延迟统计包含失败与超时的单独计数，不能删掉慢失败后声称性能改善。小样本 P95 波动较大，记录样本数与重复轮次。Token 成本使用当次实际计费标准，保存核价日期。

## 公共证据包

每个实验保存：复现脚本、合成数据种子、基线与修复提交、请求输入、预期结果、脱敏 trace、SQL/任务记录、实际结果及方案限制。面试时首先解释发现过程，再展示关键证据，不背没有执行过的结果。

## 深入案例 A：把“答案错误”定位到具体组件

### 面试问题

“你说引入了指标目录，怎么知道错在模型理解，而不是数据本身？有没有排除其他原因？”

回答必须沿证据链展开，不能只说“我们不断调 Prompt”。对每个错误案例同时保存用户输入、模型计划、有效计划、工具结果、最终结论和基准结果。

| 观察 | 优先检查 | 可证伪的假设 |
| --- | --- | --- |
| 工具结果正确，答案数字错误 | 单位变换、格式化、模型抄写 | 改用服务端表格渲染后应消失 |
| 工具参数错误 | 指标映射、条件继承、别名解析 | 用同一正确计划直接调用工具应正确 |
| 参数正确，结果错误 | 数据批次、事实粒度、SQL、舍入 | 对同一数据版本执行独立基准计算 |
| 同一句话有时错有时对 | 模型不确定性、上下文、候选描述 | 固定上下文多次运行，比较计划分布 |
| 多轮追问后才错 | 历史证据与计划未失效 | 清空旧证据并建立新 plan_revision 对照 |

例如，模型选择的指标、组织和时间均正确，但 P01 预算从 70 万变成 140 万。这时增加指标提示没有意义，应该检查预算记录与两条实际明细的连接倍增。最小实验 test_01 已复现错误连接为 55%、聚合修正为 110%。

面试讲述重点：“我把语义正确、执行正确、生成正确拆成三个检查点，因此能定位到错误层，而不是把所有问题归因于幻觉。”

## 深入案例 B：改口径后，旧证据污染了新答案

### 场景

用户第一次问年初预算，工具返回预算 100 万元；随后改为调整后预算，新工具返回 120 万元。若历史工具结果全部拼接进上下文，模型可能继续引用旧预算，或把新实际与旧预算组合。

### 排查

确认第二轮计划已更新，然后按 evidence_id 查询引用来源。如果最终答案引用的证据属于 plan_revision=1，而当前是 2，根因是上下文与证据有效性，不是检索召回率或数据库缓存。

### 方案

每条证据绑定 run_id、plan_revision、release_id、metric_version。条件变化由服务端规则判断哪些证据失效；生成节点仅获得当前有效证据。校验节点拒绝跨计划引用。旧记录保留用于审计，不继续进入新轮次的有效结果集合。

计划变更还应让待提交导出失效；已提交导出保持原冻结条件，页面明确显示它对应旧口径。不能修改原任务参数来“跟随最新对话”。

### 验证与限制

构造“年初→调整后”“上半年→下半年”“研发部→全公司”三个变更轴；最后一种必须重新检查权限。每个案例验证计划、证据和文件参数同时一致。此项属于待执行 Agent 集成实验，当前最小数据库测试未覆盖。

## 深入案例 C：恢复不是从某行代码继续

### 故障时间线

以下是注入脚本应该控制的位置：

```text
T0 prepare_export: 生成 op-001，冻结 plan-3 / release-r1
T1 持久化边界完成：操作意图可在重启后读取
T2 submit_export: 向 Java 提交 op-001
T3 Java 本地事务提交 task-001
T4 丢弃 HTTP 响应 / 中断 Agent 进程
T5 恢复原 thread，读取相同操作意图
T6 submit_export 重放：仍发送 op-001
T7 Java 唯一约束命中，返回 task-001
T8 checkpoint 保存 task-001，查询最终状态
```

面试官追问 T1 之前崩溃怎么办：因为还没有发出副作用，重新生成操作意图允许；但必须保证执行顺序和持久化模式没有让 T2 提前发生。T3 与 T8 之间没有共同事务，不能消除这个不确定窗口，只能通过稳定操作身份闭合它。

### 常见无效修复

- 重试时重新生成 UUID：只是把重复请求合法化成新操作。
- 只把 HTTP 超时调长：降低故障概率，但不能解决响应丢失和进程退出。
- 只靠图 checkpoint：不了解外部数据库已提交的事实。
- 只靠 Redis 锁：锁到期后仍可能重复；任务记录需永久或在足够去重窗口内保留。
- 以参数哈希作为唯一键：会阻止用户之后合法地再次导出相同条件。

### 如何验证“一个结果”

检查任务数量、任务 ID、冻结参数以及最终 file_key，不能只看页面上有一个下载按钮。后台可能执行两次文件生成，但必须只有当前 token 的产物被采纳。最小实验验证了唯一任务和过期 token 发布失败；HTTP 故障、真正 Worker 崩溃和对象存储尚待集成验证。

## 评测设计：把成功定义清楚，再讨论优化

### 1. 任务成功不等于 HTTP 200

成功必须同时满足：动作正确、计划合法、权限正确、数值正确、证据有效；用户要求导出时，还要区分“成功创建任务”和“文件生成并可下载”。预期应拒绝或追问的案例，正确拒绝或追问也属于成功。

对“解释原因”的任务，如果只能提供贡献分析，应标为部分完成，并说明缺少业务说明；不能用一篇流畅报告掩盖证据不足。

### 2. 一份可执行的案例结构

```json
{
  "case_id": "clarify-budget-basis-001",
  "fixture": "budget-demo-v1",
  "actor": "rd-reader",
  "input": "研发部上半年预算执行如何",
  "expected": {
    "action": "CLARIFY",
    "missing_fields": ["budget_basis", "actual_basis"],
    "forbidden_effects": ["CREATE_EXPORT"]
  }
}
```

期望表达等价即可，不比较追问文字逐字相等。对完成类案例，记录规范化计划和基准金额；对安全类案例，记录禁止访问的对象；对恢复类案例，记录预期不变量。

### 3. 建议的评测分布

先设计约 60 条核心案例，数量是计划而非已有测试：明确查询 12 条，歧义与组织别名 10 条，多轮条件变更 8 条，零预算/缺数据/负数 10 条，权限与注入 8 条，导出与故障 12 条。按场景切分开发集和留出集，不能只把同一句话改几个词就当独立测试。

至少分别报告：

- 计划准确率：仅在可以直接执行的明确案例中统计。
- 必要追问召回率：应追问案例中实际追问的比例。
- 无谓追问率：条件完整案例中仍追问的比例。
- 数值正确率：明确金额/比率断言的正确比例，金额使用精确单位与舍入规则。
- 任务成功率：按案例验收组合判断。
- 未授权工具成功数：安全案例中必须为零；有限测试不代表所有攻击都已排除。
- 导出幂等违反数：故障与重复提交场景中出现重复逻辑操作的次数。

检索评测另看“正确且有效的说明是否在候选中”，再看生成是否正确引用。模型评审只作为辅助，金额、权限和任务事实用确定性检查。

### 4. 消融实验与回归

固定模型、数据、参数及案例，比较 A=基础工具说明，B=A+指标目录，C=B+计划校验与追问，D=C+证据隔离。报告各阶段错误类型和交互轮次，判断具体模块贡献。只比较“老模型+旧提示”和“新模型+新框架”无法归因。

针对非确定性模型，每个案例可运行若干次，并保存单次结果；具体次数根据预算设定。冻结留出集后不据其逐题调提示，新增失败案例进入下一轮回归集并记录版本。

### 5. 性能指标怎么解释

TTFT 适合流式响应体验，但很快输出“正在分析”不等于任务完成快。首版轮询更应看受理延迟、排队时间、分析完成时间、文件完成时间和失败率。

容量估算示例：如果平均每个分析约 4 次模型调用、每次约 3 秒、到达率每秒 2 个任务，仅模型等待就可能对应约 24 个在途任务，这是用于理解 Little 定律的假设算例，不是实测容量。是否允许并发还受模型请求/Token 配额、工具数据库容量和内存限制，不能直接把线程池设为 24 就认为问题解决。

优先做入口限流、有限队列、每租户并发额度、模型并发和数据库查询额度。队列满时明确返回繁忙，避免请求无界堆积。Python async 或 Java 虚拟线程能改善等待资源使用，但不会增加数据库和模型服务的容量。

这些检查证明局部不变量成立，不是 Agent 应用完成证明。SQLite 并发测试不能替代 PostgreSQL 隔离级别和 Spring 事务测试；没有调用真实模型，没有启动 LangGraph，也没有测得准确率提升或生产性能。
