# 一条回答是怎样生成的

## 先确定我们最终要解释什么

你输入一句问题，屏幕上的回答逐渐出现。我们要解释的是这件完整的事：**现代大模型收到什么、内部计算什么、怎样输出文字、能力从哪里来，以及聊天产品在模型之外做了什么。**

这套内容采用自顶向下的顺序：先走完一次回答的全过程，再打开其中一个模块；遇到数学问题时，再补对应的计算。第一遍不用记住所有术语，只要知道它在整个流程里负责什么。

本篇以常见的、基于 Decoder-only Transformer 的自回归文本模型为主线。现代模型还有其他架构和多模态变体；这里给出理解它们的起点，不把所有产品当成同一种内部实现。

贯穿案例是这段对话：

```text
用户：小猫饿了。请接着写一句话。
助手：它跑到食盆旁，等主人添粮。
```

后面涉及的切分、候选概率和回答都属于教学示意，不是某个真实模型的测量结果。

## 1. 先看全貌：回答是一个循环的结果

可以先把系统分成三个部分：整理输入、模型计算、生成控制。

```text
你的消息 + 被选入的历史消息 + 系统指令等
                    ↓
          整理成模型使用的对话格式
                    ↓
          切成 Token，转换成编号
                    ↓
    ┌────── 当前上下文的 Token ──────────┐
    │                  ↓                │
    │         模型计算下一个 Token 的概率 │
    │                  ↓                │
    │         生成程序选择一个 Token      │
    │                  ↓                │
    │         把它追加到当前上下文        │
    │                  ↓                │
    └──── 未结束就继续；结束后停止 ────────┘
                    ↓
         将生成的 Token 解码为可见文字
```

模型可以把“接下来有哪些可能”表示成一组概率；生成程序根据选定的策略决定这一步采用哪个 Token。下一步的计算会考虑已经生成的内容。这叫**自回归生成**。界面可以边生成边显示，也可以积累一小段再显示。[参考：Hugging Face 生成教程](https://huggingface.co/docs/transformers/v4.42.0/llm_tutorial)

> **Tip｜生成一步，不等于显示一个汉字**
>
> Token 可能对应一个字、部分词、一个词，或其他文本片段。它和屏幕上的“字”不必一一对应。先记住“生成一个单位，再继续”，具体切分稍后展开。

**现在你知道了整体行为，接下来的问题是：输入怎样进入这个循环？**

## 2. 模型实际收到的，往往不只有最后一句话

“请接着写一句话”和“请翻译成英文”会要求完全不同的输出，即使都提到同一只小猫。因此，任务要求也必须成为模型输入的一部分。

聊天应用会把不同角色的消息整理成模型训练时所使用的格式。可以把它想成下面的示意记录：

```text
[系统消息] 你是一个写作助手。
[用户消息] 小猫饿了。请接着写一句话。
[助手消息] 从这里开始生成……
```

这些方括号只是解释用标签。实际格式可能使用特定控制 Token，且不同模型不完全相同。[参考：Hugging Face 对话模板](https://huggingface.co/docs/transformers/chat_templating)

“上下文”就是这次计算能使用的输入内容。它可能包括历史对话、检索资料或工具结果，但产品需要选择、整理这些内容，不能因为聊天记录保存在界面上，就认定模型每次都看到了全部记录。

对比两种输入：

| 同样提到小猫 | 要求的后续行为 |
| --- | --- |
| 小猫饿了。请接着写一句话。 | 续写故事 |
| 把“小猫饿了”翻译成英文。 | 给出翻译 |

参数可以保持不变，输入里的任务要求改变，输出就会改变。

> **Tip｜先区分三种“记住”**
>
> 参数保存训练形成的模式；上下文提供这次可用的信息；产品保存的聊天记录或记忆，需要被重新选入输入才能影响这次回答。它们不是同一个存储位置。

## 3. 打开输入处理：文字怎样变成可计算的东西

计算模块处理的是数字。文字通常先经过两步：

```text
文字 → Token 编号 → 每个编号对应的一串数字
       分词器          Embedding
```

**Token 编号是身份标记。** 想象给文本片段分配编号：“小猫”是 17，“饿”是 42。编号大不代表意义更强，42 也不是 17 的两倍语义。这些编号仅为教学假设。

**Embedding 把编号查成一个向量。** 每个 Token 得到一串可供后续运算的数字。我们不必人为规定“第一位是动物程度，第二位是饥饿程度”；这些表示通常通过训练形成。

顺序也必须进入计算。“猫追狗”和“狗追猫”包含相同的字，但意思不同。因此模型还需要位置相关机制。这里先知道它让计算能够利用顺序，暂不展开位置编码或 RoPE 的公式。

> **Tip｜查到向量，还没有理解当前这句话**
>
> 同一个 Token 的初始向量可以相同，但它处在不同上下文中，经过后续各层计算得到的表示可以不同。真正利用上下文的加工发生在接下来的网络里。

## 4. 打开模型：Transformer 怎样加工上下文

先看一次预测所用的简化内部流程：

```text
Token 的向量表示，并在计算中引入位置信息
                 ↓
          Transformer 第 1 层
                 ↓
          Transformer 第 2 层
                 ↓
               ……
                 ↓
          Transformer 最后一层
                 ↓
    用当前末尾位置的表示，计算词表候选分数
                 ↓
          将分数转成下一 Token 的概率
```

堆叠多层，是让上一层产生的表示继续被加工。不能把它严格理解成“第一层学语法、第二层学常识、第三层做推理”；实际功能并不按这种人工课程表整齐分层。

### 4.1 一层里，先理解两个核心动作

**注意力让一个位置按计算出的权重汇集可见位置的信息。** 在“小猫饿了。它……”这个例子里，“它”与前面“小猫”的关系，是模型需要利用的上下文关系之一。具体模型是否通过某一个头实现这种联系，不能仅凭这句话断定。

**前馈网络继续加工每个位置的表示。** 它使用可训练的变换和非线性函数。注意力把其他位置的信息带进来，前馈网络对得到的表示做进一步变换。

层内还使用残差连接来保留并叠加已有表示，以及归一化来调节数值尺度。先记住这些部件共同构成一层，后续再分别解释公式和具体排列。原始论文中的层结构与现代模型的常见实现也有差别。[参考：Transformer 原始论文，第 3 节](https://arxiv.org/html/1706.03762v7)

### 4.2 Q、K、V 应该在什么时候出现

当你追问“注意力怎么决定权重、汇集什么”，才需要引入：

- Q：当前这个位置用来计算匹配分数的查询向量。
- K：各个可见位置用来参与匹配的键向量。
- V：各个可见位置参与加权汇集的值向量。

它们由位置表示经过可训练变换得到。Q 与 K 计算分数，分数经过处理得到权重，再对 V 加权求和。多个注意力头使用不同的投影并组合结果。[参考：原始论文的注意力与多头机制](https://arxiv.org/html/1706.03762v7)

这时再学点积、矩阵乘法和 Softmax，就能知道每个计算在解决哪个问题。

> **Tip｜“注意力”是计算机制的名字**
>
> 它不是人类意识，也不是一次完整思考的解释。某个注意力权重高，只描述这部分计算中的信息汇集，不能直接当作整条回答的真实原因。

### 4.3 为什么不能偷看后文

生成时，未来的文字还不存在。训练时虽然手里有完整句子，也必须阻止某个位置利用它要预测的后文，否则任务会变成抄答案。**因果遮罩**就是限制这种可见范围的机制。

所以本篇主线采用只利用已有前缀来生成的 Decoder-only 模型。原始 Transformer 的 Encoder–Decoder 翻译架构放到对照阅读，不作为理解聊天生成的第一道门槛。

## 5. 打开输出：概率怎样变成一句回答

经过模型计算后，输出层给词表里的候选 Token 打分，Softmax 将分数转换为一组和为 1 的概率。

为方便阅读，假设下面这些片段恰好各是一个 Token，当前需要生成回答的开头：

| 候选 | 教学示意概率 |
| --- | --- |
| 它 | 0.50 |
| 小猫 | 0.25 |
| 于是 | 0.15 |
| 其他候选合计 | 0.10 |

选择最大概率候选是一种策略，按概率采样是另一种策略。温度等设置可以调整采样分布的集中程度。它们影响选择方式；并不是给模型临时增加了一批知识。

假设选中“它”，之后的过程可能是：

```text
问题 + 助手开头         → 选中“它”
问题 + “它”            → 选中“跑”
问题 + “它跑”          → 选中“到”
问题 + “它跑到”        → ……
问题 + 完整回答        → 生成结束标记，或达到停止条件
```

每一步的候选分布都会重新计算。第一步给“它”的概率，不是整句话正确的概率。

> **Tip｜高概率不等于事实正确**
>
> 这里的概率是模型在给定上下文下对后续 Token 的预测分布。它不是外部事实核验结果。一个回答可以流畅、符合常见表达，同时把某个事实说错。

实际服务常复用之前位置算出的 K、V，这叫 **KV cache**。它减少重复计算；模型仍然利用已有上下文，参数也没有因此更新。[参考：Hugging Face 生成与缓存说明](https://github.com/huggingface/transformers/blob/main/docs/source/en/llm_tutorial_optimization.md)

## 6. 到这里才问：它为什么能算出有用的概率

如果所有参数都是随机的，前面的流程照样能运行，但输出通常没有用。**训练改变参数，让这些计算逐渐产生更符合数据和训练目标的结果。**

### 6.1 预训练：从大量文本中获得预测信号

仍然用教学切分，训练文本是“小猫 / 饿了 / 。 / 它 / 跑向 / 食盆”。它自然提供多道题：

| 可用前缀 | 这一步的目标 |
| --- | --- |
| 小猫 | 饿了 |
| 小猫 / 饿了 | 。 |
| 小猫 / 饿了 / 。 | 它 |
| 小猫 / 饿了 / 。 / 它 | 跑向 |

目标来自文本本身，不必请人给每个位置单独出题。常见的交叉熵损失会在真实目标概率很低时给出较大的惩罚，再通过梯度更新参数。

例如目标为“食盆”，模型给它 0.1 的概率，比给它 0.6 时受到的交叉熵惩罚更大。下一步才值得追问：这个惩罚怎么算、怎样传回每个参数？对应的手算基础见[参数、预测与训练](01-必要基础.md)。

训练时文本已知，可以在因果遮罩下并行计算多个位置的预测和损失；常规生成时后文未知，需要逐步确定后续 Token。两者使用相关的模型计算，但执行过程不完全相同。

### 6.2 只预测下一 Token，为什么能做很多任务

预测训练不是只看紧邻的一个字。模型可以利用允许范围内的整个前缀，而前缀可能是一段故事、一道数学题或一份程序。

对“把‘小猫饿了’翻译成英文：”预测后文，需要利用翻译关系；对“2 + 3 =”预测后文，需要利用算术模式；对前后人物有关联的故事续写，需要利用上下文关系。训练把这些任务的输出都放在同一个文本生成接口里。

这是理解任务与训练目标之间联系的方式，不能据此推导出“训练得够多就必然掌握所有推理”。模型学到多少、能否推广到新问题，仍需要实际评估，复杂能力的内部机制也并未被完整解释。

### 6.3 后训练：让会续写的模型更适合作为助手

基础模型能续写，并不自动意味着它会按你的要求回答。常见的后训练方式包括：

- **指令微调**：用任务与示范回答训练，让模型适应“收到要求后给出回答”的格式与行为。
- **偏好优化或强化学习**：利用回答比较、评分或可验证的结果，调整模型更倾向产生哪些输出。

这是常见方法，不是每个模型都按同一套顺序训练。InstructGPT 提供了从示范数据到人类反馈优化的公开案例。[参考：OpenAI 指令跟随研究](https://openai.com/index/instruction-following/)

> **Tip｜推理时写得更长，与训练时学得更多不同**
>
> 后训练会更新参数；部署后为某个问题投入更多生成步骤，通常是在固定参数下使用更多计算。额外步骤可能帮助分解问题或检查结果，也可能延续错误，不保证一定正确。

## 7. 现代大模型还加了什么

现在再看现代系统中的常见术语，可以把它们放回已知流程：

| 机制 | 加在什么位置 | 主要改变什么 |
| --- | --- | --- |
| MoE（混合专家） | 部分网络层内部 | 路由机制为 Token 选择部分专家计算，改变参数使用与计算开销 |
| 推理模型的后训练与额外计算 | 训练方式与生成过程 | 学习并执行更适合复杂任务的解题过程，具体实现因模型而异 |
| 图像、音频输入 | 输入表示及其后续网络 | 将其他模态转换成模型可处理的表示，与任务上下文共同计算 |
| 检索增强（RAG） | 输入准备 | 搜索外部资料，把相关内容提供给模型 |
| 工具调用 | 生成循环与外部程序之间 | 模型提出结构化调用，程序执行后返回结果，再由模型继续 |

例如公开的 gpt-oss 使用 Transformer 与 MoE，并经过预训练和面向推理、工具使用的后训练。它能作为现代文本模型的具体对照，不代表所有闭源聊天模型的实现。[参考：gpt-oss 官方介绍](https://openai.com/index/introducing-gpt-oss/)

再把问题换成“这家宠物店今天几点关门”，工具系统可能这样工作：

```text
用户问题
   ↓
模型生成搜索请求
   ↓
应用执行搜索，并把查到的内容作为工具结果加入上下文
   ↓
模型根据新增信息继续生成回答
```

新资料进入了上下文，不意味着模型为这一个问题重新训练。模型提出的调用和应用实际执行的动作也要分开理解。

> **Tip｜模型与聊天产品要分层解释**
>
> 网页搜索、文件读取、长期记忆和代码执行，往往需要模型外部的程序配合。理解 Token 生成能解释核心计算，理解输入整理与工具循环才能解释完整助手的行为。

## 8. 用自己的话走完一次回答

现在回到“小猫饿了。请接着写一句话”。尝试从头讲一遍：

1. 应用把任务要求和相关消息整理成模型的输入格式。
2. 分词器将文本转成 Token 编号，模型取得向量表示，并在计算中利用位置信息。
3. 多层 Transformer 汇集上下文、加工表示，输出下一 Token 的分数与概率。
4. 生成程序选择 Token、追加到上下文，再继续计算，直到结束。
5. 这些计算之所以有用，是因为参数经过预训练及相应后训练；普通聊天过程中通常不更新参数。
6. 如果需要最新资料或执行操作，应用可以把检索、工具执行及其结果接入循环。

如果只能背出这一段，还不算结束。下面几个换条件的问题，能检查你有没有把各部分连起来。

| 变化 | 应该能解释的原因 |
| --- | --- |
| 同一句话从续写改成翻译 | 任务要求改变了上下文，模型据此产生不同分布 |
| 同一个问题两次回答不同 | 采样可能选择不同 Token；输入或服务设置变化也可能影响结果 |
| 明确给出新资料后回答变了 | 上下文增加了信息，无需先修改参数 |
| 回答很流畅却把日期说错 | 生成概率不等于事实核验 |
| 一道题花更长时间才回答 | 可能用了更多生成、工具或调度时间，不能只凭耗时断定具体推理过程 |

### 工作日怎么学

上午 1 小时读一段主线并用自己的话复述；下午 2 小时做案例、对比和问题记录；晚上有条件时用 30–60 分钟运行实验。公司学习不依赖安装环境，章节也不要求一天读完。

最终目标首先是解释现代大模型和助手怎样工作；实现小型 GPT 是验证机制的实践路径。教学模型的生成质量与大型助手有很大差距，不把两者能力等同。进入实践前，再根据家中电脑配置与 PyTorch 熟悉程度安排实验规模。

当你读到“参数怎样更新”并希望亲手计算时，再打开[第 01 章：参数、预测与训练（按需补充）](01-必要基础.md)。
