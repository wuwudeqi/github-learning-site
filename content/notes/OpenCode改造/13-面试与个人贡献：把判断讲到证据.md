# 面试与个人贡献：把判断讲到证据

这个项目可以体现你的架构理解和 AI 辅助开发能力，但面试内容要跟实际进度一致。读完本专题时，你拥有一套设计、一份源码阅读路径和可以复现的实验。把它接入自己的 OpenCode fork、接上公司模型、经过用户验证后，才能继续讲后面的实施成果。

## 先用一段话说明项目

下面适合完成本专题实验后的陈述，只有自己实际做过并能解释的部分才保留：

> 我在做一个基于 OpenCode 的企业内部 Agent 工作台方案。研发通过 CLI 使用，非研发从 Web 或公司聊天工具发起报表和小工具任务。我先固定版本阅读了 OpenCode 的会话与执行路径，对照 DeepSeek Harness 的事件和请求边界、Codex 的工具调度与取消机制，再做了一个独立 TypeScript 实验，验证报表结果、入口去重、能力快照和取消竞态。开发中使用 Codex 编码，通过规格、手算样例和可控时序测试校验实现。目前完成的是源码分析、方案和机制实验，真实 fork 与公司环境集成按实际进度单独说明。

这段话不需要把每个术语都念完。面试官对取消感兴趣，就直接展开07的时序和对应测试；对企业落地感兴趣，就讲身份、模型协议与产物交付。

## 哪些是上游能力，哪些是你的判断

| 内容 | 上游或资料已提供 | 可以形成个人贡献的工作 |
|---|---|---|
| 会话与服务端 | OpenCode 已有相关入口和执行机制 | 企业身份与任务映射、集成契约、故障处理 |
| Skill / MCP | OpenCode 原生支持 | 公司能力发布流程、版本解析、授权和回退设计及实现 |
| 上下文压缩 | 上游已有压缩路径 | 识别任务事实、验证口径保留、产物引用与业务检查 |
| 取消 | 上游已有取消链路 | 明确业务终态、外部结果与交付时序，验证竞态 |
| AI 编码 | Codex 能生成和修改代码 | 需求判断、证据核对、测试口径、变更审查和缺陷定位 |

单纯把工具名字写进简历，面试官很难判断深度。一个更具体的贡献是：发现任务完成与文件发布不在同一个提交边界，解释故障窗口，并给出实际实现或可验证的后续方案。

> [!TIP] 把“借鉴”讲成一个决策
> 例如：“阅读 DeepSeek 的请求边界后，我决定在任务创建时保留能力版本；实验先验证标签快照不会随目录更新改变，真实远程 MCP 的版本锁定还需要服务端支持。”这比“参考了多个先进框架”更容易核对。

## 八个容易问到深处的问题

**为什么选 OpenCode，不自己写一个循环？**

因为现有会话、模型适配、工具和服务接口能减少重复工作。先验证原有能力是否满足最小场景，再判断需要扩展的位置。这个理由成立的前提是自己追过调用链，并知道哪些属于配置、插件扩展或必须改核心的变化。

**Web 底层复用 CLI，是不是用进程执行命令再读 stdout？**

目标设计优先复用执行核心与服务接口，Web 读取结构化任务和事件。研发本地任务与服务端员工任务可以使用不同实例。若采用进程封装，也要定义进程生命周期、结构化协议、工作目录和取消传递，不能把终端展示文本当稳定 API。

**Skill 版本写进数据库，是否就能复现任务？**

还不够。需要能够按版本取得实际内容，并保留相关模型、工具实现和输入。远程 MCP 的同名接口可能变更行为，版本标签不能自动锁住远端服务。当前实验只验证标签固定，实际能力加载仍待集成。

**为什么任务取消后工具还在运行？**

AbortSignal 是协作信号，工具可能不响应，外部动作也可能已经发生。实验保证取消先提交后不接受迟到产物；真实系统还要追工具退出、资源释放和外部业务结果。不能把“页面显示已取消”当作所有副作用被撤销。

**重复消息已经去重，为什么还要业务幂等？**

入口去重只识别同一消息。工具请求可能在网络重试、进程恢复或新的消息里再次出现。具有外部写入效果的业务操作需要自己的幂等键与结果查询机制，并明确键的业务范围。

**20 个测试都通过，能说明 Agent 稳定吗？**

能说明当前20个机制案例和固定数据下的行为符合断言。实验使用固定计划替身，没有模型选择与多轮质量测试，也没有多 Worker 恢复测试。模型质量与企业集成应按11的分层另做验证。

**不熟悉 TypeScript，怎样审查 AI 的代码？**

先围绕本次改动补足语言机制，例如对象别名、类型擦除、`await` 交错和 BigInt 序列化；用最小程序验证，再审查实际代码。类型检查、业务反例和运行记录相互补充。仍看不懂的关键逻辑，需要继续拆解，不能靠“测试是绿的”跳过。

**如果 AI 写错了代码，你的个人价值是什么？**

能提出不依赖实现的正确性标准，找到能复现错误的输入，判断改动位置，验证修复没有破坏其他约束。可以当场展示取消先后两个测试，解释为什么不用短暂 sleep 猜时序，以及为什么检查状态后到提交之间不能新增异步等待。

## 用一次演示支撑这些回答

先运行基础报表，展示三行输入和150、80、230的输出。再打开第15和16条测试，说明工具等待点如何受控、两种顺序分别保留哪个终态。最后打开 `runtime.ts` 的提交位置，指出它保证的是单进程内存状态，再解释多 Worker 部署需要怎样改变设计。

这条演示路线几分钟就能暴露你是否理解代码。它也允许面试官追问：如果取消发生时外部系统已经生成文件怎么办？如果事件存储被清理，旧游标怎么处理？这些问题可以如实说当前实现未覆盖，然后给出有依据的方案，避免临时承诺代码不存在的能力。

## 接下来怎样把方案变成自己的项目

先建立固定版本的 OpenCode fork 并跑通原始基线，记录环境与命令。选择一项小改造，例如把一个经过验证的报表工具接入现有工具路径，完整走一次真实模型到产物的链路。随后增加一项企业语义，并为适配层补契约测试。

到这一步，可以把“方案与实验”改写为“完成了某一处真实集成”，附上具体提交和验证记录。再经过公司实际用户验证，才写业务效果；统计口径、样本量和失败任务也要保留。

三个项目的面试分工可以保持清楚：预算 Agent 讲真实 Java 业务和工程经验；RAG 讲文档、检索与问答评测；OpenCode 改造讲执行机制、企业集成与 AI 开发方法。JDK 升级和 Oracle 迁移 PostgreSQL 的实际经历，继续作为 Java 方案设计专题展开，无需强行挂在这个 CLI 项目上。
