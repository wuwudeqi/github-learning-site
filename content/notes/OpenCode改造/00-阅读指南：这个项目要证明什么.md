# 阅读指南：这个项目要证明什么

这套资料面向有后端经验、准备转向高级 AI 应用或 Agent 工程师的开发者。项目设定是：公司提供内部模型服务，研发通过 CLI 处理代码任务，其他员工通过 Web 整理报表、制作小工具，也可以从公司聊天工具发起任务。公司统一维护 Skill、MCP 和工作流。

阅读时始终带着两个问题：这个 Agent 怎样把任务做对？如果代码主要由 Codex 编写，我凭什么相信自己能维护它？前一个问题落实到执行状态、工具边界、上下文和业务校验；后一个问题落实到需求规格、源码证据、最小实验和变更审查。

![企业内部 OpenCode 改造的学习与系统总览](images/overview.svg)

## 先看清这套资料交付了什么

| 内容 | 当前范围 | 可以据此说什么 |
|---|---|---|
| 上游源码阅读 | 固定提交，核对 OpenCode、DeepSeek Harness、Codex 的相关文件与调用关系 | 能解释已读路径、原有能力和改造位置 |
| 企业改造方案 | 设计 CLI / Web / IM 入口、内部模型、能力目录、执行和产物边界 | 能讨论设计取舍及待验证条件 |
| TypeScript 教学实验 | 合成 CSV、确定性报表计算、内存任务状态、去重、事件游标、能力快照、取消竞态 | 能运行和解释这些独立机制 |
| 真实公司部署 | 未提供模型端点、身份系统、业务凭据与实际工作负载 | 仍需 fork 集成、环境联调和业务验收 |

实验是用于理解机制的独立小程序，没有把这些新增机制接入 OpenCode fork。阅读方案、跑过实验、完成实际集成，是三个不同的进度。每次复盘和面试都应该讲到自己的真实进度。

> [!TIP] Java 经验可以直接用在判断上
> 看到消息重投、状态转换、幂等、金额精度、任务隔离时，先用熟悉的后端经验分析，再追 TypeScript 的实现。语言要补，已经形成的工程判断不需要重学。

## 一份报表贯穿全篇

所有案例数据都是为教学编造的。基础输入只有三条：销售 100.00 元、销售 50.00 元、研发 80.00 元。正确输出是销售 150.00 元、研发 80.00 元、合计 230.00 元。

小数据便于人工核算。把同一份消息发送两次、在计算尚未结束时取消、在任务创建后更新能力版本，都会让这个案例暴露不同的系统问题。金额很少，执行语义并不简单。

完整材料可以下载 [学习包 ZIP](opencode-learning-kit.zip)。它包含本专题正文、SVG 配图、代码、合成数据、规格样例与源码索引。运行入口见 [实验说明](code/README.txt)，结果记录见 [实验输出](code/output.txt)。单独查看规格时，从 [需求约定](specs/requirements.txt) 和 [验收约定](specs/acceptance.txt) 开始。

> [!TIP] 先做可讲清楚的一段
> 首轮学习的完成标准可以是：不用 AI 提词，也能解释“同一消息为什么没有重复执行”“为什么取消后迟到结果不能覆盖状态”，并能当场运行对应测试。再接真实模型和 OpenCode，排错范围会小得多。

## 怎样安排在两个月的求职计划里

每天四小时不适合同时从零做三个庞大平台。这个项目优先完成“读源码、跑通最小任务、验证一项机制、完成一处真实集成”这条路线。按自己的薄弱点分配时间：前两次学习用于业务规格与实验；接着用数次学习追源码和修改测试；真实模型及上游集成单独安排，受实际环境影响，不预设几天必然完成。

它和另外两个项目的分工也很明确：[预算 Agent](../agent项目/00-这套项目资料，先从这里读起.md) 承接 Java 业务工程经验，[企业内部 RAG](../RAG/00-阅读指南：先把一次问答看清楚.md) 解释检索和知识问答质量，本专题讲执行机制与 AI 辅助开发。更细的 Codex 执行分析可以参照 [Codex Harness 专题](../Codex%20Harness/00-阅读指南.md)。
