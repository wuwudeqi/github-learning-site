# PARSER：让阅读并行，让推理按问题推进

[arXiv:2609.06702v1](https://arxiv.org/abs/2609.06702v1)，2026-09-06 提交，v1 预印本。阅读记录日期：2026-09-11。

原题：PARSER: Read in Parallel, Reason in Depth for Long-Context LLM Agents。

作者：Kun Li、Zexuan Qiu、Tianhua Zhang、Irwin King、Helen Meng。

## 研究问题与摘要

顺序读长文时，系统必须不断把旧内容压进一小段记忆，早读到的线索可能在发现其用途之前就被丢掉。PARSER 让多个固定的小阅读器分别负责文档块，主 Agent 每轮向它们提出问题，再根据证据决定下一轮追问；只训练主 Agent，阅读器保持冻结。

实验以 Qwen3.5-4B、9B 为主干，在 HotpotQA 与分布外的 2WikiMultiHopQA 测试 7K—896K token。4B 在 HotpotQA 的平均准确率约 84.57%，比最强顺序记忆基线高约 5.7 个百分点。作者还分别改变证据位置、顺序与间隔，以判断收益是否只是碰巧读到了关键段落。

并行减少等待，但需要更多同时运行的服务。论文在最长输入、单并发下报告约 11 倍延迟改善；并发 16 时优势降到约 1.7 倍。这个差别说明，要把时延、总调用量与机器数量一起看。

## 原文怎么读

第 3 节把流程分成 scatter 与 gather：分发查询、收集局部证据，再生成后续问题。主 Agent 不直接读取原文，局部阅读器要用结构化结果保留证据，因此输出质量会限制上层推理。

训练使用约 32,768 个 HotpotQA 合成样本，每个约 28K token。训练文档块最多 512 token，推理时扩大为 4,096 token，回合上限也从 9 调到 12。这些设置意味着“只换框架不改配置”的复现并不完整。训练与阅读器部署使用多张 H100，本期未运行。

值得追问：重复阅读是否增加总 token 成本？主 Agent 汇总大量无关结果时是否出现新的压缩损失？现有结果主要来自多跳问答，不直接证明对所有法律文档、长代码库或跨模态材料同样有效。复现实验应保留顺序阅读、单轮并行和多轮并行三类对照。
